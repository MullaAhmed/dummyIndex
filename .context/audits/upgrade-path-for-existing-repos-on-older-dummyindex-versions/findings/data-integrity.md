## data-integrity findings

- `dummyindex/export/storage.py:L274-L286` — **high** — every sharded graph write adds new content-addressed shards and never deletes unreferenced ones, so committed `.context/features/symbol-graph.parts/` grows with every rebuild. Evidence: the module docstring (`storage.py:L1-L5`) and the inline comment at L285 say "Never remove old shards". Nothing else prunes them: no shard sweep exists anywhere, and `gc/enumerate.py:L36-L60` only walks `proposals/` and `audits/`. On disk: 91 files, 12 referenced by the current manifest, 79 orphans (73,171,940 bytes), and all 79 orphans are git-tracked. The HEAD manifest referenced 13 shards, while release commit `23f4113` committed 79, so 66 were already orphans when committed. The plain-JSON branch (`storage.py:L239-L241`) orphans every existing shard when a graph shrinks below 1 MB. A side effect: the evolve gate (`evolve_gate.py:L140-L184`, `L464-L481`) reads all tracked bytes, orphan shards included, and writes them into a temp workspace twice per candidate. Only `evolve_native_snapshot.py:L51-L82` filters this "generated history" out. Crash ordering is sound: shards are fsync+replace written (`L199-L215`) before the manifest (`L286`). Only the directory fsync is missing. Suggested fix: after `_atomic_write(path, encoded_manifest)`, unlink `symbol-graph.parts/<64hex>.json` files whose digest is not in the just-published descriptors (or keep the previous generation only, so a reader holding the old manifest can finish). Do the same sweep on the `<= max_file_bytes` branch, and ship a one-time cleanup in the upgrade path for repos already carrying orphans. status: open

- `dummyindex/pipeline/io/cache.py:L106-L126` — **high** — the extraction cache key is the SHA-256 of file content only, but the cached payload holds path-bound identity (`id`, absolute `source_file`). Every later file with identical bytes therefore gets the first file's nodes and drops out of the graph. Evidence: `save_cached` (`L211-L240`) stores the extractor result verbatim. `extract/__init__.py:L197-L203` serves it for any path with matching bytes. `id_remap` (`L249-L257`) only rewrites `_make_id(str(path))` of the current path, so the foreign id survives. `portable_graph.py:L186-L200` then dedupes the identical canonical records into one. The cache entry `e3b0c442…b855.json` (empty content) holds `"source_file": "D:\\Projects\\dummyindex\\tests\\__init__.py"`. Verified: 22 of 23 empty `__init__.py` files are missing from `features/symbol-graph.json` but all 23 are in `map/files.json`. `dummyindex/context/output/__init__.py` (same blob as `domains/__init__.py`) is also missing. The same collapse removes the symbols and call edges of any duplicated non-trivial file (vendored copies, fixtures, templates). Because `source_file` is absolute, a moved repo is also served old-location paths that `_relative_path` (`portable_graph.py:L105-L119`) cannot relativize, which contradicts the "survives repository moves" claim at `cache.py:L109-L113`. Suggested fix: store path-free payloads (strip or tokenize `id`/`source_file` and re-bind to the requesting path on load), or include the repo-relative path in the key. status: open

- `dummyindex/pipeline/io/cache.py:L186-L208` — **high** — cache entries have no extractor, schema or dummyindex version, so after an upgrade unchanged files keep returning extraction from the old code indefinitely. Evidence: the key is content-only (`L106-L126`). `_is_valid_cache_payload` (`L164-L183`) checks only `nodes`/`edges` shape. Downstream reads tolerate missing newer fields, e.g. `extract/__init__.py:L328-L329` `result.get("raw_calls", [])`, so a pre-`raw_calls` entry silently yields zero cross-file call edges. No installer or update path touches `cache/` (grep found no `cache` handling under `installer/` or `skills/update/`). Measured: 466 of 537 live entries used by today's 0.37.0 refresh were written on 2026-11-05, before the 0.37.0 tag (2026-11-06 20:57 UTC). Whether that code produced different output is not proven, but nothing in the code would detect it if it did. Suggested fix: put a cache-format/extractor version (at minimum `PACKAGE_VERSION`) in the key or a `cache/<version>/` subdir, and drop other-version dirs on refresh. status: open

- `dummyindex/context/build/enriched_refresh.py:L154-L195` — **medium** — on the install refresh path, `meta.json`'s `dummyindex_version` advances before the source-docs catalog and symbol graph are rewritten. Both of those swallow failures, so the stamp can claim the new version while the graph and catalog are still the old generation. Evidence: `_refresh_meta` runs at `L154-L163`. `write_catalog` failure becomes a warning (`L183-L188`), and so does `build_graph` failure (`L190-L195`). An exception from `refresh_summaries` (`L169-L176`) propagates after the stamp has already moved. `project_init.py:L77-L89` reports "refreshed N deterministic artefact(s)" and returns success, and `skills/update/SKILL.md:L161-L166` verifies the update by comparing that stamp. `build_all` has the same shape: `write_meta`, carrying `indexed_commit=HEAD` (`runner.py:L138-L145`), runs first in `_write_all` (`runner.py:L487-L489`), before the graph and feature scaffolding, whose failures are warnings only (`runner.py:L198-L233`). So the reconcile anchor can advance past features that were never regenerated. Suggested fix: stamp `meta.json` last, and only advance `dummyindex_version`/`indexed_commit` when every required artifact landed. Otherwise exit non-zero or record a `partial` marker that `check --versions` reports. status: open

- `dummyindex/context/build/enriched_refresh.py:L106-L110` — **medium** — the upgrade path for curated indexes (install calls `refresh_deterministic_artifacts`) runs none of the legacy-layout migrations or managed-gitignore upgrades, so per-version artifacts from older releases are never migrated or removed. Evidence: the refresh calls only `ensure_context_gitattributes`. `ensure_context_gitignore` and `remove_legacy_enrich_plan` run only inside `_write_all` (`runner.py:L483-L485`). `migrate_legacy_layout` (`cli/migrate.py:L35-L92`, which moves the legacy `graph/` and relocates `CLAUDE.md`) is called only from `refresh-indexes` (`cli/refresh.py:L36-L37`). Yet `project_init.py:L74-L89` and `skills/update/SKILL.md:L125-L129` document the curated install path as the update mechanism. Suggested fix: run one idempotent `migrate_context_layout(context_dir)` step (gitignore merge, legacy file removal, orphan shard sweep, retired-dir handling) from `refresh_deterministic_artifacts`. status: open

- `dummyindex/export/storage.py:L260-L268` — **medium** — 0.37 changed the committed format of `features/symbol-graph.json` (manifest plus shards) without moving any version marker that older clients check. A teammate on 0.36 or earlier reading a 0.37-committed `.context/` gets hard errors or silently empty results. Evidence: `meta.json` `schema_version` stays `1` (`dummyindex/context/build/meta.py:L14`), so `read_meta`'s "newer than this build" gate (`meta.py:L69-L73`) never fires. In 0.36, `38c3602:dummyindex/context/domains/graph_query/load.py:L64-L71` raises `GraphArtifactInvalidError` "expected node-link JSON" on the manifest. `38c3602:dummyindex/context/domains/features/scan/refs.py:L34-L41` `_symbol_graph_ids` returns an empty set when `nodes` is missing, so every curated `symbolRef` reads as dangling. `reality_check/verify.py` returns no call edges. A 0.36 refresh then overwrites the manifest with plain JSON and orphans every shard. Suggested fix: bump `meta.schema_version` (or add a `graph_format` key that older readers reject) when emitting the manifest format, so old clients fail with "Upgrade dummyindex". status: open

- `dummyindex/context/domains/config.py:L614-L638` — **low** — the config migration is a lossy round-trip: `Config.from_dict` reads a fixed key set and `to_dict` (`L241-L260`) emits only those keys, so any unknown top-level key or unknown `build.*` sub-key is silently dropped from the committed `config.json`. Evidence: `from_dict` (`L263-L354`) never carries extras. The same `write_config` path is used by `reconcile_wired_with_equipment` (`L692-L692`) and `reconcile_default_plugins` (`L725-L732`), so up to three sequential read-modify-write rewrites run per install (`project_init.py:L342-L346`). `write_config` (`L751-L755`) is tmp+replace but uses a fixed `config.json.tmp` name and no fsync. This repo's diff (schema 4→5, `opus-4.8`→`opus`, added `build`) lost nothing only because no extra keys existed. A future schema newer than 5 is correctly refused (`L85`, `L273-L278`). Suggested fix: keep `payload` keys not consumed by `from_dict` in an `extras` mapping and merge them back in `to_dict`. status: open

- `dummyindex/context/build/maps.py:L292-L296` — **low** — the multi-file build has no lock, and every writer uses a fixed `<name>.tmp` sibling, so two concurrent builds on the same checkout (e.g. a manual `rebuild --changed` during `install`) can interleave writes into the same tmp file and leave mixed-generation artifacts. Evidence: the same fixed-tmp pattern appears in `meta.py:L101-L109`, `tree.py:L331-L332`, `conventions.py:L247-L251`, `config.py:L751-L755` and `cache.py:L226-L230`. No lock exists anywhere in `context/build/` (grep for `lock|flock|msvcrt` found none). `enriched_refresh.py:L127-L195` writes about 10 artifacts in sequence, so a crash mid-run leaves e.g. a new `map/files.json` beside the old `symbol-graph.json`. Suggested fix: use `tempfile.NamedTemporaryFile(dir=…, delete=False)` unique tmp names (as `storage.py:L199-L215` already does) plus a `.context/cache/build.lock` around `build_all` and `refresh_deterministic_artifacts`. status: open

- `dummyindex/pipeline/io/cache.py:L211-L240` — **low** — `.context/cache/` is append-only and nothing ever evicts entries, so every edited file version leaves a dead entry behind. Evidence: there are 760 entries (24 MB); only 537 are reachable from current `map/files.json` content hashes, so 223 are dead. Entries are up to about 298 KB. No delete path targets `cache/` (`unlink`/`rmtree` grep across `cli/` and `context/` found no cache eviction). The cache is gitignored (`runner.py:L343-L355`), so this is disk-only, but it grows without bound on long-lived checkouts. Suggested fix: after `extract`, drop `cache/<sha>.json` entries not hit in this build (or apply LRU/age eviction), possibly together with the version-scoped dir from the finding above. status: open
