## correctness findings

- `dummyindex/installer/install/family_write.py:122-144` — **high** — A Windows junction from `~/.claude/skills/<family>` to the owned canonical `~/.agents/skills/<family>` is treated as a "custom or unproven family" on every path. As a result every install exits 1 with `error: partial installation; edited, unproven or failed families were preserved`, and rerunning never converges. — evidence:
  - **Three different definitions of "link".** `_install_skill_references` skips only `directory.is_symlink()` (L128), which is False for a junction. `link/classify.py:230-249` uses `stat.S_ISLNK` only, so it classifies the junction `NOT_A_LINK` ("real directory"). `ownership._is_link` (`ownership.py:63-73`) does treat reparse points as links, so `_plain_target(directory, "SKILL.md")` returns `None` (`ownership.py:52-54`) and `family_is_pristine` returns False (`ownership.py:128-134`).
  - **Reproduced on this machine.** Python 3.13 in the uv-tool venv reports, for all 10 families: `is_symlink False`, `_is_link True`, `pristine False`, `classify NOT_A_LINK` (lstat `S_ISDIR=True`, `st_reparse_tag=0xa0000003`). A dry run of `_install_skill_references`, with `sync_family` stubbed out, printed `custom or unproven family; shared reference not installed` for **all 10** families and returned `False`. The 5 families the conductor saw are a subset, probably from truncated output. `create_family_links` skips the same way (`link/create.py:354-361`).
  - **Not a regression of 0.36.0 output.** `git grep -i "junction\|mklink\|CreateJunction" v0.36.0 -- dummyindex/` is empty, and so is the 0.37 installer. The junctions date from Nov 5 18:02, before today's install. So this is not "0.36 installed it and 0.37 forgot". It is an inconsistent ownership model that cannot recognize a link to its own canonical copy.
  - **The "restamped 0.37.0" main skill is an illusion.** `orchestrate.py:212-214` and `repair.py:204-212` read `.claude/skills/dummyindex/.dummyindex_version` *through* the junction, so they see the `.agents` stamp that `_install_skill_family(base, "codex")` just wrote (`orchestrate.py:207-211`). The same mechanism explains why the skill descriptions "changed in-session".
  - **Knock-on: repair makes a promise it cannot keep.** It reports "migration candidate … converted to a link the next time install selects claude" (`repair.py:307-326`), but `create.py:357` never converts.
  - **Knock-on: false source warnings.** `check --versions` picks `platform="claude"` through `copy.path.is_symlink()` (`cli/check.py:267-269`). It therefore emits a false `user claude source: dummyindex: skill source differs despite its version stamp` even from the correct 0.37.0 uv CLI. Reproduced.
  - **Knock-on: contradictory reports.** The same uv CLI prints `dummyindex versions coherent (0.37.0)` after an install that exited 1. This happens because auto-init and the `.context/meta.json` stamp run before the completeness exit (`orchestrate.py:325-344` runs before `356-361`).
  - suggested fix: detect a mount-point reparse tag via `os.lstat(...).st_reparse_tag == stat.IO_REPARSE_TAG_MOUNT_POINT` (py3.8+; don't rely on `Path.is_junction`). Classify a junction whose resolved target equals `family_link_target(...)` as `OURS_HEALTHY`, or normalize it to the canonical symlink. Make `_install_skill_references`' skip use `_is_link` rather than `is_symlink()`. Treat this as one shared "is link" predicate across `classify`, `family_write`, `check` and `ownership`. status: open

- `dummyindex/installer/legacy_fingerprints.py:1-8` — **high** — The legacy ownership catalog covers exactly one prior release (`LEGACY_VERSION = "0.36.0"`). Any skill family installed by dummyindex ≤0.35.x can therefore never be upgraded, and the docs offer no way out. — evidence:
  - **Input.** A family dir with no `.dummyindex-files.json` (every release before 0.37 wrote none; `ownership.py` was added in 23f4113) and a stamp other than `"0.36.0"`.
  - **No baselines.** `_baselines` returns `{}` for it (`ownership.py:106-116`).
  - **Rendered SKILL.md always differs.** It embeds `__VERSION__` (`common.py:208`), so its bytes change in every release. `sync_family` therefore preserves it as unproven (`ownership.py:197-202`), so `complete=False` and the stamp is never written (`ownership.py:217`, `234`).
  - **The failure propagates to exit 1.** `execute_repairs` raises `preserved customized or unproven files; repair is incomplete` (`repair.py:477-481`). That puts the host in `failed_hosts` (`orchestrate.py:199-202`), which leads to exit 1 (`orchestrate.py:356-361`) on every rerun.
  - **No override exists.** The usage block has no adopt/override flag (`args.py:26-49`). The update skill forbids the manual escape: "Do not delete or rebase preserved files" (`skills/update/SKILL.md:143-146`).
  - **Contradicts the module's own purpose.** `repair.py:3-6` says repair "repairs skill-family copies an older dummyindex version left behind".
  - **Two ownership tests now disagree.** `is_owned_copy` is stamp-based (`common.py:333-348`) and `family_is_pristine` is hash-based. `classify` and repair accept a family on the stamp, then the replace/sync path refuses it on the hashes.
  - suggested fix: generate a cumulative catalog of stock hashes per released tag (LF/CRLF × both host renders) instead of a single version. Alternatively add an explicit `--adopt-stock` mode that backs up and replaces unproven files whose stamp is any older release. status: open

- `dummyindex/installer/ownership.py:207-216` — **medium** — When `sync_family` retires files it unlinks them but leaves their parent directories behind. `family_is_pristine` then rejects any directory that has no baseline child (`ownership.py:139-142`), so after any upgrade that empties a companion directory the family is permanently "unproven". — evidence:
  - **Concrete current trigger.** A pristine full Claude copy is converted to a thin reference by `_install_skill_references` (`family_write.py:134-153`, `layout="reference"`). Two common sources of such a copy are the 0.36 Windows copy fallback and a 0.37 `--copy` install that is later rerun under AUTO without symlink capability. The main family's `agents/`, `council/` and `retrieval/` (and `dummyindex-audit/agents/`) are left empty.
  - **Result.** The next install reports `custom or unproven family; shared reference not installed` and exits partial.
  - **Reproduced in the scratchpad.** `sync_family(full) → pristine True`, then `sync_family({"SKILL.md": ref}, layout="reference") → removed ('agents/a.md','council/b.md')`. Empty `agents/` and `council/` remain, and `family_is_pristine` returns False.
  - **Existing precedent for the fix.** `remove_family` already prunes emptied parents (`ownership.py:282-294`); `sync_family` does not.
  - suggested fix: after the removal loop in `sync_family`, rmdir emptied parents the way `remove_family` does. Or let `family_is_pristine` ignore empty directories. status: open

- `dummyindex/installer/common.py:11-16` — **medium** — `PACKAGE_VERSION` comes from `importlib.metadata`. In an editable install that metadata is frozen at install time, so the version can lag the source. Here the `.venv` holds `dummyindex-0.36.0.dist-info` while `pyproject.toml:7` says `0.37.0`. Every version-stamp comparison is then wrong even though the source is identical. — evidence:
  - **False skew report.** `.venv/Scripts/dummyindex.exe context check --versions` prints `running CLI 0.36.0` and "version skew detected". It also prints `skill source differs despite its version stamp` for every user Claude and Codex family, because `render_skill` substitutes `__VERSION__`→`0.36.0` (`common.py:208`).
  - **Yet the source is identical.** The same run reports `running CLI source: 8d37861b…`, the same hash as the 0.37.0 uv tool.
  - **A venv-run install would fail.** `sync_family` sees the 0.37.0 `.agents` stamps as `newer` (`ownership.py:171-178`), preserves everything and exits partial unless `--force-downgrade` is passed. With that flag it would stamp 0.37 content as 0.36.0.
  - suggested fix: base the stamp gate on source identity (`package_source_hash`), or detect an editable dist (`direct_url.json` `dir_info.editable`). For an editable dist, read the version from source or `pyproject` and refuse to compare stale metadata. At minimum, have `check --versions` say "editable metadata stale" instead of reporting skew. status: open

- `dummyindex/context/build/enriched_refresh.py:269-299` — **medium** — `_refresh_meta`'s docstring says it "advances `dummyindex_version`". The code instead overwrites the stamp whenever the value differs (`!=` at L298). An older or stale CLI running `rebuild --changed` therefore downgrades `.context/meta.json`, and `"unknown"` overwrites a real version. — evidence:
  - **The CLI stamps whatever metadata says.** `cli/rebuild.py:62-66` reads `importlib.metadata.version` (falling back to `"unknown"`) and passes it through `rebuild_changed` → `refresh_deterministic_artifacts` → `_refresh_meta` (`context/build/incremental.py:169-174`).
  - **The managed guidance tells agents to run exactly this command.** `rebuild --changed` is prescribed in `bootstrap.py:99` and `agents_md.py:40-41`. In this repo PATH resolves to the 0.36.0-metadata `.venv` (see the editable-install finding), so the curated index's `0.37.0` stamp would become `0.36.0`.
  - suggested fix: write the version only when `_compare_stamp(new, old) == "newer"`, or when the old value is unparseable and the new one is parseable. status: open

- `dummyindex/skills/update/SKILL.md:39-118` — **medium** — The update skill measures, updates and verifies three potentially different binaries. When PATH resolves to a different CLI than the one updated, its idempotency check either never converges or stops early. — evidence:
  - **Measure.** Step 1 reads `dummyindex --version` from PATH (L39); here that is `.venv` → 0.36.0.
  - **Update.** Step 2 reinstalls "the **first**" of `uv tool` / `pipx` / pip that lists dummyindex (L79-90); here that is the uv tool in `~/.local/bin`. The "mirror exactly where `which dummyindex` resolves" rule (L95) applies only inside the virtualenv conditional, so it does not fire.
  - **Verify.** Steps 3-4 say "run the **newly installed** CLI" but issue bare `dummyindex install …` (L114-118) and `dummyindex context check --versions` (L163). Both resolve to PATH, which is the `.venv` again.
  - **Failure mode A: never converges.** The Idempotent rule (L27-31) compares a CLI that step 2 never touches, so it reinstalls on every run.
  - **Failure mode B: stops early.** If the PATH CLI is current while the tool install is stale, it stops before updating.
  - **Step 3 would hit the editable-version bug.** It would run the venv installer with `PACKAGE_VERSION=0.36.0` against 0.37.0 stamps.
  - **Minor.** L106 tells Codex to use the deprecated `--platform codex` alias (`common.py:175-182`).
  - suggested fix: resolve the updated install's absolute binary once (e.g. `uv tool dir --bin`, `pipx environment`), invoke it by absolute path for version, install and check, and stop with a diagnostic when `which dummyindex` differs from it. status: open

- `dummyindex/cli/check.py:149-166` — **medium** — The PATH-shadow detector compares `Path(sys.argv[0]).resolve()` with `shutil.which("dummyindex")` (L311-316). It reports the same binary as shadowing itself, swaps the "repo-local" and "global" labels, and cannot detect the actual shadow case it describes. — evidence:
  - **Same binary reported as shadowing itself.** The venv run printed `a repo-local dummyindex (…\.venv\Scripts\dummyindex) is shadowing the global CLI on PATH (…\.venv\Scripts\dummyindex.exe)`. `argv[0]` lacks the `.exe` that PATHEXT resolution adds.
  - **Labels inverted.** Running `~/.local/bin/dummyindex.exe` explicitly labels the global uv tool "repo-local" and the venv "global".
  - **The real case is invisible.** When invoked through PATH (venv first, uv tool second; `which -a` lists both), the running and resolved paths are equal, so no warning fires.
  - suggested fix: normalize via PATHEXT, compare against every `which -a` candidate, and label by `sys.prefix` (venv vs tool env) rather than by argument position. status: open

- `dummyindex/installer/common.py:233-265` — **low** — The `/tokens` command file that 0.36 installed is permanently "edited or unproven" even though it is byte-identical to stock. — evidence:
  - **What 0.36 wrote.** It used `shutil.copy` (`git show v0.36.0:dummyindex/installer/common.py` L264): a byte copy, CRLF from this Windows-built package. It wrote no stamp in `~/.claude/commands/`.
  - **How 0.37 compares.** It hashes the LF-normalized `read_text` (L259) and has no `dummyindex-commands` entry in `LEGACY_FILES`.
  - **On-disk result.** `cmp` confirms `~/.claude/commands/tokens.md` equals the packaged file. Even so, the written manifest is `{"complete": false, "files": {}}`.
  - **Consequences.** Future `/tokens` changes will never land. `remove_commands` → `remove_family` with empty baselines removes nothing on uninstall (`ownership.py:263-276`). The failure is silent because `_install_commands`' result is not folded into `complete` (`orchestrate.py:301-309`).
  - **Side effect.** `sync_family` drops `.dummyindex-files.json` into the user's shared `~/.claude/commands/`.
  - suggested fix: treat a byte-for-byte match against the packaged file (raw bytes, newline-insensitive) as a baseline, or add commands to the legacy catalog. status: open
