## Security

- `dummyindex/context/domains/gc/delete.py:88-107` — **`--path` skips guards 2 and 4 and containment permits the kind-root itself, so one command wipes every proposal or every audit.** `_reject_sentinel` is gated on `if safe_slug is not None` (`:88-89`), and a `path=` caller has `safe_slug is None`, so the sentinel guard never runs on that route; guard 3 then compares `resolved_target` against `resolved_root` with `_is_relative_to` (`:106`, `:273-284`), and `root.relative_to(root)` returns `Path(".")` rather than raising — so the root **is** "inside" itself and passes. Guard 4 reads `proposal.json` / `checklist.md` of the *target directory* (`:117`, `:174-221`), which for a container is absent, so liveness contributes no block. Verified end-to-end at the CLI on a throwaway tree: `gc delete --kind proposal --slug alive --yes` correctly refuses an `in_progress` proposal (exit 2), while `gc delete --kind proposal --path .context/proposals --yes` deletes that same in-flight proposal *plus* every sibling *plus* the entire `_archive/` tree and reports `removed proposal` at exit 0; `--kind audit --path .context/audits --yes` does the same to all audits. Only guard 5 remains, and on a committed `.context/` it passes by design. `--slug _archive` is refused (`:166-167`) while `--path .context/proposals/_archive` succeeds — the sentinel guard is bypassed by renaming the flag, not by defeating it. **Mitigation: none.** `plan.md:133-136` asserts the opposite ("reachable for deletion only through `--path`, which the realpath guard contains … keeps the sentinel guard … from being trivially bypassable") — the code contradicts the plan and the code wins; `SKILL.md:132-135` republishes the same false ladder to the agent. Nothing machine-enforced bounds a delete to one workspace: `--yes` is a flag any caller types and the CLI cannot distinguish a user-confirmed invocation from an unconfirmed one, so `SKILL.md:64,112` ("confirmation always gates deletion") is prose over an unenforced boundary — the guard ladder is the only real trust boundary between a skill-driven agent and `rmtree`, and on the `--path` route three of its five rungs are absent. Fix: reject a target equal to the kind-root, run `_reject_sentinel` against every path component of a `path=` target, and evaluate liveness across the target's descendants rather than only its own head files.

- `dummyindex/context/domains/gc/signals.py:63-64` — **an ARCHIVED candidate's confirm-gate evidence is read from a different directory than the one that gets deleted.** `classify` builds `workspace = proposal_dir(context_dir, candidate.slug)` = `proposals/<slug>`, but `enumerate.py:98` places archived children at `proposals/_archive/<slug>`; `Candidate.rel_path` already carries the right location and is ignored. Verified two distinct failure modes on throwaway trees. (a) *Same-slug live twin* — re-proposing a slug after archiving is the ordinary retry path: an archived workspace holding a real hand-authored `plan.md` and a half-done checklist reported `signals=['orphan-empty', 'checklist-partial', 'age-0d']`, the `orphan-empty` read wholly from the pristine never-authored live twin. `orphan-empty` is precisely the tag `SKILL.md:51` names as a *dead doc* ("an orphan scaffold"), so the council presents "nothing was ever written here, nothing is lost", the user confirms on that evidence, and authored work is destroyed. (b) *No live twin* — the candidate probes a nonexistent path and reported `signals=['age-0d']` only: no `checklist-partial`, so the one signal that would warn "this is mid-flight" silently never appears, and `age-<n>d` alone is the exact "looks old" non-evidence `SKILL.md:116` tells the council to drop. This is a confused-deputy defect at the only gate the architecture actually relies on — the design deliberately emits no machine verdict (`enums.py:8-20`, `Disposition` constructed nowhere) precisely so the human confirm carries the decision, and that confirm is being fed another directory's attributes. It composes with threat 1: deleting an `_archive/*` child is reachable only via `--path` (`plan.md:133-136`), the route with no sentinel guard. **Mitigation: none** — the delete-side liveness guard (`delete.py:117`) does read the true target, which limits this to decision integrity rather than a guard bypass, but no test covers it: `tests/cli/test_gc_cli.py:104-119` builds an archived dir with neither `plan.md` nor `checklist.md`, masking both modes. Fix: resolve the workspace from `candidate.rel_path`.

- `dummyindex/context/domains/gc/delete.py:233-238` — **a symlinked `.context/` silently disables the recoverability guard, deleting never-committed work permanently without `--allow-untracked`.** `_is_tracked` computes `target.relative_to(repo_root.resolve())` and, on `ValueError` (target outside the repo root), returns `True` — "treat as tracked so recoverability never blocks (containment already passed)". But guard 3 resolves symlinks on *both* sides (`:104-105`), so a `.context/` symlinked outside the repo satisfies containment while placing every target outside `repo_root`, making the untracked branch unreachable. This is not hypothetical for this project: dummyindex ships a link-mode single-source install, so a symlinked `.context/` is a supported topology. Verified: with `.context -> ../elsewhere/.context` and a workspace committed to no repo at all, `gc delete --kind proposal --slug untracked-work --yes` printed `removed proposal` at exit 0 and the directory is unrecoverable. The comment's premise is wrong — "outside the repo root" here means *no git recoverability whatsoever*, the strongest reason to refuse, not a reason to wave through. The user-facing promise this breaks is explicit: `SKILL.md:66` requires "the user's explicit okay on *that specific risk*" before `--allow-untracked` is added, and `spec.md:98-99` states untracked deletion "needs a second `--allow-untracked`". **Mitigation: none** — the `git ls-files` probe never runs on this path, and the off-git rationale at `delete.py:228-231` (git "never made a recoverability promise there") is sound only for a genuine non-repo, which `_is_git_repo` (`:258-270`) can distinguish and is not consulted here. Fix: on `ValueError`, probe whether the *resolved target's own* directory is inside some git work tree before degrading to tracked.
