## Data integrity

- `dummyindex/context/domains/gc/delete.py:104-107` — guard 3 accepts `resolved_target == resolved_root` (`Path.relative_to(self)` returns `.`, never raises), so `gc delete --kind proposal --path .context/proposals --yes` rmtree'd the **entire** proposals tree including all of `_archive/` (reproduced: only `.context` survived) and `--path .context/audits` does the same — reject equality and require the target to be a direct child of the kind-root (or `_archive/<child>`), and run `_reject_sentinel(resolved_target.name)` on `--path` targets too, not just slugs.
- `dummyindex/context/domains/gc/delete.py:224-255` + `dummyindex/context/domains/gc/enumerate.py:173-189` — `git ls-files --error-unmatch <dir>` exits 0 when *any one* file under the workspace is in the index, so a committed workspace holding freshly-written uncommitted files reports `tracked=True`, emits no `untracked` signal, and is deleted without `--allow-untracked` (reproduced: an audit whose `audit.json` was committed lost a new `report.md` permanently, `git show HEAD:...` → "does not exist"), which silently voids the skill's own permanence gate at `dummyindex/skills/gc/SKILL.md:66` — probe recoverability with `git status --porcelain --untracked-files=all -- <dir>` (empty ⇒ every byte is in the index) instead of `ls-files`.
- `dummyindex/context/domains/gc/signals.py:63-64` — the architect's flag is confirmed and understates it: `proposal_dir(context_dir, candidate.slug)` resolves an ARCHIVED candidate to `proposals/<slug>`, so when a live proposal shares the slug the archived row's tags are computed from the **live** workspace's files (reproduced: archived row printed `checklist-complete` while its own `checklist.md` was 0/1), feeding the council cross-contaminated delete evidence — use `context_dir / candidate.rel_path`, which already carries the right location.
- `dummyindex/context/domains/gc/delete.py:143-147` + `dummyindex/cli/gc.py:261-273` — delete keys on `(kind, slug)` while the report keys rows on `rel_path`, and `--kind archived` is unselectable, so the only slug form available for an `_archive/*` child (which `dummyindex/skills/gc/SKILL.md:51,72-75` explicitly tells the council to delete) resolves to `proposals/<slug>` and **deleted the live proposal while the archived one survived** (reproduced) — accept the report's `rel_path` as the delete target, or route `--kind archived` to `proposals/_archive/<slug>`.
- `dummyindex/context/domains/gc/delete.py:136` — the bare `shutil.rmtree` is neither atomic nor caught: a mid-tree `PermissionError` left `plan.md`/`spec.md` deleted, `locked/` intact, no `DeleteResult`, and an unhandled traceback at exit 1 (reproduced), which falsifies the recovery story at `.context/features/gc/plan.md:81-84` — the retry is not a no-op because the dir still exists, and the half-deleted workspace has lost the `proposal.json`/`checklist.md` that guard 4 reads, so liveness stops protecting an `in_progress` proposal on the second attempt; rename the workspace into a sibling temp dir first (atomic) then rmtree, and map `OSError` to `DeleteResult(refused=...)`.
- `dummyindex/context/domains/gc/anchor.py:139-143` + `dummyindex/cli/gc.py:166` — `--to` is persisted verbatim with no validation, so `gc stamp --to HEAD~5` stored the literal string `"HEAD~5"` as the anchor (reproduced) and any rev-expression or typo permanently darkens the nudge (`commits_since → None → should_signal False` forever) while `dummyindex/cli/gc.py:251-255` misreports the corruption as "history rewrite" — resolve through `git rev-parse --verify <to>^{commit}` and exit 2 when it does not resolve, so only a real 40-char sha is ever written.
- `dummyindex/context/domains/gc/anchor.py:176-182` — the prune calls `kv[1].get(...)` on every memo value, so one non-dict entry plus a memo over the 100 cap raises `AttributeError` out of `should_signal` (reproduced), contradicting the "corrupt-tolerant by construction … never raises" claim at `.context/features/gc/plan.md:65-68` (`_load_memo` validates only the top-level dict) — filter to `isinstance(v, dict)` entries in `_load_memo`, mirroring the anchor reader's per-key type check at `anchor.py:53-54`.
- `dummyindex/context/domains/gc/delete.py:116` — guard 4 is `kind in _PROPOSAL_KINDS`, so an AUDIT gets no liveness backstop at all: an audit panel mid-run (no `report.md` yet, every evidence file uncommitted) is indistinguishable from a finished one to the ladder and, combined with the `ls-files` hole above, is destroyed permanently by a single `--yes` — refuse an audit workspace lacking `report.md` unless `force_partial`, mirroring the proposal branch.
- `dummyindex/context/domains/gc/scan.py:51-53` — `enumerate` accepts any on-disk dir name (`enumerate.py:126-135` filters only `_`/`.` prefixes) but `classify` re-validates it through `proposal_dir` / `report_written`, so a dir such as `proposals/foo bar` kills the *read-only* sweep with an unhandled `ProposalSlugError` traceback at exit 1 (reproduced) — the one command whose job is to report a messy `.context/` cannot run against one; have `classify` build the workspace from `candidate.rel_path` (no re-validation) and let enumerate surface an out-of-charset dir as a signal rather than a crash.
- `dummyindex/context/domains/gc/delete.py:83-97` — the "exactly one of slug/path" precondition is documented but unenforced, so a caller passing both has guards 1–2 validate the *slug* while `path` silently becomes the delete target (`path is not None` wins at line 93); only `dummyindex/cli/gc.py:119-120` prevents it today, one flag-parsing change away from a validated-one/deleted-another split — raise `GcTargetError` in `delete_workspace` when both are given.
- `dummyindex/context/domains/gc/scan.py:58` vs `dummyindex/context/domains/gc/anchor.py:117-123` — the JSON key `should_signal` means "over threshold" in the report but "over threshold AND memo unconsumed" in the probe, so after `gc signal` fires, `gc status --json` still reports `should_signal: true` for that same session and any consumer keying on the report (`dummyindex/skills/gc/SKILL.md:31`) re-nudges — emit `over_threshold` plus `already_signalled` instead of one name carrying two contracts.

## Security

- `dummyindex/context/domains/gc/delete.py:88-107` — **`--path` skips guards 2 and 4 and containment permits the kind-root itself, so one command wipes every proposal or every audit.** `_reject_sentinel` is gated on `if safe_slug is not None` (`:88-89`), and a `path=` caller has `safe_slug is None`, so the sentinel guard never runs on that route; guard 3 then compares `resolved_target` against `resolved_root` with `_is_relative_to` (`:106`, `:273-284`), and `root.relative_to(root)` returns `Path(".")` rather than raising — so the root **is** "inside" itself and passes. Guard 4 reads `proposal.json` / `checklist.md` of the *target directory* (`:117`, `:174-221`), which for a container is absent, so liveness contributes no block. Verified end-to-end at the CLI on a throwaway tree: `gc delete --kind proposal --slug alive --yes` correctly refuses an `in_progress` proposal (exit 2), while `gc delete --kind proposal --path .context/proposals --yes` deletes that same in-flight proposal *plus* every sibling *plus* the entire `_archive/` tree and reports `removed proposal` at exit 0; `--kind audit --path .context/audits --yes` does the same to all audits. Only guard 5 remains, and on a committed `.context/` it passes by design. `--slug _archive` is refused (`:166-167`) while `--path .context/proposals/_archive` succeeds — the sentinel guard is bypassed by renaming the flag, not by defeating it. **Mitigation: none.** `plan.md:133-136` asserts the opposite ("reachable for deletion only through `--path`, which the realpath guard contains … keeps the sentinel guard … from being trivially bypassable") — the code contradicts the plan and the code wins; `dummyindex/skills/gc/SKILL.md:132-135` republishes the same false ladder to the agent. Nothing machine-enforced bounds a delete to one workspace: `--yes` is a flag any caller types and the CLI cannot distinguish a user-confirmed invocation from an unconfirmed one, so `dummyindex/skills/gc/SKILL.md:64,112` ("confirmation always gates deletion") is prose over an unenforced boundary — the guard ladder is the only real trust boundary between a skill-driven agent and `rmtree`, and on the `--path` route three of its five rungs are absent. Fix: reject a target equal to the kind-root, run `_reject_sentinel` against every path component of a `path=` target, and evaluate liveness across the target's descendants rather than only its own head files.

- `dummyindex/context/domains/gc/signals.py:63-64` — **an ARCHIVED candidate's confirm-gate evidence is read from a different directory than the one that gets deleted.** `classify` builds `workspace = proposal_dir(context_dir, candidate.slug)` = `proposals/<slug>`, but `enumerate.py:98` places archived children at `proposals/_archive/<slug>`; `Candidate.rel_path` already carries the right location and is ignored. Verified two distinct failure modes on throwaway trees. (a) *Same-slug live twin* — re-proposing a slug after archiving is the ordinary retry path: an archived workspace holding a real hand-authored `plan.md` and a half-done checklist reported `signals=['orphan-empty', 'checklist-partial', 'age-0d']`, the `orphan-empty` read wholly from the pristine never-authored live twin. `orphan-empty` is precisely the tag `dummyindex/skills/gc/SKILL.md:51` names as a *dead doc* ("an orphan scaffold"), so the council presents "nothing was ever written here, nothing is lost", the user confirms on that evidence, and authored work is destroyed. (b) *No live twin* — the candidate probes a nonexistent path and reported `signals=['age-0d']` only: no `checklist-partial`, so the one signal that would warn "this is mid-flight" silently never appears, and `age-<n>d` alone is the exact "looks old" non-evidence `dummyindex/skills/gc/SKILL.md:116` tells the council to drop. This is a confused-deputy defect at the only gate the architecture actually relies on — the design deliberately emits no machine verdict (`enums.py:8-20`, `Disposition` constructed nowhere) precisely so the human confirm carries the decision, and that confirm is being fed another directory's attributes. It composes with threat 1: deleting an `_archive/*` child is reachable only via `--path` (`plan.md:133-136`), the route with no sentinel guard. **Mitigation: none** — the delete-side liveness guard (`delete.py:117`) does read the true target, which limits this to decision integrity rather than a guard bypass, but no test covers it: `tests/cli/test_gc_cli.py:104-119` builds an archived dir with neither `plan.md` nor `checklist.md`, masking both modes. Fix: resolve the workspace from `candidate.rel_path`.

- `dummyindex/context/domains/gc/delete.py:233-238` — **a symlinked `.context/` silently disables the recoverability guard, deleting never-committed work permanently without `--allow-untracked`.** `_is_tracked` computes `target.relative_to(repo_root.resolve())` and, on `ValueError` (target outside the repo root), returns `True` — "treat as tracked so recoverability never blocks (containment already passed)". But guard 3 resolves symlinks on *both* sides (`:104-105`), so a `.context/` symlinked outside the repo satisfies containment while placing every target outside `repo_root`, making the untracked branch unreachable. This is not hypothetical for this project: dummyindex ships a link-mode single-source install, so a symlinked `.context/` is a supported topology. Verified: with `.context -> ../elsewhere/.context` and a workspace committed to no repo at all, `gc delete --kind proposal --slug untracked-work --yes` printed `removed proposal` at exit 0 and the directory is unrecoverable. The comment's premise is wrong — "outside the repo root" here means *no git recoverability whatsoever*, the strongest reason to refuse, not a reason to wave through. The user-facing promise this breaks is explicit: `dummyindex/skills/gc/SKILL.md:66` requires "the user's explicit okay on *that specific risk*" before `--allow-untracked` is added, and `spec.md:98-99` states untracked deletion "needs a second `--allow-untracked`". **Mitigation: none** — the `git ls-files` probe never runs on this path, and the off-git rationale at `delete.py:228-231` (git "never made a recoverability promise there") is sound only for a genuine non-repo, which `_is_git_repo` (`:258-270`) can distinguish and is not consulted here. Fix: on `ValueError`, probe whether the *resolved target's own* directory is inside some git work tree before degrading to tracked.
