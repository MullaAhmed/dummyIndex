## Data integrity

- `dummyindex/context/claude_settings.py:175-179` — `write_settings` writes through a **fixed-name** tmp sibling (`settings.json.tmp`) with no uniqueness, no `try/except`, and no `unlink`, so the exact scenario `atomic_io._replace_bytes:13-18` was made unique-named for ("hooks from two Claude profiles can update the same repo-local cache concurrently") interleaves two writers into one tmp and `replace`s truncated JSON over the user's `settings.json` — the single file every preserve-or-refuse guard in the plan exists to protect — fix: route it through `atomic_io.write_text_atomic`.
- `dummyindex/context/domains/equip/lifecycle/manifest.py:59-70` — `write_manifest` is a second fixed-tmp writer (`equipment.json.tmp`), so a concurrent `apply`/`refresh`/`patch` corrupts the ledger and `read_manifest:39-51` then hard-raises `EquipError` on *every* later equip verb plus `domains/audit/catalog.py`; the plan's Data-model claim that per-file atomicity holds "precisely because [two profiles] can write concurrently" (`plan.md:140-143`) is true of only one of the five writers — fix: same unique-tmp primitive.
- `dummyindex/cli/equip/dispatch.py:596-606` — `_write_file` is a third fixed-tmp writer (`<agent>.md.tmp`) that bypasses `write_text_atomic` entirely, and since `origin_hash` is computed from the **in-memory** string (`:458-459`) and never re-read from disk, a torn write records a baseline for bytes that were never persisted and pins the item to `USER_MODIFIED` forever — fix: call `write_text_atomic`.
- `dummyindex/context/domains/config.py:662-681` — `write_config` is the fourth fixed-tmp writer and has no `try/except`; combined with the read-modify-write at `cli/equip/install.py:479-482` and `config.py:610-618`, a concurrent `equip install` and init-time `ensure_wired_defaults` lose each other's `config.wired` entries (the docstring at `install.py:458` concedes "Single-writer per repo (no locking)" without enforcing it) — fix: unique tmp, and re-read + merge `wired` immediately before the write.
- `dummyindex/context/domains/equip/lifecycle/status.py:243-303` — `refresh` writes each refreshed file inside the loop (`:291`) but persists the manifest only once after it (`:300-303`), so an `OSError` out of `write_text_atomic` on file N leaves files 1..N-1 rewritten against stale baselines, which `classify_item:165-171` then reads as `USER_MODIFIED` and `refresh` skips **forever** — fix: persist the accumulated `new_items` in a `finally`, or re-baseline per item.
- `dummyindex/context/domains/equip/lifecycle/status.py:377-403` — `uninstall` appends a marketplace item to `removed` (`:381`) *before* attempting `disable_plugin`, swallows `MalformedSettingsError` (`:388-389`), then unlinks the manifest anyway (`:403`), so a still-enabled `enabledPlugins` key is orphaned with its only ledger record deleted and simultaneously reported as removed — fix: skip the manifest unlink (and drop the name from `removed`) when any un-wire failed.
- `dummyindex/cli/equip/dispatch.py:499-540` — only `MalformedSettingsError` is caught around `wire_hooks`, but `claude_settings.write_settings:177-179` raises a bare `OSError` (read-only `.claude/`, ENOSPC), which escapes as a traceback *after* the generated files are written and *before* the manifest write — producing exactly the unrecorded-files partial state the "files first, then hooks, then manifest" ordering was designed to prevent — fix: catch `OSError` alongside `MalformedSettingsError`.
- `dummyindex/cli/equip/dispatch.py:453-459` — on a re-render the freshly built `item` wins the merge and only `version`/`origin_hash` are carried forward from `prior_item`, so a prior record's v3 provenance (`marketplace`, `origin_repo`, `origin_ref`, `mechanism`) and its `grounded_in` usage playbook are silently dropped from the ledger — fix: `dataclasses.replace(prior_item, …)` with the new render's fields rather than replacing onto `item`.
- `dummyindex/context/domains/equip/models.py:114-133` + `dummyindex/cli/equip/dispatch.py:535` — `from_dict` ignores unknown keys and `to_dict` emits a fixed key set while `apply` unconditionally stamps `schema_version=SCHEMA_VERSION`, so a manifest written by a newer dummyindex that added a *field* (the way `invariants` was added at `:99-102`) loads cleanly, is stripped of that field, and is stamped back down to v4 — silent forward-incompatible data loss, in contrast to the enum path which `manifest.py:45-51` does guard — fix: raise `EquipError` (or round-trip the unknown keys) when `schema_version > SCHEMA_VERSION`.
- `dummyindex/cli/equip/dispatch.py:480,515-522` — the dedupe/carry-forward key is `name` alone, ignoring `kind` and `path`, so a prior record whose name collides with a differently-pathed item this run is dropped and its on-disk file becomes an orphan that no lifecycle verb (`status`/`refresh`/`uninstall`) can ever see or clean up — fix: key the carry-forward on `(kind, name)` and warn when a surviving record's `path` changed.
- `dummyindex/context/default_plugins.py:388-409` + `dummyindex/context/claude_plugins.py:113-124` — `_declare_marketplace` runs its identity-conflict check against one `load_settings` (`:388`) and then hands the write to `add_marketplace`, which re-reads and upserts (`:114-123`), so a settings write landing between the two reads bypasses the guard and clobbers a foreign marketplace declaration — the plan's "mechanism in the base layer, policy in its caller" split (`plan.md:216-219`) is a TOCTOU as implemented — fix: perform the guard and the write inside one read-modify-write, or pass the already-loaded dict through.
- `dummyindex/context/domains/equip/lifecycle/remove.py:15-17,60-79` — the module docstring promises "we never half-remove: record kept on refusal", but the file `unlink` (`:70`) and the marketplace un-wire (`:76`) both precede `write_manifest` (`:79`), so an `EquipError` on the manifest write leaves the file deleted and the plugin disabled with the record still claiming both exist — fix: correct the docstring, or persist the manifest first and only then perform the destructive steps.
- `dummyindex/context/domains/atomic_io.py:13-34` — no `fsync` on the tmp handle (nor on the parent directory) before `replace`, so a crash or power loss can surface a zero-length or stale generated file whose content no longer matches its recorded baseline, converting every affected item to permanently-skipped `USER_MODIFIED` — fix: `handle.flush(); os.fsync(handle.fileno())` inside the `with`.
- `dummyindex/context/domains/atomic_io.py:40-45` — the byte-faithful contract's own rationale cites `equip/lifecycle/hashing.text_hash`, which does not exist anywhere in the tree (the function is `content_hash`, `lifecycle/hashing.py:17-19`), so the single docstring explaining *why* this writer must never normalize points at nothing — confirmed, and code wins — fix: rename the reference to `content_hash`.
- `.context/map/symbols.json` vs `dummyindex/context/domains/atomic_io.py:13-50` and `dummyindex/context/domains/equip/generate/catalog.py:75` — verified stale: the index records `write_text_atomic` at 12, `normalize_eof_newline` at 28, and `build_catalog` at 61 (actual: 37, 50, 75) and omits `_replace_bytes` and `_all_templated_capabilities` entirely, so tracing the hash-baseline write path from the index lands on the wrong lines — fix: `dummyindex context rebuild --changed`.
