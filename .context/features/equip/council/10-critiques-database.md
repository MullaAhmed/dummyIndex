## Data integrity

- `dummyindex/context/domains/equip/lifecycle/evolve.py:41-70` — `apply_patch` checks only `is_lifecycle_managed` and never calls `classify_item`, so a USER_MODIFIED or INVARIANT_BROKEN body that still contains `old` once is patched and re-baselined to PRISTINE+evolved. That erases the alarm `dispatch.py:493-495` deliberately preserves, and a later `uninstall` then **deletes the user's edited body** (`status.py:378-391`), where before the patch it would have kept it. This contradicts plan.md:64-67 ("user-owned bodies are never rewritten or re-baselined") and plan.md:75-76 ("second writer under the same rule"): the other writer, `evolve_gate.py:306-309`, refuses "edited outside evolve", and `tests/context/domains/equip/test_equip_evolve.py` only patches pristine items. Code wins. Fix: raise `PatchError` unless `classify_item(root, target_item) is ItemState.PRISTINE`.
- `dummyindex/cli/equip/dispatch.py:626-632` + `dummyindex/context/claude_settings.py:175-179` — only `MalformedSettingsError` is caught around `wire_hooks`. `write_settings` uses a fixed `settings.json.tmp` and has no `unlink` and no Windows `PermissionError` retry, unlike `atomic_io._replace_bytes:56-65`. So a plain `OSError` escapes `_apply_write` after the bodies are written (`:551`) and before `write_manifest` (`:663`) or `restore_migrations` run. Every re-rendered body now differs from its old recorded hash and reads USER_MODIFIED forever. Converted legacy files now hold pointers while their records keep the legacy hash, so they also read user-owned forever, and the canonical copies are untracked. Plan.md:83-85's "restore reverts converted legacy pointers" does not hold on this path. Fix: route `write_settings` through `write_text_atomic` and catch `OSError` with `MalformedSettingsError`, which then still writes the manifest.
- `dummyindex/cli/equip/dispatch.py:306-307,661-663` + `dummyindex/context/domains/equip/lifecycle/manifest.py:53-69` — every equipment.json writer (apply, `refresh` `status.py:232,313-316`, `patch`, `reset`, `remove`, `install.py:267,284-287` and `:316,329-332`) does read-modify-write on its own snapshot with no lock and no compare-before-replace. `write_manifest` also uses a fixed `equipment.json.tmp`. Two sessions (the concurrency `atomic_io.py:41-42` names) therefore either lose a record or tear the file. Losing a record: a concurrent `equip patch` re-baseline is overwritten by apply's stale `prior`, so the patched body becomes USER_MODIFIED. Tearing the file: `read_manifest:38-41` then hard-raises on every verb. Plan.md:81-82's "no record silently drops" holds only against the snapshot. Fix: write through `_replace_bytes`, and re-read and compare the manifest bytes immediately before replacing (abort or re-merge on change).
- `dummyindex/context/domains/equip/lifecycle/status.py:297-316` — `refresh` writes each body inside the loop (`:303`) but writes the manifest once after it. An `OSError` on item N leaves items 1..N-1 rewritten against stale baselines, which then read USER_MODIFIED and are skipped forever. `run_refresh` (`verbs.py:132-134`) has no `except`, and the reinstall path catches `Exception` and prints "refresh skipped" (`installer/install/project_init.py:212-214`) even though bodies did change. `reset` (`:345-356`) and `patch` (`evolve.py:62-70`) have the same body-before-ledger order, and a patch retry then fails exact-once. Fix: write the manifest in a `finally` with the items processed so far, or re-baseline per item.
- `dummyindex/context/domains/equip/lifecycle/status.py:401-427` — `uninstall` adds each marketplace item to `removed` (`:405`) before `disable_plugin`, swallows `MalformedSettingsError` (`:412-413`), and still unlinks the manifest (`:427`). A local-scope plugin whose `.claude/settings.local.json` is malformed therefore stays enabled, loses its only ledger record, and is reported as removed. Conversely, `remove_hook_entries` (`:424-426`) is unguarded (`verbs.py:251` has no `except`). A malformed `settings.json` raises there after pristine bodies and pointers were already unlinked (`:389-394`), so the user gets a traceback and no report. `remove.py:70-82` deletes the file and un-wires before `write_manifest`, despite its "never half-remove" docstring (`:16-17`). Fix: keep the ledger and drop the name from `removed` on any un-wire failure, and persist the ledger before destructive steps.
- `dummyindex/context/domains/equip/models.py:156-196,273-282` — `from_dict` ignores unknown keys, `to_dict` emits a fixed key set, and `read_manifest` never gates on `schema_version`. So a manifest from a newer dummyindex that added a field loads cleanly. `refresh` then writes it back without the field, and `apply`/`install` also re-stamp it as v4 (`dispatch.py:661`, `install.py:286`). The enum guard (`manifest.py:44-50`, `constants.py:11-13`) covers only added enum values. `evolve_gate.py:323` explicitly "Keep[s] unknown fields", so the two writers disagree. Fix: raise `EquipError` when `schema_version > SCHEMA_VERSION`, or round-trip unknown keys.
- `dummyindex/cli/equip/dispatch.py:551,562-581` — the canonical body is written before the legacy→pointer conversion. When `write_native_adapter` warns, `written` keeps the legacy `prior_item` and leaves the new body at `.context/equipment/<name>.md` untracked. It warns, for example, when `.claude/agents` is a symlink or junction, which the `:483` guard never checks because it walks only `rel_path`'s parents. `restore_migrations` (`:467-478`) likewise leaves canonical bodies behind. After the next template change, `_matches_content` (`:528-540,723-727`) treats that orphan as "existing user file, not ours", so the migration stalls permanently and `uninstall` never sees the file. Fix: check the adapter path's parents before writing the canonical body, or unlink the canonical body when the migration is declined.
- `dummyindex/context/domains/atomic_io.py:38-68` — no `fsync` on the temp file or its directory before `replace`. This matters most at `context/build/upgrade.py:440-445`: `_back_up` (`:447-470`) is followed immediately by `_unlink` (`:485-493`), so a crash before writeback can lose both a user-edited retired file and its backup, which spec.md:107-112 promises is backed up first. The provenance read (`:298`) and the backup read (`:454`) are also separate from the unlink, so an edit made in between is deleted without a copy. Separately, the `atomic_io.py:76` docstring cites `equip/lifecycle/hashing.text_hash`, which does not exist; the real function is `content_hash` (`hashing.py:17-19`, `map/symbols.json`). Code wins. Fix: `flush()` + `os.fsync()` inside the `with`, unlink only when the bytes still equal the backed-up bytes, and rename the docstring reference.
