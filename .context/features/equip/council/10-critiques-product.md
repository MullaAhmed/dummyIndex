## Product surface

- **A generated file exists on disk but its manifest record is gone** (manifest hand-edited, lost, or written by an older equip). Live in this repo: `.claude/agents/dummyindex-performance-specialist.md` carries `<!-- dummyindex:generated -->` but `.context/equipment.json` holds 9 items and none is `dummyindex-performance-specialist`. `equip status` cannot see it; `refresh`/`reset`/`uninstall` skip it (all gate on `is_lifecycle_managed`, `lifecycle/status.py:82-94`). The next `apply` takes the `elif not is_safe_to_write(target)` branch (`cli/equip/dispatch.py:460-467`), and `is_safe_to_write` returns True on any file containing the sentinel (`wiring/safety.py:19-34`) — **gap: the file is overwritten with no baseline comparison, so a hand-edited generated file with no manifest record is clobbered by the exact operation the never-clobber contract exists to prevent.**

- **`uninstall` then `apply`.** `uninstall` deliberately keeps user-owned files and reports them (`lifecycle/status.py:358-368`), then deletes `.context/equipment.json` (`lifecycle/status.py:403`). The kept file now has no record and still carries the sentinel — **gap: the next `apply` silently overwrites the edit `uninstall` just promised to preserve; this is the previous bullet reached through a documented, single-step happy path.**

- **User deletes a generated specialist to decline it.** `refresh` reports it `skipped(missing)` and does not recreate it (`lifecycle/status.py:259-262`), but `apply` rewrites it (`cli/equip/dispatch.py:450-459`) because `_all_templated_capabilities` hands the whole templated alphabet to every pass (`generate/catalog.py:62-72`). `remove NAME --delete-file` drops the record and the file, and the next `apply` regenerates both. **Gap: there is no persistent decline. The only off-switch is editing the file into a no-op so the hash baseline freezes it — the opposite of the intuitive gesture (delete), which is the one that does not stick.**

- **Project slug or stack label changes** (repo renamed, stack re-detected). The prior record is carried forward verbatim (`cli/equip/dispatch.py:512-533`). `reset NAME` refuses it: `not a generated item in the current catalog` (`cli/equip/verbs.py:193-198`). `refresh` reaches `fresh = fresh_renders.get(item.name)` → `None` → appends to `unchanged` (`lifecycle/status.py:275-277`). **Gap: an orphan record is reported as "unchanged", indistinguishable from a genuinely current item, in both `refresh` and `status`; only `remove` clears it, and only if the caller already knows the stale name.**

- **`equip status` on this repo, right now.** Prints 8 generated rows. It prints no row for the wired `ruff-format` hook (record excluded by `path == ".claude/settings.json"`, `lifecycle/status.py:89-94`), and no row for the three reviewed default plugins that are enabled in `.claude/settings.json` (`superpowers@claude-plugins-official`, `caveman@caveman`, `i-have-adhd@i-have-adhd`) because they are never written to the manifest (`default_plugins.py:676-760`). **Gap: the two things dummyindex most recently changed about this repo's Claude config are the two things its own status verb cannot report.**

- **User asks to remove a reviewed default plugin.** `equip remove superpowers@claude-plugins-official` raises `RemoveError: no manifest item named …` (`lifecycle/remove.py:57-60`), and `equip uninstall` only walks `EquipmentSource.MARKETPLACE` manifest items (`lifecycle/status.py:377-390`), of which there are zero here. `--no-default-plugins` is a one-run installer flag (`installer/args.py:42-43`). **Gap: `dummyindex/skills/equip/SKILL.md:199-203` states uninstall "disables any plugins equip enabled (and drops their marketplaces)" — for the three plugins equip actually enabled in this repo, it disables none. The doc contradicts the code; the code wins.**

- **User disables a default plugin through Claude Code's `/plugin` UI**, which writes an explicit `false`. `wire_default_plugins` reads `_effective_enabled` → `False` → files it under `already` and moves on (`default_plugins.py:526-528`), so the tombstone survives re-init — correct. But `disable_plugin` **pops the key entirely** rather than writing `false` (`claude_plugins.py:158-171`), so `equip remove` / `equip uninstall` on a marketplace item leave no tombstone. **Gap: the two off-paths are asymmetric — the UI's off sticks, equip's own off does not, and a later `init`/`wire` pass re-enables what equip removed.**

- **`equip status` reports a marketplace plugin as `pristine`.** `_classify_marketplace` reads only `enabledPlugins[name] is True` in the settings file (`lifecycle/status.py:112-123`). Whether Claude Code actually materialized the plugin lives in `~/.claude/plugins/installed_plugins.json`, read only by the separate `equip verify` verb (`cli/equip/plugin_state.py:107-146`). **Gap: `status` says pristine for a plugin that never loaded; the caller has to know `verify` exists and run it per-target — `status` neither checks nor mentions it.**

- **Re-installing a vendored skill after editing it.** `install` refuses with "run `equip uninstall` first to re-vendor" (`cli/equip/install.py:413-419`). `uninstall` keeps user-owned files and deletes the manifest (`lifecycle/status.py:362-365`, `:403`), so the edited `SKILL.md` remains with the `<!-- dummyindex:installed -->` stamp and no record — the re-install then hits `_vendor_write_ok`, which accepts a `VENDORED_SENTINEL`-bearing file (`cli/equip/install.py:290-300`) and overwrites the edit. **Gap: the printed recovery instruction either fails to clear the block or silently discards the edit it was protecting, depending on which guard fires — and it also destroys every other manifest record as collateral.**

- **`equip install --scope user`.** Wires `~/.claude/settings.json`, deliberately writes no manifest record (`cli/equip/install.py:186-196`) and skips the `config.wired` write-back. **Gap: the install prints success, then `status` shows nothing and `uninstall` removes nothing — the scope flag silently opts the target out of the entire lifecycle, and neither the flag's help text nor the success line says so.**

- **Preview before a destructive verb.** `refresh` and `uninstall` accept `--dry-run` (`cli/equip/verbs.py:152`, `:262`). `reset`, `remove`, and `patch` do not — no flag is parsed in `run_reset`/`run_remove`/`run_patch` (`cli/equip/verbs.py:175-325`). `reset` overwrites a user's edit; `remove --delete-file` deletes a file; `patch` mutates content. **Gap: `SKILL.md:600-601` makes "show the dry-run output or the patch's old→new before any refresh / patch / reset / uninstall" a completion checklist item, and for three of those four verbs no such output exists — the operator has to hand-simulate it.**

- **`equip apply` on a fresh repo.** Seeds one `<tool>.suite.json` per generated tool, silently (`cli/equip/dispatch.py:542-545`, `cli/equip/seed.py`). The prompts are literal placeholders — `"<replace: a synthetic prompt that SHOULD trigger …>"` — and they land under `.context/`, which is committed (8 such files are git-tracked here). **Gap: an unannounced write of committed placeholder files; the apply summary line (`cli/equip/dispatch.py:560-567`) counts written / adopted / carried / skipped / preserved / evolved and never mentions them.**

- **`equip status` immediately after a first `apply`.** Every managed tool is listed `unevaluated … (no eval result — run equip eval)` (`cli/equip/verbs.py:121-145`) — 8 lines on this repo, doubling the output. Running the suggested `equip eval` scores the placeholder suite from the previous bullet. **Gap: the nag is unconditional and un-suppressible, and following it produces a meaningless score rather than a signal; there is no `--no-eval-hints` or per-tool opt-out.**

- **Cost of `hooks install` per session, measured on this repo (2026-08-06).** SessionStart spawns four separate `dummyindex` processes (`context/hooks.py:147-198`): `plan-update` 3.81 s, `gc signal` 1.45 s, `memory session-start` 1.16 s, `memory mine` 1.11 s. `UserPromptSubmit`'s second command runs `memory prompt-context` at 1.13 s on **every** prompt (`context/hooks.py:132-142`). `PreToolUse` runs `guard-doc-write` at 1.06 s on **every** `Write` (`context/hooks.py:245-267`). A `--global` install prefixes a `defer-check` spawn to each command (`context/hooks.py:287-290`). **Gap: none of these are disclosed as a latency cost anywhere in `hooks install` output or `SKILL.md`, no per-hook timeout is set, and no verb disables a single event — `hooks uninstall` is all-five-or-nothing.**

- **Hook bodies drift after an upgrade.** This repo's `.claude/settings.json` SessionStart entry has 3 commands and the pre-`memory mine` managed comment ("reports drift / gates reconcile / nudges memory"), while the shipped constant has 4 commands and different text (`context/hooks.py:70-73`, `:147-198`). `hooks status` reports `SessionStart ✓` because `_claude_hook_installed` tests presence only (`context/hooks.py:694-713`, `:716`). **Gap: stale hook bodies are invisible to the only verb that inspects them; the sole repair is a blind reinstall, which the plan itself flags as an open question (`plan.md:269-273`).**

- **Team-wide behavior contract.** `UserPromptSubmit` carries `ALWAYS_ON_TURN_REMINDER` and is described as load-bearing precisely because it survives a missing CLI (`plan.md:221-230`, `context/hooks.py:105-145`). `hooks status` on this repo reports `claude/UserPromptSubmit ✗`. **Gap: the contract that is supposed to always fire is absent from the repo that ships it, and nothing surfaces that — no SessionStart notice, no `equip status` row, no drift report.**

- **Formatter hook added to a repo that already formats on write.** `wire_hooks` upserts under `DUMMYINDEX_EQUIP:<event>` and scrubs only its own legacy sentinel (`wiring/hooks.py:31-55`); `_format_hooks` decides purely from the detected stack (`generate/catalog.py:147-178`). Live result here: two `PostToolUse` entries with overlapping matchers — the user's `.claude/hooks/ruff-check.sh` on `Edit|Write` and equip's `ruff format` on `Write|Edit`. **Gap: equip never inspects existing hook entries for an equivalent formatter, so every Write/Edit runs ruff twice and the apply output reports it as a clean `wired 1 hook event(s)`.**

- **Caller follows the skill's "Channel B" flow.** `SKILL.md:226-270` presents `npx skills` / skills.sh as a co-equal discovery-and-install channel and states "the flow below applies to **both**", recommending `npx skills add <owner/repo@skill> -g -y`. No `dummyindex/` module references `npx skills` or skills.sh; there is no CLI verb, no manifest record, no `status` row, and `-g` writes outside the repo entirely. **Gap: half the documented product surface has no entry point and no lifecycle — a skill installed that way is invisible to `status`, untouched by `uninstall`, and unrecoverable after a machine change.**

- **`hooks install` and the statusLine.** Wired write-if-absent across both scopes with no prompt and no mention in the verb's argument surface (`context/hooks.py:346-376`, `:553-562`) — it replaces whatever the user's Claude UI was showing. **Gap: an un-sentinelled scalar write to a shared settings file, so `hooks uninstall` cannot distinguish it from a user value and leaves it; the only removal is a hand edit.**
