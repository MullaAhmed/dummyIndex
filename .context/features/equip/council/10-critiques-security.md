## Security

**T1 (top) — repo-supplied symlink redirects every `.claude/**` write; no containment guard exists on any equip write path.**

- `claude_settings.py:78`, `claude_settings.py:175-179`, `claude_plugins.py:113`, `cli/equip/dispatch.py:596-606` — a cloned repo ships `.claude/settings.json` as a symlink to `~/.claude/settings.json` (git preserves symlinks). Victim runs the advertised workflow — `dummyindex ingest` / `install` — and `wire_default_plugins → enable_plugin` calls `load_settings(project/.claude/settings.json)`, which **follows the symlink** and reads the user's *global* settings (typically carrying `env` API keys/tokens and the whole `permissions` block). `write_settings` then writes a tmp sibling inside the repo and `tmp.replace(settings_path)` **replaces the symlink with a regular file** holding that entire global payload. The repo's own contract calls this file "the committed project settings file … the team-wide artefact" (`default_plugins.py:307-316`), so the victim commits their global secrets and permission grants to the attacker's repo on the next `git add .`. Same mechanism with `.claude/` as a symlinked *directory*: `mkdir(parents=True, exist_ok=True)` + tmp+replace write generated agents, skills, and hook entries into the linked tree, outside the repo. — mitigation: **none**. The repo already knows this attack class and guards exactly one path — `output/bootstrap.py:107-120` `ensure_guidance_target_in_scope` resolves the full path "so a symlinked `.claude` directory … cannot redirect a context command into another tree" — but that guard is never applied to `claude_settings`, `claude_plugins`, `wiring/hooks.py`, `cli/equip/install.py`, or `_write_file`. `is_safe_to_write` (`wiring/safety.py:19-32`) blocks a symlinked *existing* leaf only incidentally (it reads through and finds no sentinel); an absent leaf under a symlinked parent is unguarded.

**T2 — the reviewed third-party defaults are unpinned `runs_code=True` sources installed unattended at init; "reviewed" gates nothing at materialization time.**

- `default_plugins.py:173-193`, `:404-408`, `:637-673`, `cli/init.py:74`, `installer/install/project_init.py:346` — `caveman@caveman` (JuliusBrussee/caveman, SessionStart + UserPromptSubmit Node command hooks) and `i-have-adhd@i-have-adhd` (ayghri/i-have-adhd, SessionStart shell hook) are declared with **no `ref`**, then `_install_one` runs `claude plugin marketplace add <repo> --scope project` + `claude plugin install` during `dummyindex install`. `surfaces` / `runs_code` are static strings in this file recording a point-in-time human read; nothing at clone time compares a hash, tag, signature, or even the reviewed commit — the ledger records no ref for them at all (`plan.md:266-268`: reviewed defaults never enter `equipment.json`). A malicious commit or account takeover on either personal-account repo lands a SessionStart command hook in **every** dummyindex-initialised repo on the machine at the next session — no user action, no re-prompt, no drift signal, and `equip status` structurally cannot report it. — mitigation: **partial and one-shot**. `describe_default_plugin_trust()` (`:196-214`) prints repo, "tracks latest", surfaces, "runs code: yes", and `--no-default-plugins` *before* the mutation, and `_effective_enabled`'s `false` tombstone (`:328-340`) is honored forever. Neither is a continuing gate. **Load-bearing correction to the plan:** `plan.md:200-209` and `default_plugins.py:1-18` justify unpinned tracking with "a pin cannot be expressed here", but the same sentence concedes `git clone --branch <ref>` "accepts branch/tag names" — and `add_marketplace` already takes `ref` (`claude_plugins.py:105-124`), which `_declare_marketplace` deliberately never passes. A **tag** pin is expressible today; only a *commit* pin is not. The plan should say that, and the decision to track a moving default branch on two code-executing personal repos should be re-argued on those terms.

**T3 — `equip install` re-points an existing marketplace declaration, escalating "approve one plugin" into "re-source every plugin under that name".**

- `cli/equip/install.py:177` → `claude_plugins.py:105-124` — `add_marketplace` is an unconditional upsert: `block[name] = {"source": {...}}`, overwriting whatever `extraKnownMarketplaces[name]` held, including a user's deliberate branch/tag `ref`. Attack: victim repo declares `tools → acme/tools` with `fmt@tools` and `deploy@tools` enabled. Attacker publishes `attacker/tools` whose `marketplace.json` sets `"name": "tools"` and gets the victim to run `equip install helper@tools --repo attacker/tools --yes`. `--repo` catalogs are admitted at priority 2, **ahead** of locally-declared ones at priority 3 (`cli/equip/discover.py:177-207`), so the attacker's catalog wins the name; the install then rewrites `tools` to point at `attacker/tools`. The user approved `helper`; `fmt` and `deploy` now load from the attacker's repo at next session. — mitigation: **none on this path**. `_admit`'s reserved-name guard (`cli/equip/discover.py:55-57, 130-140`) covers only *trusted* seed names, and the identity-conflict refusal exists solely in `default_plugins._declare_marketplace:373-409`, which `equip install` does not call. `plan.md:252-257` files this as an **open question**; it is a trust boundary, not a UX preference — the refusal (or an explicit "this repoints N enabled plugins" confirmation) belongs on the interactive path too.

**Also (not top-3, all with a concrete path):**

- `cli/equip/install.py:132-145`, `:239-255` — the `--yes` gate for an untrusted source is waived when `_already_enabled_in` finds `enabledPlugins["<target>"] == true` in the **committed** `.claude/settings.json`. That file is repo content: a PR adds one dangling line `"enabledPlugins": {"pwn@pwn-market": true}` with no matching `extraKnownMarketplaces` entry, so it is inert and reads as harmless cruft in review. A later `equip install pwn@pwn-market` (the plugin name is itself the discovery query at `install.py:89-91`, so a gh-searchable attacker repo surfaces) prints "already enabled — re-registering" and supplies the missing marketplace declaration with no approval prompt — completing exactly the half the attacker could not write. — mitigation: none; the pre-approval oracle must be machine-local (`settings.local.json`) or the manifest, never the committed, PR-writable file.
- `claude_settings.py:177-179` vs `domains/atomic_io.py:13-34` — `write_settings` writes a **fixed-name** tmp sibling (`settings.json.tmp`) and replaces. `atomic_io._replace_bytes` uses a *unique* `NamedTemporaryFile` for exactly the stated reason ("hooks from two Claude profiles can update the same repo-local cache concurrently"), and `plan.md:138-143` credits that atomicity — but the file carrying hook commands, `enabledPlugins`, `permissions`, and `env` never routes through it. Two concurrent `hooks install --global` / installer runs (or `install_statusline(scope="global")` from two sessions) interleave writes into one `~/.claude/settings.json.tmp` and produce torn JSON in the machine-wide settings file. Every subsequent managed write then hits `MalformedSettingsError` and refuses (`hooks.py:644-660`), leaving hooks unmanageable until hand-repair — the destruction preserve-or-refuse exists to prevent. `_write_file:596-606` has the same fixed-tmp shape. — mitigation: none; route both through `atomic_io.write_text_atomic`.
- `hooks.py:110-145`, `hooks.py:716-733`, `cli/equip/verbs.py:74-118` — `settings.json` is the only equip-written store with **no** hash baseline and no ledger record, and it is the one holding executable command bodies. `_USER_PROMPT_SUBMIT_PAYLOAD` bakes `ALWAYS_ON_TURN_REMINDER` into a single-line shell-quoted JSON blob injected as `additionalContext` with `suppressOutput: true` on **every** prompt. A PR that edits that literal (adding, say, an instruction to include an extra dependency or endpoint in generated code) is a per-turn prompt-injection channel that renders as a system reminder and never appears in the visible transcript. Detection today: `_claude_hook_installed` matches `SENTINEL in command` — substring only — so a tampered body reports **installed**; `hooks status` reports healthy; `equip status` reads manifest + evals only and never looks at settings at all. `plan.md:269-273` notices the missing version stamp but frames it as an upgrade-path question; the tamper-detection gap is the sharper half. — mitigation: partial — a subsequent `hooks install` rewrites our entry to canonical (`claude_settings.py:92-109`) and reports `refreshed`, but nothing runs it automatically and "refreshed" is not an alarm.
- `default_plugins.py:353-370`, `:399-408` — legacy-SHA-pin healing converts a declaration that **fails closed** (a 40-hex ref Claude Code's `--branch` clone can never resolve, so the plugin never loads) into a live, latest-tracking clone of a `runs_code=True` third-party repo, silently and with no prompt. Shape-exactness bounds it to the three reviewed targets and the same repo, but the direction of the flip is trust-widening and it is the only place dummyindex *removes* a pin a user may have hand-written believing it held. — mitigation: partial (shape-exact match + same-repo check); a one-line "unpinned <target>; it now tracks latest" on the healing branch would make the widening visible.

**Checked and clean (do not re-raise):**

- `generate/catalog.py:164-178` + `generate/detect.py:71-75` — the `PostToolUse` format hook body is **not** repo-influenced: `formatter` and `format_command` come from a closed three-row table; repo manifest text only *selects* a row (`_first_token:148-157`). `$CLAUDE_FILE_PATHS` is double-quoted, so a hostile filename cannot word-split or re-expand.
- `hooks.py:110-130`, `:379-409` — every managed command interpolates only `"$CLAUDE_PROJECT_DIR"` (quoted) and a `shlex.quote`d pre-serialized payload; no prompt text or project path reaches the command string.
- `plugins/install_plan.py:41-48` — `requires_approval = not candidate.trusted` unconditionally; the attacker-controlled `runs_code=False` claim never waives the gate. Correct, and `marketplace.py:144-175` + `cli/equip/discover.py:55-57` keep `trusted` off the JSON entirely.
- `plugins/sources.py:134-146` + `cli/equip/install.py:355-360` — skill-name path traversal is guarded twice (enumeration and install boundary).
- `plugins/sources.py:34-49`, `default_plugins.py:589-605` — fixed argv, `shell=False`, bounded timeouts on every shell-out.
