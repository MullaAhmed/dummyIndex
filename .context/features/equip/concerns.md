## Data integrity

- `dummyindex/context/claude_settings.py:175-179` — `write_settings` writes through a **fixed-name** tmp sibling (`settings.json.tmp`) with no uniqueness, no `try/except`, and no `unlink`, so the exact scenario `atomic_io._replace_bytes:13-18` was made unique-named for ("hooks from two Claude profiles can update the same repo-local cache concurrently") interleaves two writers into one tmp and `replace`s truncated JSON over the user's `settings.json` — the single file every preserve-or-refuse guard in the plan exists to protect — fix: route it through `atomic_io.write_text_atomic`.
- `dummyindex/context/domains/equip/lifecycle/manifest.py:59-70` — `write_manifest` is a second fixed-tmp writer (`equipment.json.tmp`), so a concurrent `apply`/`refresh`/`patch` corrupts the ledger and `read_manifest:39-51` then hard-raises `EquipError` on *every* later equip verb plus `domains/audit/catalog.py`; the plan's Data-model claim that per-file atomicity holds "precisely because [two profiles] can write concurrently" (`plan.md:140-143`) is true of only one of the five writers — fix: same unique-tmp primitive.
- `dummyindex/cli/equip/dispatch.py:596-606` — `_write_file` is a third fixed-tmp writer (`<agent>.md.tmp`) that bypasses `write_text_atomic` entirely, and since `origin_hash` is computed from the **in-memory** string (`:458-459`) and never re-read from disk, a torn write records a baseline for bytes that were never persisted and pins the item to `USER_MODIFIED` forever — fix: call `write_text_atomic`.
- `dummyindex/context/domains/config.py:662-681` — `write_config` is the fourth fixed-tmp writer and has no `try/except`; combined with the read-modify-write at `cli/equip/install.py:479-482` and `config.py:610-618`, a concurrent `equip install` and init-time `ensure_wired_defaults` lose each other's `config.wired` entries (the docstring at `install.py:458` concedes "Single-writer per repo (no locking)" without enforcing it) — fix: unique tmp, and re-read + merge `wired` immediately before the write.
- `dummyindex/context/domains/equip/lifecycle/status.py:243-303` — `refresh` writes each refreshed file inside the loop (`:291`) but persists the manifest only once after it (`:300-303`), so an `OSError` out of `write_text_atomic` on file N leaves files 1..N-1 rewritten against stale baselines, which `classify_item:165-171` then reads as `USER_MODIFIED` and `refresh` skips **forever** — fix: persist the accumulated `new_items` in a `finally`, or re-baseline per item.
- `dummyindex/context/domains/equip/lifecycle/status.py:377-403` — `uninstall` appends a marketplace item to `removed` (`:381`) *before* attempting `disable_plugin`, swallows `MalformedSettingsError` (`:388-389`), then unlinks the manifest anyway (`:403`), so a still-enabled `enabledPlugins` key is orphaned with its only ledger record deleted and simultaneously reported as removed — fix: skip the manifest unlink (and drop the name from `removed`) when any un-wire failed.
- `dummyindex/cli/equip/dispatch.py:499-540` — only `MalformedSettingsError` is caught around `wire_hooks`, but `claude_settings.write_settings:177-179` raises a bare `OSError` (read-only `.claude/`, ENOSPC), which escapes as a traceback *after* the generated files are written and *before* the manifest write — producing exactly the unrecorded-files partial state the "files first, then hooks, then manifest" ordering was designed to prevent — fix: catch `OSError` alongside `MalformedSettingsError`.
- `dummyindex/cli/equip/dispatch.py:453-459` — on a re-render the freshly built `item` wins the merge and only `version`/`origin_hash` are carried forward from `prior_item`, so a prior record's v3 provenance (`marketplace`, `origin_repo`, `origin_ref`, `mechanism`) and its `grounded_in` usage playbook are silently dropped from the ledger — fix: `dataclasses.replace(prior_item, …)` with the new render's fields rather than replacing onto `item`.
- `dummyindex/context/domains/equip/models.py:114-133` + `dummyindex/cli/equip/dispatch.py:535` — `from_dict` ignores unknown keys and `to_dict` emits a fixed key set while `apply` unconditionally stamps `schema_version=SCHEMA_VERSION`, so a manifest written by a newer dummyindex that added a *field* (the way `invariants` was added at `:99-102`) loads cleanly, is stripped of that field, and is stamped back down to v4 — silent forward-incompatible data loss, in contrast to the enum path which `manifest.py:45-51` does guard — fix: raise `EquipError` (or round-trip the unknown keys) when `schema_version > SCHEMA_VERSION`.
- `dummyindex/cli/equip/dispatch.py:480,515-522` — the dedupe/carry-forward key is `name` alone, ignoring `kind` and `path`, so a prior record whose name collides with a differently-pathed item this run is dropped and its on-disk file becomes an orphan that no lifecycle verb (`status`/`refresh`/`uninstall`) can ever see or clean up — fix: key the carry-forward on `(kind, name)` and warn when a surviving record's `path` changed.
- `dummyindex/context/default_plugins.py:388-409` + `dummyindex/context/claude_plugins.py:113-124` — `_declare_marketplace` runs its identity-conflict check against one `load_settings` (`:388`) and then hands the write to `add_marketplace`, which re-reads and upserts (`:114-123`), so a settings write landing between the two reads bypasses the guard and clobbers a foreign marketplace declaration — the plan's "mechanism in the base layer, policy in its caller" split (`plan.md:216-219`) is a TOCTOU as implemented — fix: perform the guard and the write inside one read-modify-write, or pass the already-loaded dict through.
- `dummyindex/context/domains/equip/lifecycle/remove.py:15-17,60-79` — the module docstring promises "we never half-remove: record kept on refusal", but the file `unlink` (`:70`) and the marketplace un-wire (`:76`) both precede `write_manifest` (`:79`), so an `EquipError` on the manifest write leaves the file deleted and the plugin disabled with the record still claiming both exist — fix: correct the docstring, or persist the manifest first and only then perform the destructive steps.
- `dummyindex/context/domains/atomic_io.py:13-34` — no `fsync` on the tmp handle (nor on the parent directory) before `replace`, so a crash or power loss can surface a zero-length or stale generated file whose content no longer matches its recorded baseline, converting every affected item to permanently-skipped `USER_MODIFIED` — fix: `handle.flush(); os.fsync(handle.fileno())` inside the `with`.
- `dummyindex/context/domains/atomic_io.py:40-45` — the byte-faithful contract's own rationale cites `equip/lifecycle/hashing.text_hash`, which does not exist anywhere in the tree (the function is `content_hash`, `lifecycle/hashing.py:17-19`), so the single docstring explaining *why* this writer must never normalize points at nothing — confirmed, and code wins — fix: rename the reference to `content_hash`.

## Security

**T1 (top) — repo-supplied symlink redirects every `.claude/**` write; no containment guard exists on any equip write path.**

- `claude_settings.py:78`, `claude_settings.py:175-179`, `claude_plugins.py:113`, `cli/equip/dispatch.py:596-606` — a cloned repo ships `.claude/settings.json` as a symlink to `~/.claude/settings.json` (git preserves symlinks). Victim runs the advertised workflow — `dummyindex ingest` / `install` — and `wire_default_plugins → enable_plugin` calls `load_settings(project/.claude/settings.json)`, which **follows the symlink** and reads the user's *global* settings (typically carrying `env` API keys/tokens and the whole `permissions` block). `write_settings` then writes a tmp sibling inside the repo and `tmp.replace(settings_path)` **replaces the symlink with a regular file** holding that entire global payload. The repo's own contract calls this file "the committed project settings file … the team-wide artefact" (`default_plugins.py:307-316`), so the victim commits their global secrets and permission grants to the attacker's repo on the next `git add .`. Same mechanism with `.claude/` as a symlinked *directory*: `mkdir(parents=True, exist_ok=True)` + tmp+replace write generated agents, skills, and hook entries into the linked tree, outside the repo. — mitigation: **none**. The repo already knows this attack class and guards exactly one path — `output/bootstrap.py:107-120` `ensure_guidance_target_in_scope` resolves the full path "so a symlinked `.claude` directory … cannot redirect a context command into another tree" — but that guard is never applied to `claude_settings`, `claude_plugins`, `wiring/hooks.py`, `cli/equip/install.py`, or `_write_file`. `is_safe_to_write` (`wiring/safety.py:19-32`) blocks a symlinked *existing* leaf only incidentally (it reads through and finds no sentinel); an absent leaf under a symlinked parent is unguarded.

**T2 — the reviewed third-party defaults are unpinned `runs_code=True` sources installed unattended at init; "reviewed" gates nothing at materialization time.**

- `default_plugins.py:173-193`, `:404-408`, `:637-673`, `cli/init.py:74`, `installer/install/project_init.py:346` — `caveman@caveman` (JuliusBrussee/caveman, SessionStart + UserPromptSubmit Node command hooks) and `i-have-adhd@i-have-adhd` (ayghri/i-have-adhd, SessionStart shell hook) are declared with **no `ref`**, then `_install_one` runs `claude plugin marketplace add <repo> --scope project` + `claude plugin install` during `dummyindex install`. `surfaces` / `runs_code` are static strings in this file recording a point-in-time human read; nothing at clone time compares a hash, tag, signature, or even the reviewed commit — the ledger records no ref for them at all (`plan.md:266-268`: reviewed defaults never enter `equipment.json`). A malicious commit or account takeover on either personal-account repo lands a SessionStart command hook in **every** dummyindex-initialised repo on the machine at the next session — no user action, no re-prompt, no drift signal, and `equip status` structurally cannot report it. — mitigation: **partial and one-shot**. `describe_default_plugin_trust()` (`:196-214`) prints repo, "tracks latest", surfaces, "runs code: yes", and `--no-default-plugins` *before* the mutation, and `_effective_enabled`'s `false` tombstone (`:328-340`) is honored forever. Neither is a continuing gate. **Load-bearing correction to the plan:** `plan.md:200-209` and `default_plugins.py:1-18` justify unpinned tracking with "a pin cannot be expressed here", but the same sentence concedes `git clone --branch <ref>` "accepts branch/tag names" — and `add_marketplace` already takes `ref` (`claude_plugins.py:105-124`), which `_declare_marketplace` deliberately never passes. A **tag** pin is expressible today; only a *commit* pin is not. The plan should say that, and the decision to track a moving default branch on two code-executing personal repos should be re-argued on those terms.

**T3 — `equip install` re-points an existing marketplace declaration, escalating "approve one plugin" into "re-source every plugin under that name".**

- `cli/equip/install.py:177` → `claude_plugins.py:105-124` — `add_marketplace` is an unconditional upsert: `block[name] = {"source": {...}}`, overwriting whatever `extraKnownMarketplaces[name]` held, including a user's deliberate branch/tag `ref`. Attack: victim repo declares `tools → acme/tools` with `fmt@tools` and `deploy@tools` enabled. Attacker publishes `attacker/tools` whose `marketplace.json` sets `"name": "tools"` and gets the victim to run `equip install helper@tools --repo attacker/tools --yes`. `--repo` catalogs are admitted at priority 2, **ahead** of locally-declared ones at priority 3 (`cli/equip/discover.py:177-207`), so the attacker's catalog wins the name; the install then rewrites `tools` to point at `attacker/tools`. The user approved `helper`; `fmt` and `deploy` now load from the attacker's repo at next session. — mitigation: **none on this path**. `_admit`'s reserved-name guard (`cli/equip/discover.py:55-57, 130-140`) covers only *trusted* seed names, and the identity-conflict refusal exists solely in `default_plugins._declare_marketplace:373-409`, which `equip install` does not call. `plan.md:252-257` files this as an **open question**; it is a trust boundary, not a UX preference — the refusal (or an explicit "this repoints N enabled plugins" confirmation) belongs on the interactive path too.

**Also (not top-3, all with a concrete path):**

- `cli/equip/install.py:132-145`, `:239-255` — the `--yes` gate for an untrusted source is waived when `_already_enabled_in` finds `enabledPlugins["<target>"] == true` in the **committed** `.claude/settings.json`. That file is repo content: a PR adds one dangling line `"enabledPlugins": {"pwn@pwn-market": true}` with no matching `extraKnownMarketplaces` entry, so it is inert and reads as harmless cruft in review. A later `equip install pwn@pwn-market` (the plugin name is itself the discovery query at `install.py:89-91`, so a gh-searchable attacker repo surfaces) prints "already enabled — re-registering" and supplies the missing marketplace declaration with no approval prompt — completing exactly the half the attacker could not write. — mitigation: none; the pre-approval oracle must be machine-local (`settings.local.json`) or the manifest, never the committed, PR-writable file.
- `claude_settings.py:177-179` vs `domains/atomic_io.py:13-34` — `write_settings` writes a **fixed-name** tmp sibling (`settings.json.tmp`) and replaces. `atomic_io._replace_bytes` uses a *unique* `NamedTemporaryFile` for exactly the stated reason ("hooks from two Claude profiles can update the same repo-local cache concurrently"), and `plan.md:138-143` credits that atomicity — but the file carrying hook commands, `enabledPlugins`, `permissions`, and `env` never routes through it. Two concurrent `hooks install --global` / installer runs (or `install_statusline(scope="global")` from two sessions) interleave writes into one `~/.claude/settings.json.tmp` and produce torn JSON in the machine-wide settings file. - `hooks.py:110-145`, `hooks.py:716-733`, `cli/equip/verbs.py:74-118` — `settings.json` is the only equip-written store with **no** hash baseline and no ledger record, and it is the one holding executable command bodies. `_USER_PROMPT_SUBMIT_PAYLOAD` bakes `ALWAYS_ON_TURN_REMINDER` into a single-line shell-quoted JSON blob injected as `additionalContext` with `suppressOutput: true` on **every** prompt. A PR that edits that literal (adding, say, an instruction to include an extra dependency or endpoint in generated code) is a per-turn prompt-injection channel that renders as a system reminder and never appears in the visible transcript. Detection today: `_claude_hook_installed` matches `SENTINEL in command` — substring only — so a tampered body reports **installed**; `hooks status` reports healthy; `equip status` reads manifest + evals only and never looks at settings at all. `plan.md:269-273` notices the missing version stamp but frames it as an upgrade-path question; the tamper-detection gap is the sharper half. — mitigation: partial — a subsequent `hooks install` rewrites our entry to canonical (`claude_settings.py:92-109`) and reports `refreshed`, but nothing runs it automatically and "refreshed" is not an alarm.
- `default_plugins.py:353-370`, `:399-408` — legacy-SHA-pin healing converts a declaration that **fails closed** (a 40-hex ref Claude Code's `--branch` clone can never resolve, so the plugin never loads) into a live, latest-tracking clone of a `runs_code=True` third-party repo, silently and with no prompt. Shape-exactness bounds it to the three reviewed targets and the same repo, but the direction of the flip is trust-widening and it is the only place dummyindex *removes* a pin a user may have hand-written believing it held. — mitigation: partial (shape-exact match + same-repo check); a one-line "unpinned <target>; it now tracks latest" on the healing branch would make the widening visible.

## Product surface
