## Product surface

### Install/uninstall asymmetry

- User runs `dummyindex uninstall` after a flagless install — `dummyindex/installer/uninstall.py:22-131` removes the skill families, sweeps dangling family links, removes the slash-command aliases, and removes Codex guidance — the five managed hook events / ten commands written into `<project>/.claude/settings.json` are left live. `dummyindex/context/hooks.py:617-688` (`hooks.uninstall`) exists but nothing under `dummyindex/installer/` references it (`grep -rn "context hooks" dummyindex/installer/` → no hits), so the drift report, the Stop reconcile-gate, and the PreToolUse `Write` deny keep firing in a repo the user believes is uninstalled.
- User uninstalls the skill *and* removes the CLI — the first UserPromptSubmit command is `_MANAGED_COMMENT + printf … + exit 0` with no `command -v dummyindex` self-gate (`dummyindex/context/hooks.py:120-131`), unlike every other managed command which opens with `_SILENT_GATE`/`_SESSION_START_GATE` — 854 characters of `ALWAYS_ON_TURN_REMINDER` (`dummyindex/context/output/bootstrap.py:78-92`) continue to be injected into every prompt in that repo forever. The plan justifies the missing gate for an alternate Claude profile (`plan.md:224-231`); the same mechanism makes the reminder un-retractable by uninstall.
- User (or a teammate) wants the freshness badge gone — `install_statusline` writes `statusLine` into `<project>/.claude/settings.json` (`dummyindex/context/hooks.py:346-376`) and reports it as the token `claude/statusLine` inside the `hooks -> installed:` line; `hooks.uninstall` (`dummyindex/context/hooks.py:617-688`) scrubs only sentinel-bearing entries under the five hook event keys — no command at any level removes `statusLine`. `plan.md:248-253` records "we can never migrate the badge command"; the surface is worse than that — we can never retract it either.
- User installs at user scope then wants the global registration gone — `_register_claude_user_skill` (`dummyindex/installer/install/orchestrate.py:534-547`) appends `_SKILL_REGISTRATION` to `~/.claude/CLAUDE.md`, and `uninstall.py` has no counterpart (`_remove_codex_guidance:221-270` handles only the Codex side) — after a full uninstall the user's global CLAUDE.md still tells every session to invoke a skill that no longer exists.
- User reads `dummyindex uninstall --help` to find out what stays — `_UNINSTALL_USAGE` (`dummyindex/installer/args.py:51-67`) discloses exactly one leftover ("leaves project guidance and hooks intact") — it names neither `statusLine`, the three `enabledPlugins` entries, the marketplace declarations, the `~/.claude/plugins/` clones, the `~/.claude/CLAUDE.md` block, nor `.context/`, and it offers no remediation command for any of them.
- User runs `dummyindex uninstall --platform agents` on a linked layout — `dummyindex/installer/uninstall.py:79-99` detects that the sweep removed the only real tree, warns on stderr, and prints the exact `dummyindex install … --platform claude` restore command — this is the one leftover handled well; no settings-level leftover above gets equivalent treatment.

### Default plugins

- User decides after installing that they do not want the three reviewed defaults — `wire_default_plugins(..., enabled=False)` returns every target in `skipped` and writes nothing (`dummyindex/context/default_plugins.py:504-506`); `reconcile_default_plugins` respects `default_plugins_enabled is False` (`dummyindex/context/domains/config.py:642`) — the three `enabledPlugins: true` values a prior install already wrote stay enabled forever, and there is no CLI verb that sets `default_plugins_enabled` (`grep -rn default_plugins_enabled dummyindex/` finds only readers plus `default_config`/`reconcile_default_plugins`) so the durable opt-out is hand-editing `.context/config.json`.
- User runs `dummyindex install --no-default-plugins` — `_wire_default_plugins_step` early-returns before any print (`dummyindex/installer/install/project_init.py:300-303`) — the run says nothing at all about plugins, so the opt-out produces no confirmation and the two trust-disclosure lines that would have named `caveman@caveman` and `i-have-adhd@i-have-adhd` are suppressed along with the action.
- User types `--no-superpowers` expecting to skip superpowers — it sets `no_default_plugins` at parse (`dummyindex/installer/args.py:141-143`) and suppresses all three defaults; help calls it "compatibility alias for --no-default-plugins" (`args.py:43`) — the flag name understates its blast radius, and per the previous bullet the run prints nothing that would reveal the other two were also skipped.

### Flag surface

- User passes `--defaults` and `--no-onboarding` — they occupy distinct tuple slots (`dummyindex/installer/args.py:206-217`) and are ORed at the call site: `if init_ran and (defaults or no_onboarding)` (`dummyindex/installer/install/orchestrate.py:489`) — two documented flags with zero observable difference, no diagnostic when both are passed, and the "ability to diverge" the plan cites (`plan.md:274-278`) is unfalsifiable from the CLI.
- User combines `--skill-only` with `--defaults` and/or `--no-default-plugins` — `_auto_init_project` runs only under `not skill_only and target_is_repo` (`orchestrate.py:473-480`) and `_write_default_config` only under `if init_ran and (…)` (`orchestrate.py:489-490`) — all three flags parse cleanly, one takes effect, and nothing warns that the other two are inert.
- The four adjacent bools, by CLI flag: slot 2 `skill_only` ← `--skill-only`, slot 3 `no_onboarding` ← `--no-onboarding`, slot 4 `defaults` ← `--defaults`, slot 5 `no_default_plugins` ← `--no-default-plugins`/`--no-superpowers` (`dummyindex/installer/args.py:206-217` → `dummyindex/__main__.py:293-316`) — a reorder on either side is type-clean; the user-visible failure would be `--skill-only` silently skipping plugins while `--no-default-plugins` silently skips auto-init, and nothing in the printed output identifies which slot moved.
- User runs `dummyindex install --scope user --dedupe project` — parses cleanly (`dummyindex/installer/args.py:155-189`) and deletes a skill family at a scope different from the one being installed (`orchestrate.py:444-456` → `dummyindex/installer/repair.py:493-604`) — one invocation both installs and deletes across two scopes with no confirmation prompt and no dry-run; `--dedupe`'s argument being independent of `--scope` is not called out in `_INSTALL_USAGE` (`args.py:44-45`).
- User runs `--copy --platform agents` vs `--link --platform agents` — `--link` with codex exits 2 with a precise message (`args.py:196-202`); `--copy` has no such check and the whole link dispatch is gated on `"claude" in concrete_platforms` (`orchestrate.py:371`) — the same "no Claude side to act on" condition produces a hard error one way and a silent no-op the other.
- Caller uses the public API rather than the CLI — `install()` takes the internal vocabulary and passes `platform` straight to `platforms_for()`, so `install(platform="agents")` exits 1, while `uninstall()` normalizes first and accepts it (`spec.md:227-233`, `orchestrate.py:131-135` vs `dummyindex/installer/uninstall.py:43-47`) — the two halves of the same public pair disagree about a vocabulary the CLI presents as canonical.

### Hook noise

- User opens a session in an indexed repo — SessionStart runs `plan-update`, `memory session-start`, `gc signal`, and silent `memory mine` (`dummyindex/context/hooks.py:147-198`); measured in this repo, `dummyindex context plan-update --root .` emits 6,702 characters / 40 lines including a full per-feature file listing, all of it appended to the session's `additionalContext` — `render_drift_summary` (`dummyindex/context/drift.py:194`) has no cap, `dummyindex/cli/plan_update.py` has no `--brief`, and no config field bounds it.
- User wants the session-start report quieter without losing the rest — the only lever is `dummyindex context hooks uninstall` (`dummyindex/cli/hooks.py:83-92`), which removes all five events at once — there is no per-event or per-command opt-out, no verbosity knob, and `install --skill-only` (the only install-time way to avoid hooks) also skips building `.context/` entirely.
- Teammate clones the repo without ever installing dummyindex — every hook command self-gates and exits 0 silently, so the Stop gate and PreToolUse deny stay inert, but the ungated UserPromptSubmit `printf` fires (`dummyindex/context/hooks.py:120-131`) — a developer who never opted in gets the caveman/ADHD output contract injected into every prompt from a git-tracked settings file.

### statusLine takeover

- User has no `statusLine` anywhere and runs `dummyindex install` in a repo — the badge is written into `<project>/.claude/settings.json`, which `plan.md:209-211` itself classifies as the git-tracked "shared team declaration", and the value `dummyindex context statusline` carries no `command -v` gate (`dummyindex/context/hooks.py:311-315`) unlike every hook command — a teammate without the CLI on PATH gets a broken status line rather than a silent no-op, and every repo the user inits accumulates its own committed `statusLine`.
- User already has their own global status line — `install_statusline` returns `None` when *either* scope defines a truthy value and `install` reports nothing for `None` (`dummyindex/context/hooks.py:329-340`, `557-563`) — the badge is never wired in any repo and the user is never told it exists or why it was skipped; the only advisory (`_STATUSLINE_UNWRITABLE_NUDGE`, `hooks.py:321-327`) covers the unparseable-file case only.
- User's `.claude/settings.json` is unparseable, so the badge cannot be wired — `HookResult.nudges` carries the hand-edit advisory and `dummyindex/cli/hooks.py:70-77` prints it, but `_install_project_hooks` (`dummyindex/installer/install/project_init.py:203-223`) prints `installed`/`skipped`/`errors` and never iterates `nudges` — the one advisory the badge machinery can produce is invisible to anyone arriving through `dummyindex install`, the primary entry point.

### Discoverability

- User runs `dummyindex status` to find out what install did — the read-only overview (`dummyindex/__main__.py:337-342` → `dummyindex/cli/status.py:21`) reports index, version stamp vs CLI, config, anchor, drift, equipment, depth, wired, proposals, and session-memory — it reports nothing about hook state, `statusLine`, install scope, or link-vs-copy layout, i.e. exactly the four surfaces `install` writes and `uninstall` leaves behind. `dummyindex context hooks status` covers the five hook booleans only, and no command reports the statusLine at all.
- User re-runs `dummyindex install` on a repo whose `.claude/skills/dummyindex*` are real directories — the flagless default is AUTO, so `create_family_links` converts each proven real copy to a relative link and eight `claude skill migrated ->` lines are printed (`dummyindex/installer/install/link_dispatch.py:217-242`) — the layout of an existing install silently changes shape on an upgrade; the printed lines are the only signal, and no command afterwards reports which mode the install is in.
