## Data integrity

- `dummyindex/context/hooks.py:654-671` — `uninstall` filters at the ENTRY level (drops any entry holding a sentinel hook), destroying exactly the co-located user hook that `install_hook_entry` deliberately merged INTO our managed entry — verified live: after `install` → hand-add `{"command":"echo MY-OWN-HOOK"}` into `hooks.Stop[0].hooks` → `install` (survives) → `uninstall` (gone) — replace the local reimplementation with `claude_settings.remove_hook_entries(settings_path, sentinel=SENTINEL)`, which already does per-HOOK filtering and is what equip uses (`context/domains/equip/lifecycle/status.py:401`).
- `dummyindex/context/hooks.py:592-596` — `_scrub_legacy_claude_hooks` has the same entry-level filter, so a user hook co-located inside our legacy `PostToolUse` entry is deleted by the scrub that runs on every `install` — same fix, `remove_hook_entries` with the legacy event restricted.
- `dummyindex/context/claude_settings.py:81-82` — `settings.setdefault("hooks", {})` assumes the `hooks` value is a dict; a settings.json of `{"hooks": null, "permissions": {...}}` is a valid JSON object so `load_settings` admits it, and the call then raises `AttributeError: 'NoneType' object has no attribute 'setdefault'` — verified by direct invocation — which `hooks.install:550`'s `except (OSError, MalformedSettingsError)` does not catch, so `dummyindex context hooks install` tracebacks instead of refusing — isinstance-check the block and raise `MalformedSettingsError`, mirroring `remove_hook_entries:131-133` and `_scrub_legacy_claude_hooks:588-590`.
- `dummyindex/installer/install/family_write.py:66-69` vs `:140-143` — the companion `*.md` wipe runs before the fresh copy while the pre-existing stamp is left in place, so an install interrupted mid-wipe during a **same-version** rerun leaves `agents/`/`council/`/`retrieval/` empty and `repair._decide_rewrite` (`installer/repair.py:683-690`) then reports "stamp already matches; no rewrite needed" permanently — stamp-last is only evidence across a version transition, not within one; unlink `.dummyindex_version` before the wipe (or stage the family in a temp dir and rename) so "unproven" is the on-disk state for the whole rewrite window.
- `dummyindex/installer/install/link_dispatch.py:96-123` — `_backfill_sibling_stamps` mints ownership evidence onto any real directory sitting at a `_SIBLING_SKILLS` path purely because the MAIN dir is stamped, inspecting none of the sibling's contents, and the next run's `create_family_links` treats exactly that stamp as its licence to rename the directory aside (`installer/link/create.py:368-376`) and delete it (`:296-297`) — a hand-authored `dummyindex-plan/` beside a stamped family is fabricated-into-ours and destroyed; require at least one recognisable family artefact (a `SKILL.md` matching the rendered source, or the legacy heading) before minting.
- `dummyindex/installer/uninstall.py:101-131` — uninstall removes the skill tree, slash commands and Codex guidance but none of the Claude state install wrote: the `~/.claude/CLAUDE.md` registration block (`installer/install/orchestrate.py:534-546`), the managed hook entries and `statusLine` (`context/hooks.py:617-688` exists but is unreachable from this path), and `enabledPlugins`/`extraKnownMarketplaces` (`context/default_plugins.py:472-554`) — every one left declaring a path that no longer exists; at minimum call `context.hooks.uninstall` and strip the `_SKILL_REGISTRATION` block at the same scope, or print the residue explicitly.
- `dummyindex/installer/common.py:84,87-95` + `installer/uninstall.py:194-209` + `installer/common.py:267-283` — removal enumerates the *current build's* `_SIBLING_SKILLS` / `_COMMAND_FILES`, never what was actually installed, so any family or command a later release renames or retires is orphaned on disk with nothing able to find it again — record the installed family/command labels in the stamp (or a sidecar manifest) and drive removal from that.
- `dummyindex/context/claude_settings.py:92-113` — the sentinel scan returns on the first matching entry and resolves its position via `events.index(entry)` (equality, not identity), so a second managed entry under the same event — a git merge of two branches that both added it, or a hand-copied entry — is never refreshed and never deduped, and every managed command under that event fires twice on every session, forever; collect all sentinel-bearing entries, merge into the first, drop the rest.
- `dummyindex/context/hooks.py:532-551` — the five managed events are installed as five independent load→mutate→write cycles (`install_hook_entry` writes per call), so an interrupt or a mid-loop error leaves a partially installed hook set that `status:694-713` can see but nothing repairs, and `HookResult` has no field distinguishing partial from complete; build the merged settings once across all five events and issue one `write_settings`.
- `dummyindex/context/claude_settings.py:175-179` — `write_settings` uses a fixed `settings.json.tmp` name and never copies the target's mode, so the two managed writers that share it under different sentinels (`context/hooks.py` and `context/domains/equip/wiring/hooks.py:20`) can lose each other's entries wholesale through concurrent read-modify-write, and a `0600` settings.json carrying `env` secrets is silently widened to the umask default on the first managed write; `os.stat`+`chmod` the tmp before `replace` and allocate it with `tempfile.mkstemp` in the same directory.
- `dummyindex/context/hooks.py:362-364` — `install_statusline`'s "absent in either scope" pre-check reads the *project* settings even for a `scope="global"` install, so `dummyindex install --scope user` run from inside a repo that defines its own `statusLine` permanently skips wiring the global badge (write-if-absent means it is never retried), making the persisted global state depend on the cwd of one install run; gate a global write on the global file alone.
- `dummyindex/context/default_plugins.py:511-548` — the wiring loop performs a separate `_declare_marketplace` write and `enable_plugin` write per entry, so an interrupt leaves `extraKnownMarketplaces` declaring a marketplace whose plugin was never enabled (and a half-wired target set) with no rollback and no signal separating partial from user-declined; accumulate the mutation across all entries and write once.
- `dummyindex/installer/common.py:197-224` + `installer/link/create.py:466-587` — the `.claude` bytes diverge by mode: COPY renders `platform="claude"` (no preamble) while LINK points `.claude/skills/*` at the `.agents` copy rendered `platform="codex"`, so a linked Claude install reads `_PORTABLE_HOST_PREAMBLE` — including its "prefer the `.claude/skills` copy" row, which now resolves to itself — and a copied one does not; render one host-neutral body for the shared tree, or drop the Claude row when the copy is link-shared.
- `dummyindex/installer/install/orchestrate.py:534-546` — `_register_claude_user_skill` read-modify-writes the user's global `~/.claude/CLAUDE.md` with a bare `write_text` (no tmp+rename, unlike `write_settings`) and keys idempotence on the substring `"**dummyindex** ("`, so an interrupted write truncates the whole global instruction file and any user edit dropping that substring makes the next install append a second registration block; use a managed-region marker plus atomic tmp+rename.
- `dummyindex/installer/args.py:203-217` + `dummyindex/__main__.py:293-316` — the only test crossing the tuple→keyword boundary (`tests/test_install.py:1462-1484`) asserts `link_mode` and `platform` only, so swapping `skill_only` with `no_default_plugins` in the unpack passes the entire suite while changing whether `.context/`, `.claude/settings.json`, and `config.json` are written at all (the four bools are not equivalent — only `no_onboarding`/`defaults` are, ORed at `orchestrate.py:489`); assert all four bools individually in that test, or return the frozen `InstallArgs` the plan's open question proposes.
- `dummyindex/installer/repair.py:651-709` — ownership and currency are proven from the stamp file alone with no content manifest, so corruption inside a current-stamped copy (truncated `SKILL.md`, deleted companion, the wipe case above) is invisible to `plan_repairs` and never repaired; stamp a file count/hash beside the version, or add a `--verify` that diffs the installed set against the packaged source.
- `dummyindex/installer/uninstall.py:128-131` — uninstall accumulates every removed path then prints only `removed[0]`, so a partial removal (a sibling skipped at `:201-207`, a rmdir break at `:115-118`) is indistinguishable in output from a complete one and the user cannot verify what state survived; print each removed path, or a count with the roots touched.
