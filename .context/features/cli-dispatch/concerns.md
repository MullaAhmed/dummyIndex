## Data integrity

- `dummyindex/cli/init.py:90-154` + `dummyindex/context/domains/config.py:458-494` — without an explicit `--depth`, `resolve_depth` fully deserializes `config.json` before the `--no-default-plugins` and Codex-only gates take effect. A malformed plugin-only field can block the deterministic index build. That happens even though the caller explicitly disabled or cannot use Claude plugins. This contradicts the plan's pre-config opt-out boundary. Read only depth fields at this stage, or defer full plugin-config validation until `_wire_default_plugins_step`.
- `dummyindex/cli/init.py:51-84` + `dummyindex/cli/init.py:225-231` — default reconciliation can commit `config.wired` and `default_plugins_enabled` before settings declaration or materialisation fails. `_wire_default_plugins_step` returns no aggregate. `init.run` still exits 0 unconditionally. Automation cannot tell a fully applied state from config-only intent. Return a structured partial-state result. Surface a nonzero exit or a persisted pending marker until settings or machine state is healed.
- `dummyindex/cli/init.py:51-78` + `dummyindex/cli/wire.py:88-123,221-244` + `dummyindex/context/default_plugins.py:448-524,645-699` — headless init passes every custom `config.wired` plugin. Interactive wire passes each approved custom plugin through the reviewed-default declaration seam. That seam writes `enabledPlugins=true` without a marketplace source. Materialisation selects zero targets. The next `wire` run treats the enabled key as satisfied. It never offers the interactive repair path. Route custom targets through source-resolving `equip install`. Or persist source, declaration, and materialisation as separate states. Do not equate an enabled key with completion.
- `dummyindex/cli/wire.py:109-123` + `dummyindex/cli/wire.py:156-173` + `dummyindex/cli/wire.py:221-244` — when declaration writes `enabledPlugins=true` and materialisation then errors, the command reports needs-user. The next run classifies the entry as satisfied from the settings key alone. It never retries the failed install. Roll back enablement on install failure. Or track declaration and materialisation as separate persisted states during classification.
- `dummyindex/cli/wire.py:239-244` + `dummyindex/context/default_plugins.py:677-711` — `_wire_plugin` treats `deferred` and `skipped` install results as success. It checks only `errors`. That collapses "installed", "CLI unavailable", and "not eligible" into one `wired` state. Require `installed` for synchronous success. Render deferred and skipped explicitly, without removing the entry from needs-user tracking.
- `dummyindex/cli/wire.py:96-166` — `wire` snapshots the entire ledger before it may block on multiple prompts. It never re-reads the ledger. A concurrent config edit can remove or change an entry while the stale approved copy stays enabled. After each affirmative prompt, re-read under a per-config lock. Verify the exact entry is still declared before mutating settings.
- `dummyindex/cli/common.py:13-46` + `dummyindex/cli/init.py:109-119` + `dummyindex/cli/wire.py:46-63` + `dummyindex/context/default_plugins.py:448-524` — the selected project root is not enforced as the settings-store boundary. A symlinked `.claude` directory redirects declaration writes. Later effective-state reads follow it into a sibling or user tree. `config.wired` stays under the selected root. Desired and effective state then split across two repositories. Both look locally satisfied. Resolve and validate the settings destination beneath the selected root before every read and write. Reject symlinked parents, or use no-follow directory handles.

## Security

1. **High — repository-controlled symlinks can redirect Claude settings mutation outside the selected root.** `init` and `wire` trust the root returned by `resolve_context_root`. They construct `.claude/settings.json` without binding it back to that root (`dummyindex/cli/common.py:13-46`, `dummyindex/cli/init.py:109-119`, `dummyindex/cli/wire.py:46-63`, `dummyindex/context/default_plugins.py:448-524`). Attack scenario: a malicious clone supplies `.claude` as a directory symlink to a sibling or user tree. Or it supplies `.claude/settings.json.tmp` as a symlink to any user-writable file. Declaration follows the redirected directory. `write_settings` follows the predictable temporary symlink during `write_text`, before its rename (`dummyindex/context/claude_settings.py:175-179`). The selected repo's `config.wired` stays local. Effective-state reads follow the external settings. So both the overwrite and the split-store state look satisfied on later runs. **Mitigation today: none at the dispatch or integration boundary.** Config validation and atomic rename constrain content and commit shape only after the unsafe destination is selected. Resolve and enforce the settings destination beneath the selected root. Reject symlinked parents. Create temporary files with exclusive no-follow directory-handle operations.
2. **High — headless `context init` bypasses and then suppresses the CLI's untrusted-plugin confirmation model.** Repository config accepts any non-empty `WiredEntry.target`. Init passes the entire post-build `cfg.wired` tuple into the headless declaration service (`dummyindex/context/default_plugins.py:62-108`, `dummyindex/cli/init.py:51-78`). Attack scenario: a committed `attacker-plugin@known-marketplace` entry is written as `enabledPlugins=true` during ordinary init. It is written without the warning or prompt reserved for `context wire` (`dummyindex/context/default_plugins.py:430-445,487-524,645-699`). The reviewed-default materialiser filters the custom target out. But the next `wire` run sees the enabled key as `SATISFIED`. It never offers confirmation or repair (`dummyindex/cli/wire.py:88-123,193-218`). **Load-bearing mitigation today:** dummyindex's immediate subprocess pass does not fetch the custom target, because it intersects with `DEFAULT_PLUGINS`. The persistent Claude declaration can still materialise later. The only approval surface has been disabled by classification. Restrict unattended declaration to reviewed targets. Require verified marketplace provenance and materialisation before classifying a custom entry as satisfied. Mere key presence is not enough.
3. **Medium — plugin-capable CLI handlers execute whichever `claude` binary wins inherited `PATH`.** Both init's default pass and wire's approved path reach `install_default_plugins` (`dummyindex/cli/init.py:70-78`, `dummyindex/cli/wire.py:221-244`). Its availability check executes bare `claude --version`. Marketplace and install commands reuse the unresolved name. `default_runner` changes into the selected repository and inherits the caller's environment (`dummyindex/context/default_plugins.py:565-581`, `dummyindex/context/default_plugins.py:602-642`). A malicious repository gains code execution at the availability probe. That requires a launcher, direnv rule, or user PATH that lists the repository first. **Load-bearing mitigation today:** subprocess uses list argv without a shell. It has a timeout. It allowlists immediate plugin targets. It pins non-official marketplace refs to full SHAs. Init discloses reviewed code-running surfaces before the probe (`dummyindex/context/default_plugins.py:149-223`, `dummyindex/cli/init.py:46-49`). None of these authenticates the executable. Resolve an approved absolute Claude CLI path before entering repository context. Execute with a minimal explicit environment and PATH.

## Product surface

- Recovery run with `context init --no-default-plugins` or `--platform codex` against a config whose plugin fields are malformed. `init` removes the opt-out flag. But without an explicit `--depth`, it calls `resolve_depth`. That fully deserializes `config.json` and exits 2 before the build or the later Claude and plugin gates (`dummyindex/cli/init.py:90-154`, `dummyindex/context/domains/config.py:458-494`). The documented one-run opt-out cannot isolate indexing from irrelevant plugin corruption. Read only the depth fields here, or defer full plugin validation until the plugin step.
- Successful `context init --no-default-plugins`. `_wire_default_plugins_step` returns before printing anything. Codex-only init bypasses the same step entirely (`dummyindex/cli/init.py:17-27,222-231`). The caller cannot tell an honored explicit opt-out from a plugin phase that was unreachable or omitted. Emit one stable `plugins -> skipped for this run` line.
- `context init` or approved `context wire` in a cloned repository whose `.claude` directory or `settings.json.tmp` is a symlink. Declaration follows the external destination. Config stays under the selected root. The command reports plugin outcomes without revealing which settings file changed (`dummyindex/cli/init.py:51-78,109-119`, `dummyindex/cli/wire.py:46-63,156-173`, `dummyindex/context/default_plugins.py:448-524`, `dummyindex/context/claude_settings.py:175-179`). The caller gets no destination preview, containment error, or split-store warning. A sibling or user file changes, and later reads treat it as this project's effective state.
- Ordinary headless `context init` in a repository whose `config.wired` holds an arbitrary valid custom plugin target. Init writes `enabledPlugins=true` without a prompt. The reviewed-default installer silently filters that target out. A later `context wire` classifies the key as satisfied. It never presents the promised approval or repair surface (`dummyindex/cli/init.py:51-78`, `dummyindex/cli/wire.py:88-123`, `dummyindex/context/default_plugins.py:430-445,448-524,645-699`). Current help and guide say the headless reconciler only classifies and reports needs-user. They say `wire` is the escalation surface (`dummyindex/cli/help.py:700-712`, `docs/guide/07-cli.md:586-590`). So code wins. The public trust boundary is stale and unrecoverable through the advertised command. Restrict unattended mutation to reviewed defaults.
- `context init` with a durable per-target `enabledPlugins=false` tombstone. Reconciliation preserves the opt-out. But it puts the target in `already`. That renders as `<target> already enabled (left as-is)` (`dummyindex/context/default_plugins.py:293-313,478-524`). The success transcript states the opposite of the effective state. Render `already disabled (left as-is)` separately.
- `context init` when config reconciliation succeeds but settings declaration or Claude materialization fails. Warnings print. `_wire_default_plugins_step` returns no aggregate. `init.run` still exits 0 (`dummyindex/cli/init.py:51-84,225-231`). Automation cannot tell a fully ready repo from config-only intent or a partially applied machine state without scraping prose. Expose a structured final summary and a documented partial-success signal.
- `context wire --yes` for a custom `plugin@marketplace` target. Declaration writes a dangling enabled-plugin key without a marketplace source. The reviewed-default installer selects zero targets. `_wire_plugin` sees no error. The command prints `wired: <target>` (`dummyindex/cli/wire.py:88-123,156-173,221-244`, `dummyindex/context/default_plugins.py:430-445,448-524,670-699`). On the next run that key is classified as satisfied and omitted from repair. The success message promises resolution for a plugin that cannot load. It makes the false completion sticky. Reject unresolved custom sources, or route them through source-aware installation.
- `context wire` for a reviewed default when the Claude CLI is unavailable. Materialization returns `deferred`. But `_wire_plugin` tests only `errors`. It prints the same `wired` success used for a completed install (`dummyindex/cli/wire.py:156-173,221-244`, `dummyindex/context/default_plugins.py:701-729`). Interactive output hides that installation is pending until a future session. Render installed, deferred, and skipped as distinct outcomes.
- `context wire --yes` when declaration or materialization errors. The command prints `could not wire` and leaves needs-user state. The handler still returns 0 (`dummyindex/cli/wire.py:156-173,221-244`). Shell callers get the same success as a fully wired run. Reserve exit 0 for complete resolution. Or provide a machine-readable result mode with explicit partial or failure status.
- Interactive `context wire` for one of the pinned reviewed defaults that init advertises. Every syntactically valid absent plugin is labeled and prompted as `untrusted plugin` (`dummyindex/cli/wire.py:193-218`). The allowlisted, full-SHA-reviewed defaults get no distinction. The CLI presents two contradictory trust models for one target. Reuse the registry trust metadata. Reviewed defaults and custom plugins then get different disclosure.
- Interactive `context wire` pauses at a plugin prompt. Another process removes or changes that entry in `config.wired`. The handler keeps the startup snapshot. After affirmative input, it enables the stale target without rereading or checking that the entry is still declared (`dummyindex/cli/wire.py:96-166`). The confirmation looks current but is not bound to a config revision. The final summary does not show that persisted intent changed during the prompt. Reread and compare the exact entry before mutation.
- `context scan-check --json` after the severity split. `ok` reflects only error-severity violations. But `violations[]` still lists warning entries. A consumer that tests `violations.length`, or ignores the new per-violation `severity` field, calls a warnings-only scan failed. The process still exits 0 (`dummyindex/cli/scan.py:69-95`). Document `severity` as the discriminator. Or split warnings into their own array.
- `context graph` for a resolved symbol that has no edges. Only `path` and `community` map an empty answer to exit 1. `callers-of`, `callees-of`, `neighbors`, `impact`, and `dead-code` return 0 with an empty listing (`dummyindex/cli/graph.py:182-183`). A valid empty answer is the point of `dead-code`. Shell callers that probe whether a query hit must special-case the verb. The usage block documents the exit-1 cases but not this asymmetry (`dummyindex/cli/help.py:291-292`).

## Rule-copy canary

- **The constant-to-doc coupling is human-maintained, not mechanical.** Each `_PolicyInvariant` row pairs a `constant_pattern` with a `statement_pattern`. Both are written by hand. Rewording `ALWAYS_ON_OUTPUT_POLICY` and updating only the constant side leaves docs stale while the suite stays green. `_POLICY_CONSTANT_HASH` mitigates this by forcing an editor to re-check coverage. But it is a prompt, not a check. Upstream ponytail accepts the same limitation with its hand-maintained `INVARIANTS`.
- **Adding a new rule to the policy does not force a new row.** The hash pin fires on any constant edit, which is the only signal. Nothing verifies that the row set still covers every load-bearing clause.
- **The markers are test-only scaffolding in shipped files.** They live in `dummyindex/skills/skill.md`, which ships. They sit outside the reserved `dummyindex:*` marker namespace, and nothing parses them at runtime. `render_skill` strips them. A future reader may still find comment syntax in a shipped doc. It serves a test in a repo they may not have.
- **A missing or unbalanced marker pair is a hard failure, not a silent empty scan.** This is deliberate. A silently empty region would pass every assertion while checking nothing.

## Placement

- **Four new CLI wire modules register through this feature's seam, but no curated feature owns them yet.** `dummyindex/cli/maintain.py`, `fleet.py`, `drift_ack.py`, and `evolve.py` exist at HEAD. Either cli-dispatch takes them (wire-layer only), or they get their own maintenance-family features at the next reconcile. Until then, this feature documents them as registration-only.

It re-baselines an orphaned anchor at HEAD instead (`dummyindex/cli/reconcile.py:85-130`). That default-off ruling is correct. But nothing distinguishes a cleanly anchored run from a healed one, except the warning text on stdout. If automation parses stamp output, a machine-readable healed marker keeps the two cases apart.
