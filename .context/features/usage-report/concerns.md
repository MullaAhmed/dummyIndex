## Data integrity

- **Non-numeric `usage` field crashes the whole read, defeating best-effort.** `_turn_from_line` runs `int(usage.get("input_tokens") or 0)` and similar calls (`dummyindex/usage/transcripts.py:138-141`). `int()` raises `ValueError` on a float-string (`"12.5"`) or other non-coercible string. `_read_file`'s try/except guards only `json.loads` (`transcripts.py:165-168`) and `open` (`OSError`, `156-159`). The `_turn_from_line` call at `174-176` is unguarded. One malformed numeric value aborts the generator mid-file. That silently truncates later turns. For `load_session`, the whole report stops. This contradicts the plan's claim that a single bad line should not sink a read (`plan.md:107-109`). Fix: coerce defensively (per-field try/except to 0) or wrap the `_turn_from_line` call.

- **Dedup keeps the FIRST line per `message.id`. Streaming usage is cumulative on the LAST line.** Risk: undercount. `_dedup_key` is `message.id|requestId` (`transcripts.py:100-111`). `_read_file` adds the key to `seen` on first yield. It skips all later lines with that key (`172-181`). Claude Code rewrites the same message as the stream completes. If the authoritative final token usage lands on a later line for the same `message.id`, first-wins undercounts. The dedup is correct for "count once" but assumes every line for a key carries identical usage. That invariant is unstated and unverified. Confirm against a real multi-line message, or switch to last or max per key.

- **Global seen-set in `iter_all_turns` can collapse distinct turns sharing a fallback key across projects.** `iter_all_turns` uses one `seen` set spanning every main and subagent file (`transcripts.py:243-262`). `load_session` scopes main and subagent independently (`204-227`). For lines lacking `message.id`, the key falls back to line `uuid` (`_dedup_key:110-111`). `uuid` is globally unique, so that is safe. But turns that share a `message.id` across different sessions are counted once globally. Forked or resumed transcripts re-emit ids. Yet it drops a genuinely re-issued turn with new usage. Cross-project totals hinge on "same `message.id` implies same tokens." Nothing in code or tests asserts that.

- **`find_main_transcript` tie-breaks only on `st_mtime`, so equal-mtime matches are non-deterministic.** `transcripts.py:70-74` (and the no-session fallback `77-79`) sort by `st_mtime` in reverse and take `[0]`. Two transcripts with identical mtime give a winner that depends on filesystem order. Examples include the same `session_id` under two project slugs, or copied files. The report silently picks a different session run to run. Fix: add a stable secondary sort key, such as path.

- **`load_session` indexes `main_turns[-1]`, `min`, and `max` over file order, not timestamp order.** `chat_report` takes `window_now = window_tokens(main_turns[-1])` (`aggregate.py:95`) as the most recent main turn. But `main_turns` is in file line order, not timestamp order (`load_session:205-213`). If a transcript is appended out of chronological order (resume or fork interleaving), `[-1]` is not the latest turn. Then `window_now` is wrong. `started` and `last` correctly use `min` and `max` over timestamps (`aggregate.py:107-108`). Only `window_now` assumes monotonic file order, unguarded.

- **Timestamp parse normalises `Z` via blind `replace`, corrupting any literal `Z` mid-string.** `_parse_timestamp` runs `raw.replace("Z", "+00:00")` (`transcripts.py:92`). That replaces every `Z`, not only a trailing one. A pathological timestamp such as `2024Z01...` would be mangled. In practice Claude emits clean ISO-8601, so impact is low. But the transform is not anchored to the end. Prefer `raw.removesuffix("Z") + "+00:00"` (3.9+) or slicing the final char.

- **`chat_report` reads `main_turns[-1]` after an `if main_turns` guard. `infer_context_limit(peak_window=0)` returns 200K for an empty session.** A session with only subagent turns and zero main turns reports `context_limit=200000` and `window_now=0` (`aggregate.py:95-100`). That is a sane floor, not a bug. The empty-main path is handled.

## Security

Threat model: the usage feature ingests `~/.claude/projects/**/*.jsonl`. Claude Code writes those transcripts. Their content (model strings, usage numbers, timestamps) is partly derived from assistant and tool output. Anything that ever appeared in a chat can influence it. Treat every parsed field as untrusted at the render boundary. Severity tags are HIGH, MED, and LOW.

- **[HIGH] Terminal-escape injection via the `model` field into rendered report (info-leak / spoofing).** `model = message.get("model") or ""` is taken verbatim from transcript JSON (`transcripts.py:127`). It flows unsanitized into `TurnUsage.model` (`:137`). `by_model` groups it. It prints raw as the first table cell: `_totals_row(usage.model, …)` (`render.py:84`). `_table` left-justifies it with `.ljust` (`render.py:31`) and joins (`:33`). Then `__main__` does `print(text)` (`__main__.py:97`). Nothing strips control characters. Attack path: a transcript line such as `{"type":"assistant","message":{"model":"[2J[1;1H FAKE-BILLING…","usage":{…}}}` renders ANSI escapes to the user's terminal when they run `dummyindex usage`. A malicious MCP or tool can write that content, since Claude Code persists it. A hand-edited or synced transcript file works too. Impact: clear-screen, cursor-move, hyperlink (`OSE 8`), and color sequences let an attacker forge a benign-looking usage table. They can hide rows. With `\r` or overwrite, they can rewrite earlier output. That is a credible vector for masking unexpected token spend or impersonating a "TOTAL" line. The `_c()` numbers are safe, being int-formatted. The `model` and session or project columns are not. Fix: at the render boundary, strip or escape C0/C1 controls before placing any transcript-derived string in a cell. For example, reject anything matching `[\x00-\x1f\x7f-\x9f]`, or `repr`-quote it. Do this for `model`, `project`, and `session_id`.

- **[MED] `project` column is filesystem-derived but still rendered unsanitized.** `render_sessions` prints `_shorten(bucket.project, 28)` (`render.py:179`). `project` is `main_transcript.parent.name` (`transcripts.py:203`, `246`), the project-slug directory name. `encode_project_slug` maps non-alphanumerics to `-` (`:49-51`). So slugs this tool creates are clean. But the glob (`*/*.jsonl`, `*/<sid>.jsonl`) trusts whatever directory names already exist under `projects_root`. A directory named with embedded escapes or newlines flows straight into the table. Such a directory could come from another tool, an archive extraction, or a synced `.claude` dir. The same sanitization fix covers it. Severity is lower, because creating such a name needs filesystem write access under `~/.claude/projects`.

- **[MED] Unbounded single-line read enables memory-exhaustion DoS on a malformed transcript.** The module advertises streaming, "never slurps — some are tens of MB" (`transcripts.py:4-5`). It iterates `for line in handle` (`:161`). That yields one line at a time with no length cap. A transcript with a single multi-gigabyte line and no `\n` is read entirely into one `str`. Causes: a corrupted or oversized JSON blob, or a crafted file. The iterator then hands it to `line.strip()` (`:162`) and `json.loads` (`:166`). Peak memory is a few times the line size. For the per-project kinds (`daily/monthly/session/blocks`), this runs over every transcript via `iter_all_turns` (`:244-262`). So one planted oversized file can OOM-kill the whole report. Fix: bound line length. Read in chunks, or enforce a maximum bytes per line and skip over-long lines. That matches the existing best-effort skip stance (`:167-168`).

- **[LOW/MED] `json.loads` on attacker-sized lines causes CPU and recursion DoS, not only memory.** The same untrusted line feeds `json.loads` (`transcripts.py:166`). Only `JSONDecodeError` and `ValueError` guard it (`:167`). A deeply nested JSON line can hit Python's recursion limit. That raises `RecursionError`. It is not a subclass of `ValueError`, so it is uncaught. It propagates out of the generator and aborts `iter_all_turns` or `load_session`. This defeats best-effort, like the `int()` issue above. A huge but valid line also burns CPU. Fix: pair the line-length cap with broadening the parse guard to catch `RecursionError` too. Then one crafted line is skipped, not fatal.

- **[LOW] Arbitrary file read via transcript path is largely N/A. Note the env-var seam.** The CLI exposes **no** path argument. `_run_usage` parses only a report-kind token and rejects extra args (`__main__.py:67-84`). The file path is always derived by globbing under `projects_root` (`find_main_transcript:69-80`, `iter_all_turns:244`). So there is no direct path-traversal sink. The one influence seam is `CLAUDE_CONFIG_DIR` into `default_projects_root` (`transcripts.py:36-40`). An attacker who controls that env var, or `$HOME`, can repoint the scan at any directory. Its `*/*.jsonl` contents are then read and rendered. That requires already controlling the victim's environment, so it is informational, not a vuln in this code. `session_id` appears only inside a glob pattern (`f"*/{session_id}.jsonl"`, `:71`). `glob` does not treat `..` or absolute paths as traversal here. A hostile `$CLAUDE_CODE_SESSION_ID` therefore cannot escape `projects_root`. No fix required. Documented so a future path-accepting variant adds `Path.resolve()` and containment checks.

Net: the single material finding is terminal-escape injection of transcript-derived strings into the report (HIGH). The unbounded-line and uncaught-`RecursionError` DoS pair is MED. Both are remediable at the trust boundary, without changing the dedup or aggregation logic. Fixes are render-time sanitization and a per-line size and recursion guard.

## Product surface

- **No-session error is correct, but the message blames the user for an env var Claude Code owns.** `dummyindex usage` (chat) with no `$CLAUDE_CODE_SESSION_ID` and no cwd transcript exits 1. It prints `could not identify the current session: $CLAUDE_CODE_SESSION_ID is unset and no transcript exists under <slug>` (`report.py:69-73`). Running it directly, outside the `/tokens` slash command, hits this every time. Only `/tokens` injects the env var. The message reads like a bug report about an internal variable, not an instruction. Gap: no hint that this command must run inside a Claude Code session. No fallback suggestion either, such as `dummyindex usage session` for cross-session history. The non-chat kinds work fine without the env var, but the error does not say so.

- **Brand-new-session "empty" chat renders a confusing all-zero table with no explanation.** When `session_id` is known but its transcript isn't flushed, `_chat` builds `chat_report(session_id, (), (), subagent_count=0)` (`report.py:62-68`). Then `render_chat` prints `Context window now 0 tokens (≈0% of 200K …)`. It also prints a bare `TOTAL  0 0 0 0 0` row, with no per-model rows because `by_model` is empty. `started` and duration are omitted, and `subagents: none` appears (`render.py:81-128`, `aggregate.py:95-108`). Gap: a user sees a zero-filled report with no "session not flushed yet" or "no turns recorded" note. It is indistinguishable from a real session that spent zero tokens. The design intent, "renders empty, never a sibling's numbers" (`spec.md:30-33`), is invisible to the reader.

- **The `(deduplicated; cache re-reads counted each turn)` caption is the only on-screen dedup explanation, and it conflates two ideas.** The chat table header is `Session cumulative — by model (deduplicated; cache re-reads counted each turn)` (`render.py:122-123`). Deduplicated means counting one logical turn once across rewritten or forked lines (`spec.md:9-11`). Cache re-reads counted each turn is a billing choice about `cache_read_tokens`. The two are unrelated. The parenthetical joins them with a semicolon, which implies they are one caveat. Gap: a user reconciling these numbers against Anthropic billing cannot learn what was deduplicated. Nor can they learn why the cumulative total may exceed naive line-summed totals. The daily, session, monthly, and blocks tables carry no dedup caption at all (`render.py:131-203`). The accuracy caveat disappears on 4 of 5 report kinds.

- **The `(matches /context)` window claim is an unverifiable promise on inferred limits.** The window line asserts `(≈{pct}% of {limit} · main thread · matches /context)` (`render.py:92-95`). The denominator is inferred. It is the smallest of `(200K, 1M)` that holds the peak window (`aggregate.py:100`, `infer_context_limit`). It is not the model's real advertised window. A 1M-context session whose peak never exceeded 200K reports `% of 200K`. Also, `window_now` is `window_tokens(main_turns[-1])` over file order, not timestamp order (flagged in Data integrity, `aggregate.py:95`). Gap: the literal "matches /context" claim is wrong whenever the inferred tier differs from the live model's window. It is also wrong when file order is not chronological. Yet the text states it as fact. A user who spots the mismatch will distrust the whole report.

- **`>100%` window overflow has no clamp. A session above 1M prints a nonsensical percentage.** `pct = round(window_now / context_limit * 100)` (`render.py:87-91`), with `context_limit` capped at the largest tier, 1M (`infer_context_limit`, `aggregate.py`). The plan flags this as an open question (`plan.md:131-133`). A session above 1M reports `≈>100%` with no clamp. Gap: the percentage is the headline number of the `/tokens` view. It can read `≈137%`. That looks like a bug to a user. It undermines confidence in the figure meant to "match /context."

- **Help text and the doc-hinted capability set list five report kinds with no hint of what each shows.** `dummyindex usage -h` prints exactly `Usage: dummyindex usage [chat|daily|session|monthly|blocks]` (`__main__.py:70`). It gives kind names only, with no one-line description. It does not say that `chat` needs a live session, while the other four scan all projects. Gap: via `--help`, a user cannot tell `blocks` (5-hour billing windows) from `session` (per-chat rows). Only trial and error reveals the difference. The richer guidance exists only in the `/tokens` skill prose (`skills/commands/tokens.md:14-15`). Bare-CLI users never see it. The spec's per-kind descriptions (`spec.md:27-39`) appear nowhere the end user sees.

- **Truncated 8-char session ids and `…`-truncated project names can collide or mislead in multi-session tables.** `render_sessions` shows `bucket.session_id[:8]` (`render.py:178`). `_shorten(bucket.project, 28)` keeps the tail and prepends `…` (`render.py:210-211`). Gap: two sessions sharing an 8-char prefix render as the same id. No disambiguator exists. Two projects differing only in a long common suffix (`…/projects/app-frontend` vs `…/app-backend`) become indistinguishable once truncated. So a user cannot reliably map a row back to a real session or project. There is no `--full`/`--no-truncate` escape hatch.
