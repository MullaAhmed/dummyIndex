## Data integrity

- `memory/breadcrumb.py:49-52` — the "newest section is already a breadcrumb, replace it" branch checks only `AUTO_BREADCRUMB_TAG`. It ignores date and session. `roll_tiers` is wired to **no hook**. Only `dummyindex/skills/memory/SKILL.md:30` calls it, from the agent running `/dummyindex-remember`. Users who never save a handoff therefore lose data. Every PreCompact destroys the previous day's and every concurrent session's breadcrumb. Only one auto-entry ever survives. Fix: compare `section_date(sections[0].heading)` with `now.date()` and the session id. Prepend when they differ instead of replacing.
- `memory/roll.py:84-98` — the tier cascade is three independent `write_text_atomic` calls. The delete side runs first: `now.md` minus `now_down` (`84-88`), then `recent.md` plus `now_down` (`89-93`). A crash, OSError, or SIGKILL between them permanently loses the relocated sections. No tmp file remains to recover from. Fix: invert to archive, then recent, then now. An interruption then duplicates instead of deleting. The re-run must drop sections already present.
- `memory/roll.py:39-41,74` + `memory/parse.py:21,52-55` — `_DATE_RE` accepts any `\d{4}-\d{2}-\d{2}`, including non-constructible dates. A heading containing `2026-13-45`, or a ticket or version token of that shape, makes `_ordinal` raise `ValueError` out of `roll_tiers`. `cli/memory.py:189` has no try/except. Worse, `_is_before_today` compares strings. The bad section first moves down into `recent.md`, then breaks every later roll. Fix: `section_date` returns `None` when `date(...)` cannot be constructed. Malformed text is then treated as undated.
- `memory/emit.py:40-60` — `now` is inlined in full, while `recent` is capped at `_RECENT_HEAD`. The `max_chars` cut at `59-60` truncates from the end. Once `now.md` passes about 3.9 KB, the SessionStart block silently drops `core-memories.md`, the one durable tier that is never rolled. Fix: apply `_head` to `now` too, and reserve a fixed budget for `core` before truncating.
- `memory/breadcrumb.py:47-54`, `memory/nudge.py:60-67`, `memory/roll.py:64-98` — every store mutation is an unlocked read-modify-write. `domains/atomic_io.py:14-18` documents that two Claude profiles hit the same repo concurrently. `write_text_atomic` prevents a torn file but not a lost update. A breadcrumb written between another session's roll-read and roll-write vanishes. Fix: guard tier-store read-modify-write with an `O_EXCL` lock file. The pattern already exists at `context/output/bootstrap.py:499`.
- `domains/atomic_io.py:22-31` — there is no `flush` or `os.fsync` before `replace`, and no parent-directory fsync. The tmp sibling is unlinked in `finally`. A power loss mid-write can leave a zero-length `now.md` with nothing to recover from. This is the git-committed, user-owned half of the store. The repo lives on a mounted Windows filesystem, where rename-after-content ordering is weaker than on ext4. Fix: fsync the handle before close, and the directory after `replace`.
- `domains/atomic_io.py:22-29` — `NamedTemporaryFile` creates the replacement at `0600`, and no mode is copied from the original. Every `.context/session-memory/*.md` and cache file therefore loses group and other read permission on its first rewrite. Git tracks only the exec bit, so the change is invisible. Fix: `os.chmod` the tmp to the pre-existing file's `st_mode`. For a new file, fall back to `0o666 & ~umask`.
- `miner/pipeline.py:146-152` + `miner/feedback.py:112-133` — `refresh_skill_feedback` discards the `bool` from `write_skill_feedback`. That function returns `False` on every `OSError` (`117`, `131-132`). `cli/memory.py:101-108` swallows whatever escapes. An unwritable `.context/cache/` therefore makes `memory mine` a permanent silent no-op. It still returns a populated tuple to its caller. Fix: propagate the write outcome and surface it on the non-hook invocation path.
- `miner/feedback.py:113-128` — the write path `lstat`s for symlink and regular file. Unlike `read_skill_feedback:143-152`, it never checks `st_size` before the `path.read_text()` comparison. A corrupt or oversize `skill-feedback.json` is decoded in full on every SessionStart. Fix: apply the same `MAX_CACHE_BYTES` guard before the comparison read.
- `miner/pipeline.py:112-137` + `miner/corrections.py:269-283` — the cache is a pure projection, recomputed from whichever transcripts still exist. There is no decay and no durable record. When the host prunes old JSONL, the count falls below `DEFAULT_MIN_SKILL_CORRECTIONS` (`miner/enums.py:38-40`), and an established preference silently disappears. The derived state is non-monotonic, and no consumer can detect it. Fix: persist first-seen and last-seen counters in the cache. Threshold on those, not on live transcript availability.
- `memory/parse.py:35-42` — `split_sections` treats any line starting with `## ` as a boundary, with no fenced-code awareness. A handoff containing a markdown example therefore splits into two sections. `roll_tiers` can send them to different tiers, severing a fence and orphaning half an entry. Fix: track ` ``` ` and `~~~` fence state while scanning.
- `memory/parse.py:40,48,70` — the split and render round-trip is lossy. Bodies get `.strip("\n")`, and sections are re-joined with exactly one blank line. A roll therefore rewrites the formatting of user-authored entries it did not move. This contradicts the byte-faithful contract that `write_text_atomic` promises at `domains/atomic_io.py:41-45`. Fix: preserve each section's inter-section whitespace, or state the normalization as the store's contract.
- `memory/nudge.py:38-46,60-67` — `_load_state` checks only that the top level is a `dict`. `mark_nudged` then calls `kv[1].get(...)` on every value, so one non-dict entry raises `AttributeError`. The NUDGE verb has no try/except (`cli/memory.py:144-156`), unlike MINE and PROMPT_CONTEXT. That breaks the "a Stop hook must never fail the turn" guarantee asserted at `cli/memory.py:156`. The same shape appears at `context/reconcile_gate.py:255-263`. Fix: drop non-conforming entries on load, matching the fail-closed validation that `miner/feedback.py:136-200` applies to the sibling cache.
- `memory/roll.py:79,94-98` + `memory/emit.py:40-42` — `archive.md` is append-only, with no tier below it and **no reader**. Emit consumes only now, recent, and core. Yet it is git-committed, because `.gitignore:19` covers only `.context/cache/`. It grows without bound in every consumer repo. Fix: bound it by size, or split by year at roll time.

## Security

- `miner/scan.py:209-227` + `miner/feedback.py:203-247` + `cli/memory.py:110-142` — **Transcript-mined "human directives" have no proof of human origin, so repo-controlled text becomes a per-turn instruction.** `_human_prompt_text` accepts any `type:"user"` / `userType:"external"` row whose content is a string or all-`text` blocks. The `origin.kind == "human"` check is `if origin is not None:`. The field is absent on this Claude Code version, so the check never fires. Verified against the live store: **220 rows are slash-command expansions** (`<command-name>…<command-message>…`; keys are `cwd, entrypoint, gitBranch, isSidechain, message, parentUuid, promptId, sessionId, timestamp, type, userType, uuid, version`, with no `origin`). They pass the filter as human prompts. So does a row that is a whole injected charter file (`# Instructions (read first)…`).

  Attack: a repo ships `.claude/commands/<x>.md`, or any prompt-file body expanded into the user turn. The body contains the plain sentence `Use the <attacker-slug> skill.` `_POSITIVE_PATTERNS[0]` matches it (`corrections.py:35-41`). `_without_quoted_examples` does not strip it, because it removes only backticked and quoted text. Two invocations suffice, even in one session. They yield distinct `uuid`s and so distinct `event_key`s. `DEFAULT_MIN_SKILL_CORRECTIONS = 2` counts corrections, not sessions. `write_skill_feedback` then persists the promotion. From then on, every `UserPromptSubmit` injects `- \`<attacker-slug>\`: If this skill is currently exposed and its trigger matches or the user names it, invoke and follow it on this turn.` under a header that tells the model these are *instructions* (`feedback.py:25-28`). Pair it with a planted `.claude/skills/<attacker-slug>/SKILL.md`. Repo content has then bought a standing per-turn invocation directive.

  Mitigation is partial. `_valid_slug` (`feedback.py:45-53`) and the fixed sentence templates (`feedback.py:25-37,239-247`) cap the payload at a 64-char `[a-z0-9-]` slug inside text dummyindex wrote. No free-form attacker prose reaches the prompt. `MAX_PROMPT_SKILLS` and `MAX_PROMPT_CHARS` bound the volume. Nothing mitigates the rest. `cwd` matching (`scan.py:193-206`) passes by construction, since the malicious content is this repo's. The mine hook runs with `>/dev/null 2>&1`. `prompt-context` sets `suppressOutput: true` (`hooks.py:110-145,147-198`). Neither the write nor the injection is user-visible. Per `plan.md:111`, nothing ages the promotion out. Deleting the malicious file does not revoke it, because re-derivation re-reads historical transcripts forever.

  Fix: require a positive human marker rather than tolerating an absent one. Treat a missing `origin` as non-human, or reject rows containing `<command-name>`, `<command-message>`, or `<system-reminder>`. Add a max-age window to `aggregate_skill_corrections`.

- `miner/signatures.py:86-99` + `miner/scope.py:52-71` + `miner/render.py:73-87` — **the failure-pattern renderer writes tool inputs verbatim into a git-tracked file, and the sanitizer redacts only paths.** `canonical_signature` keeps every non-pagination structured field byte-for-byte (`signatures.py:93-99`). The bash branch keeps the whole command string, lowercased, with integers collapsed. `sanitize_signature` rewrites or redacts only what matches `_ABSOLUTE_PATH_RE`. It has no notion of a token, key, or header. Two `Write` calls with the same `content` (a `.env` or key file) put that secret in the file. So does a repeated `curl -H "authorization: bearer sk-…"` in one session. Both land in `.context/session-memory/failure-patterns.md`, which is committed. The banner's claim, "no excerpt of tool output is kept" (`render.py:60-65`), is true but beside the point. The leak is on the input side. `plan.md:90` ("Privacy is structural, not a filter") overclaims. It is accurate for `ToolCallRecord` and `SkillDirectiveEvent`, not for `RepeatedSignature.signature`.

  The load-bearing mitigation is that the pipeline is **unwired**. `write_report` is reachable only from `mine_and_feed` and `scan_transcript_store`, and no CLI verb calls them (`cli/memory.py:101-108` routes `mine` to `refresh_skill_feedback`). That is the open question at `plan.md:109`. "Gets a verb" must not be chosen before this is fixed. Fix: redact or hash the signature body for non-allowlisted tools, or render `sha256(signature)[:12]` plus the tool name. Correct decision 4's scope claim.

- `cli/memory.py:45-56` + `cli/reconcile_gate.py:24-33` + `context/reconcile_gate.py:240-263,283-295` — **hook stdin is trusted verbatim by the shared adapter. The Stop gate's block-once memo is keyed on a caller-supplied `session_id`, so one ordinary CLI call disarms the staleness gate.** `resolve_transcript` turns `hook["transcript_path"]` straight into `Path(tp)`, with no containment check against the resolved store (`transcript.py:57-60`). `session_id` is taken as given. Attack path needs no privilege and no hook. The agent, or anything running as the user, runs one Bash call: `printf '{"session_id":"'"$CLAUDE_CODE_SESSION_ID"'","transcript_path":"/nonexistent"}' | dummyindex context reconcile-gate --root <repo>`. With any index stale, `decide_block` takes the "transcript unreadable but session id present" branch. It calls `mark_blocked`, prints an advisory, and exits 0. The genuine Stop hook then returns `None` at `already_blocked` (`reconcile_gate.py:240-247`). The gate is spent for the session, which is exactly when it should fire. The same adapter serves `guard_doc_write.py:27`, so the trust assumption is repo-wide. `read_hook_stdin` also reads stdin unbounded, with no size cap (`cli/memory.py:33`).

  Mitigation: **none.** There is no authenticity check on hook stdin. `transcript_path` is not contained under `<config>/projects/`. The supplied `session_id` is not checked against `CLAUDE_CODE_SESSION_ID`. Cheapest fix: in `resolve_transcript`, reject a `transcript_path` that does not resolve under the resolved projects store. In `decide_block`, honour only an explicit `session_id` that matches the live env id, and fall back to `resolve_session_id()` otherwise.

- Checked and clean, recorded so they are not re-litigated. `tool_result` rows are `userType:"external"`, but the block-type check rejects them (`scan.py:238-246`). `.context/cache/` is genuinely gitignored (`.gitignore:19`), so `skill-feedback.json` is not committed. `read_skill_feedback` (`feedback.py:136-200`) refuses symlinks, non-regular, oversize, duplicate, and mis-sorted files fail-closed. Running the real grammar over the entire local transcript store produced **one** match, an authentic human prompt. The false-positive rate on organic content is not the problem. Adversarial content is.

## Product surface

- Every prompt in an equipped repo runs `dummyindex context memory prompt-context` as its own process (`hooks.py:132-143`). Measured on this repo: 0.94 s and 1.07 s wall, against a 1.20 s floor for `dummyindex context memory` with no verb. That floor is an exit-2 path that opens no store. The gap: about 1 s of interpreter and import startup is paid on every turn. That includes turns where `.context/cache/skill-feedback.json` is absent and nothing prints. No `stat`-first fast path exists before the Python cost.
- SessionStart in this repo runs four dummyindex commands (`hooks.py:147-198`). Measured: `plan-update` 3.14 s, `memory session-start` 1.14 s, `gc signal` 1.56 s, and `memory mine` 1.30 s and 1.52 s. Total is about 7.1 s. The gap: `memory mine` adds about 1.4 s unconditionally. Nothing compares transcript-dir mtimes against the last cache write to skip a scan that cannot have changed.
- The wired miner, on its own home repo: 19 root-level transcripts, 23 MB, under `~/.claude/projects/-mnt-windows-ssd-Projects-dummyindex`. Of these, 524 candidate `"type":"user"` rows contain `skill`. `parse_skill_directive_events` across all 19 yields **1** event, below `DEFAULT_MIN_SKILL_CORRECTIONS = 2` (`miner/enums.py:38-40`). So `refresh_skill_feedback` returns `()`, and `write_skill_feedback` returns early without creating the cache (`feedback.py:119-120`). The gap: in the repo whose own `.claude/CLAUDE.md` carries a standing `caveman` and `i-have-adhd` instruction, the feature delivers zero output. It still charges the latency above. Precision-first is decision 6. The intended trigger case does not fire.
- A user asking "is skill feedback working?" gets no answer. `mine` swallows every exception (`cli/memory.py:106-107`), with stdout sent to `/dev/null` (`hooks.py:185-196`). `prompt-context` sets `suppressOutput: true` (`cli/memory.py:135`). `dummyindex context status` prints only `session-memory: present|absent` (`cli/status.py:57,326`). `MemoryVerb` has no show, explain, or clear member (`memory/enums.py:17-26`). The gap: a broken install, an empty scan, and a working silent run look identical from the user's seat. Nothing shows what was injected into the last prompt.
- A user who wants the injection off has two switches. The reconcile gate names its own opt-out in the block text (`"auto_council": false`, `reconcile_gate.py:128-130`). `.remember/` stands down emit, nudge, and breadcrumb (`detect.py:8-15`). The gap: neither switch reaches `mine` or `prompt-context`. Plan decision 13 states this deliberately. The only off-ramps are editing the managed `.claude/settings.json` hook block, or deleting a cache that the next SessionStart rewrites.
- A correction given twice inside one session. The cache refreshes only at SessionStart, and only a directive in the *current* prompt is exempt from the threshold (`feedback.py:227-236`). The gap: the second event does not become durable policy until the next session. The "already said twice" contract holds across sessions, not within one.
- A user types `normal mode` mid-session. That turn's render drops the cached `i-have-adhd` line (`feedback.py:210-225`). The gap: the drop lasts one turn. The cache stays untouched until the next `mine`. The line returns on the next prompt of the same session, unless the revocation phrase is retyped.
- The same repo opened through a git worktree, a symlink, or a different mount point. `project_dir_name` dashes the *resolved* absolute path, and the store directory must match exactly (`scope.py:41-49`). The gap: corrections given from an alternate path are invisible to the primary checkout. No diagnostic separates "no corrections" from "wrong project dir".
- Multi-profile hosts. `resolve_claude_config_dirs` unions `~/.claude`, `$CLAUDE_CONFIG_DIR`, and every `~/.claude-*` directory (`resolve.py:47-56`). This machine resolves two: `/home/ahmed/.claude` and `/home/ahmed/.claude-os`. The gap: an abandoned or experimental profile keeps promoting skills. The cache records slug and counts only, so the contributing profile cannot be recovered. There is no per-profile exclusion.
- A correction from months ago. `aggregate_skill_corrections` counts every post-revocation event in every retained transcript, with no time window (`corrections.py:269-281`). The gap: a stale instruction stays on every prompt until the user types a revocation phrase or deletes transcripts. There is no decay and no per-slug reset verb.
- A repo whose `now.md` has grown. `render_session_start` builds the handoff header, the full `now.md` body, the first 1500 chars of `recent.md`, and all of `core-memories.md`. It then tail-truncates the whole block at 4000 chars (`emit.py:33-61`). The gap: `core-memories.md` is appended last, so the durable tier is the first content dropped. The user sees `…(truncated)` with no sign that core memories were lost.
- A user who never invokes `/dummyindex-remember`. `roll` appears on no hook event (`hooks.py:110-243`). Its only caller is step 4 of the skill (`skills/memory/SKILL.md:28-30`). The gap: hand-edited stores never roll. `now.md` accumulates dated sections and uses up the 4000-char emit budget indefinitely.
- PreCompact fires after a real handoff was already saved today. `write_breadcrumb` makes the `(auto-breadcrumb)` entry the top section. `real_handoff_saved_today` inspects only `sections[0]` (`nudge.py:70-79`). The gap: compaction re-arms the Stop nudge for a session that already saved. The agent then offers a handoff the user already made. The memo at `nudge.py:56-67` bounds this to once per session.

Archive is terminal, committed, never emitted by `render_session_start`, and never pruned. The gap: the only monotonically growing tier is also the only tier no surface reads. - The docs at `docs/COMMANDS.md:224` and `docs/guide/07-cli.md:484` say the `failure-patterns.md` miner "remains an explicit command path" or "remains explicit and unwired". `MemoryVerb` has seven members, and none reaches `mine_and_feed`. `memory mine` routes to `refresh_skill_feedback` (`cli/memory.py:101-108`). - If the failure-pattern pipeline gets a verb. `write_report` targets `.context/session-memory/failure-patterns.md` (`miner/render.py:11-19,83`). That is a **committed** directory, not gitignored `cache/`. `ensure_memory_store`, `roll_tiers`, and `render_session_start` all iterate `MemoryTier`, which excludes the filename. The gap: the output would be a committed file that no surface reads and no lifecycle maintains. The `_ERROR_MARKERS` false-positive rate (`miner/scan.py:29-41`) is unmeasured, because nothing consumes it.
- `dummyindex context memory init` in a built repo. `build/runner.py:245-249` calls `ensure_memory_store` on every rebuild, so the store and its four stubs already exist. ## Drift engine (reconcile 2026-08-23)

- **Basis-classified rows ignore doc-side recency, so the rendered advice is now wrong for them.** In `compute_drift`, a (feature, file) pair covered by `cache/doc-basis.json` is classified purely by blob-sha equality (`dummyindex/context/drift.py:215-232`). Equal means suppressed. Unequal means a row. Doc mtime is consulted only on the manifest and mtime fallback (`:235-243`). After stamp, a source edit, and doc edits without a re-stamp, the pair keeps reporting as drift. That lasts until the next `reconcile-stamp`. Meanwhile `_render_mtime_section` still prints a hint (`drift.py:368-371`), and the hint is false for exactly these pairs. Fix: consult `_newest_doc_mtime` on the basis branch too. Or reword the hint to "or run `reconcile-stamp`". The hint reads: "_Drift clears naturally: once you edit a feature doc, its mtime updates and these entries drop off._"
- **`drift-ack` without `--path` bulk-acks every currently drifting file of the feature in one shot** (`dummyindex/cli/drift_ack.py:111-119`). One invocation with a fat-fingered `--reason` dismisses all real rows of that feature until their bytes change. Nothing distinguishes one deliberate ack from ten rows waved through, because `acked_count` renders only as a silent counter. Cheapest fix: require a confirmation flag when record mode expands past one file. Alternatively, print the would-be acked list with `--dry-run`.
