## Security

Threat model note: the guard is a *hygiene* control over a semi-trusted agent, not a containment boundary — anything that removes `dummyindex` from PATH, or the `2>/dev/null || true` + `exit 0` wrapper in `hooks.py:257-262`, already silently disables it. The findings below are cases where the guard silently disagrees with the filesystem, ranked by how invisibly they fail.

- **[1] `cli/guard_doc_write.py:46` + `cli/common.py:31-34` vs `domains/docguard/classify.py:174-185`** — resolution asymmetry: `resolve_context_root` returns `explicit_root.resolve()` (symlinks followed) while `_rel_posix` uses lexical `Path.relative_to` on the raw `file_path` with a comment explicitly forbidding `resolve()`. When the project is reached through a symlink — symlinked git worktree, `/tmp` → `/private/tmp` on macOS, a home-dir or bind-mount alias — `$CLAUDE_PROJECT_DIR` resolves to the real path, the harness sends the aliased path, `relative_to` raises `DocPathError`, and `run`'s catch-all (`:39-42`) converts it to exit 0. **The guard is then off for every write in the repo, with no output and no error.** Verified: identical `Write` payload for `<root>/docs/plans/x.md` emits the deny through the real root and emits *nothing* through a symlink to that same root. Mitigation: **none** — nothing in `tests/cli/test_guard_doc_write_e2e.py` constructs a symlinked root, so the whole-guard-disabled state is untested. Fix: compare `os.path.realpath` of both sides (once, at the boundary in `guard_doc_write._decide`) before falling back to allow; the classifier stays lexical.

- **[2] `domains/docguard/classify.py:88-102`** — the location gate reads `parts[0]` and `set(interior)` off an un-normalized path, so a `..` segment moves a write across the gate in *both* directions. Verified: `<root>/src/../docs/plans/x.md` classifies `is_planning_doc=False` → allowed, while the write physically lands in `docs/plans/`; inversely `<root>/docs/plans/../guide/x.md` classifies as a stray → **denied**, though it lands in `docs/guide`, an `EXCLUDED_DOCS_SUBTREES` path the design says is never a stray. Attack path: an agent steered by injected content in a repo file (a README, an issue body, a vendored doc) writes the traversal form and the leak the feature exists to stop lands anyway. Mitigation: **none in this code** — it depends entirely on an unverified assumption that Claude Code normalizes `tool_input.file_path`; nothing in the guard, the classifier docstring, or the tests states or pins that assumption. Fix: `os.path.normpath` in `_rel_posix` before `relative_to` — still pure/lexical, no I/O, no contract change.

- **[3] `.context/features/managed-doc-homes/spec.md:32` vs `domains/docguard/decision.py:57-63`** — the stated safety invariant, *"a single bad classification can only ever allow, never block (never `exit 2`)"*, is false as written: `permissionDecision: "deny"` **is** a block of that `Write`; `exit 2` is merely a *second* way to block. Finding [2]'s inverse case is a concrete false-positive deny, and `plan.md:99` concedes a deny is unobservable (no `--json`, no counter, no log). So the feature can block legitimate writes, on a rule tuned by a frozenset of four bare directory names (`constants.py:49`), with no field signal that it is happening. Mitigation: **none** — the escape hatch (`doc_guard_allow`) requires the user to first *diagnose* an invisible deny. Fix: reword the invariant to what the code guarantees ("never blocks the session; only ever denies one `Write`, with a named alternative"), and emit the deny to stderr as well as stdout — stderr is already muted in the hook, so it costs nothing at runtime but is capturable when debugging.

- **[4] `domains/docguard/classify.py:81,85` vs `:89,94,98`** — case handling is inconsistent: the suffix (`rel.suffix.lower()`) and root chrome (`rel.stem.lower()`) are case-folded, but every directory comparison is exact. On the case-insensitive filesystems that are default on macOS and Windows, `Docs/specs/x.md` and `docs/Specs/x.md` both resolve to the same real directories the gate is protecting and both classify as **not planning** (verified). `Docs/` capitalized bypasses the gate entirely, including the filename heuristics, since the location gate runs first. Mitigation: **none**. Fix: case-fold the segment comparisons on the same footing as the suffix.

- **[5] `cli/guard_doc_write.py:61-77` + `domains/config.py:497-521`** — the hook is designed to be installed **globally**, but its enable bit and allowlist come from `.context/config.json` inside whatever repo is currently open — untrusted content in a cloned repo. `doc_guard_enabled: false`, or `doc_guard_allow: ["*"]`, turns a user's global protection off for that repo with zero output. Compounding it, matching is `fnmatch(rel_path, glob)` where `*` crosses `/` (plan open question #4): an author writing `docs/superpowers/*` to exempt one published directory actually exempts everything beneath it recursively — the allowlist is silently broader than its authors will expect, which is validation-as-gesture. (Checked and *not* a threat: `fnmatch.translate` emits atomic groups, so a hostile glob does not ReDoS the hot path — a 45-char `*a*a…b` glob against a 60-char path is sub-millisecond.) Mitigation: **partial** — `read_doc_guard_settings` is correctly bounded (two keys, type-checked, never raises, no full `Config`). Fix: document the `*`-crosses-`/` semantics at the config key, and treat "guard disabled by repo config" as a state worth surfacing once per session rather than never.

- **Verified sound, no finding** — the migration half holds up under the attacks I aimed at it: `migrate.py:115-120` validates every group's containment with `resolve()` on both sides *before* pass 2, so a symlinked `.context/proposals/<slug>` escapes into `MigrationContainmentError` and aborts the whole batch; `_moves_for` always yields ≥1 target under the home, so `_ensure_head`'s un-validated write paths (`:234-258`) are transitively contained; a planted symlink at `proposal.json`/`spec.md` cannot be written through, because `atomic_io._replace_bytes:22-31` and `Path.replace` are both tmp-file-plus-rename and neither follows a destination symlink; `run_git` (`git.py:65-74`) passes an argument list with no shell and absolute paths, so the missing `--` terminator is not reachable as option injection; and the guard reads `tool_input.file_path` only — never `content` — so no document body reaches stdout or any log.
