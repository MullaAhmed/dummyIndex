## Data integrity

- **Local `_atomic_write` diverges from the mandatory convention helper.** `writers.py:115-120` reimplements tmp+`replace` instead of routing through `write_text_atomic` (`domains/atomic_io.py:11-24`). It inherits none of the convention's guarantees. It lacks the `cache/`-style Windows `PermissionError` copy-then-delete fallback (cf. `pipeline/io/cache.py:98-105`). On Windows, `tmp.replace(path)` can raise when a reader holds `INDEX.json`. That leaves the `.tmp` orphan and the prior `INDEX` stale, with no signal. Code wins over the plan's "per the data-access convention" claim (`plan.md:85`). The shape matches, but the resilience does not.
- **Two-file write is not atomic as a unit.** `write_catalog` makes two independent `_atomic_write` calls (`writers.py:25-26`). Each file is individually atomic. The pair is not transactional. A crash or exception between the two writes leaves `INDEX.json` updated and `INDEX.md` stale, or the reverse. Downstream consumers read one as ground truth for the other. `output/docs.py` reads the catalog and can act on mismatched confidence. No cross-file integrity check or shared sha gate exists.
- **`mtime`-derived age signal is non-robust to clock skew / copied files.** `age_delta = newest_code_mtime - stat.st_mtime` (`catalog.py:159`) trusts filesystem `st_mtime` absolutely. A `git clone`/checkout/`cp`/rsync resets doc mtime to "now." A genuinely stale doc then looks `fresh` and grades `high`. Conversely, a clock-skewed mount or a restored backup can show a future or ancient mtime. That mis-buckets the doc. The `fresh` floor at `-1s` (`catalog.py:24`) means even 1s of NTP jitter flips `recent`↔`fresh`. Both map to `high`, so this is harmless here. But the signal has no skew tolerance and no content-based corroboration. `sha256` is computed but never used for staleness.
- **Single scalar `newest_code_mtime` makes age coarse and brittle.** Age judges every doc against the one latest-touched file in the repo (`catalog.py:104,159`). One unrelated edit, such as a formatting sweep, refreshes `newest_code_mtime` for all docs. A stale doc about an untouched subsystem can then show a small `age_delta` and hold `high`. Determinism is preserved. The freshness verdict is only as good as that scalar.
- **`unknown` age → `high` is a deliberate mass-promotion with no stale-catalog backstop.** On a first build, or any run where `newest_code_mtime is None`, every low-broken-ratio doc grades `high` (`catalog.py:85-88,155-157`). That is correct per the plan's first-build rationale (`plan.md:82`). But no separate "catalog itself is stale" detector exists. Nothing flags that the catalog was built against a since-changed AST. Staleness detection is delegated entirely to the external cache manifest (`data-access.md:19-21`). That manifest does not cover the source-docs `INDEX` files specifically.
- **`broken_ratio` float persisted unrounded in the entry; rounding only at the dict boundary.** `DocEntry.broken_ratio` stores raw `len(broken)/len(refs)` (`catalog.py:153,183`). The plan says `to_dict` rounds to 4 places (`plan.md:54`). The grading thresholds (`_classify_confidence`, `catalog.py:77,85`) compare the *unrounded* value against `0.10`/`0.40`. The serialized JSON shows the rounded value. So a doc graded off `ratio=0.10000001 > 0.10` can display `0.1000`. That is a small but real audit-trail divergence between the stored signal and the verdict it drove. It is deterministic, but not self-consistent on inspection.
- **Confidence ordering relies on a lookup with a silent default.** Sort uses `DOC_CONFIDENCE_ORDER.get(e.confidence, 3)` (`catalog.py:192`). Any value missing from the map sorts last without error. Today the set is closed (high, medium, low via `DocConfidence`), so byte-identical re-runs hold. A future enum member would be absorbed without a contract failure. That erodes the "council can trust it" determinism guarantee (`plan.md:79`).
- **JSON written with `sort_keys=False`.** `writers.py:24` serializes with `sort_keys=False`. The convention at `dummyindex/context/build/meta.py:98` adds `sort_keys=True` for byte-identical re-runs. Its source is `.context/conventions/data-access.md:13`, a `.context/` doc. Reality-check cannot resolve it against source. Determinism here rests entirely on `to_dict` emitting keys in a stable insertion order. That holds for frozen-dataclass `to_dict`. It is a weaker guarantee than the convention's explicit sort. It would break silently if `to_dict` key order ever shifts.

## Security

Adversarial lens: this engine reads arbitrary prose docs. These include external trees the user points at with `--docs PATH`. It trusts their bytes and metadata. The dominant risks are resource-exhaustion DoS from untrusted file content. The other is symlink-mediated reads of files outside the intended doc roots. Backtracking is **not** a real threat here. It was empirically confirmed below. It is recorded as a non-finding, not padded into one.

- **Unbounded full-file read of arbitrary `--docs` content: memory-exhaustion DoS (High).** `build_doc_catalog` does `data = p.read_bytes()` (`catalog.py:139`). `extract_doc_text` re-reads the whole file (`refs.py:218-242`). Neither checks size first. There is no `size_bytes`/`st_size` pre-check, even though `stat()` runs one line later (`catalog.py:140`). `size_bytes` is already a model field (`models.py:15-52`).
  Attack path: `dummyindex ... --docs /path/with/huge.md`, or a multi-GB sparse or real `.txt` planted in any walked doc root. Every file under that root is slurped whole into RAM. A second full copy is then materialised as `text`. `sha256(data)` hashes the whole buffer (`catalog.py:176`). A single oversized doc, or a `/dev/zero`-fed regular file, OOM-kills the indexer. No streaming, no cap, no per-file budget.
  Remediation: skip or truncate files whose `stat().st_size` exceeds a constant cap, such as `_MAX_DOC_BYTES` in `constants.py`. Do this **before** `read_bytes`. Hash through a streamed `hashlib` chunk loop.
- **Decompression-bomb DoS via office/PDF converters (High).** `.docx`, `.xlsx`, and `.pdf` go to third-party parsers with no resource guard. `xlsx_to_markdown` calls `openpyxl.load_workbook` (`detect.py:226`). `docx_to_markdown` calls `python-docx`'s `Document` (`detect.py:186`). `extract_pdf_text` calls `pypdf.PdfReader` (`detect.py:168-170`).
  `.docx` and `.xlsx` are ZIP containers. A ~tens-of-KB zip-bomb spreadsheet expands to gigabytes of cell strings. `xlsx_to_markdown` accumulates **every** cell of **every** sheet into an in-memory `rows`/`sections` list (`detect.py:235-244`). It has no row or cell cap. A crafted PDF with millions of glyph ops makes `page.extract_text()` (`detect.py:173`) burn unbounded CPU.
  The blanket `except Exception` (`detect.py:177,217,249`) only catches *raised* errors. It does **not** bound memory or wall-clock before the bomb detonates.
  Attack path: `--docs DIR` containing one malicious `.xlsx`.
  Remediation: gate office and PDF parsing behind the same size cap. Cap rows, cells, and pages processed. Consider running converters in a subprocess with an RLIMIT/timeout.
- **Symlinked doc *files* in a `--docs` root are read through to their target: path-confinement bypass (Medium).** The doc walk uses `os.walk(root)` with default `followlinks=False`. That stops directory-symlink descent. But `os.walk` still *yields* symlinked **files**. Each one is resolved and later read wholesale (`catalog.py:139`, `refs.py:218-242`).
  Attack path: a `--docs` root, such as a shared or cloned docs folder, contains `notes.md -> /etc/passwd` or `-> ~/.ssh/id_rsa`. The symlink target's **bytes flow into `INDEX.json`**. Its `sha256`, `size_bytes`, harvested headings, title, and backticked tokens become catalog content. The `abs_path`/`path` fields show the *resolved* target outside the repo. This is read-amplification: a doc tree an attacker can write into exfiltrates readable files into a committed artifact.
  The repo's own deep walker defaults `follow_symlinks=False` and prunes self-referential link loops (`detect.py:352,414-421`). But the doc-catalog `walk_doc_files` has **no symlink check at all**.
  Remediation: in the doc walk, skip entries where `p.is_symlink()` before resolving. Or, after resolving, assert the target stays under the intended root. Apply the same to in-repo discovery's root `iterdir` (`discovery.py:79-84`).
- **`--docs` roots are explicitly de-confined. External absolute paths are by design, but the catalog does not flag them as untrusted (Medium).** `_relpath_or_abs` marks anything outside `repo_root` as `is_external=True` with an absolute `path` (`catalog.py:92-97`). `_attribute_source_root` attributes it to the `--docs` root (`catalog.py:206-222`). That is correct provenance. But `is_external` is a *display* flag only. External-doc bytes feed the **same** confidence grading. Downstream, `generate_project_md` can lift an external README's first paragraph into `PROJECT.md` (per spec `output/docs.py:122-194`). A doc the repo owner never wrote, planted in a sibling `--docs` dir, can become the project's self-description. It can also seed `extra_names` and title tokens the grader trusts. The threat is content trust, not traversal. The tool treats external prose with the same authority as in-repo prose.
  Remediation: never source the `PROJECT.md` description from `is_external` docs. Visibly tier external docs below in-repo ones in confidence.
- **`_attribute_source_root` compares a resolved doc path against an *unresolved* `repo_root` in one branch (Low).** `build_doc_catalog` resolves `repo_root` up front (`catalog.py:124`). It passes that resolved value on. So today the `doc_path.relative_to(repo_root)` check (`catalog.py:216`) is sound. But the helper re-`.resolve()`s only `extra_doc_roots` (`catalog.py:211`), not `repo_root`. A future caller passing an unresolved or symlinked `repo_root` would mis-attribute in-repo docs as external, with an empty `source_root`. The impact is defensive and low today. It is flagged because the resolution contract is implicit, not enforced at the helper boundary.
- **Doc content is trusted as ground-truth signal, but the trust is bounded (informational).** Backticked tokens harvested from prose (`extract_code_refs`, `refs.py:191-205`) and JSON keys (`harvest_json_keys`, `keys.py:13-47`) only *widen* the known-name set. That set marks refs as non-broken. They never execute, and they never index into the AST. `harvest_json_keys` caps at `limit=5000` keys (`keys.py:15,30`). So a hostile doc can at worst *suppress* its own `broken_refs`. It can grade itself falsely `high` by citing plausible tokens. This is self-serving confidence inflation, not code execution or cross-doc tampering. It is worth noting, because the council consumes `confidence` as evidence. A doc can lie its way to `high`. No fix is required beyond awareness. The `broken_count ≥ 4` floor and ratio thresholds (`catalog.py:77-89`) limit the blast radius.
- **Non-finding (regex): no catastrophic backtracking.** `_INLINE_CODE_RE`, `_CODE_FENCE_RE` (`re.DOTALL`), and the shape regexes (`_DOTTED_RE`, `_FILE_PATH_RE`, etc., `refs.py:13-21`) were measured against adversarial inputs. Per-token regexes are anchored and bounded to ≤160 chars (`refs.py:14,166-205`). The whole-document `fence` and `inline` passes ran linearly, about 0.03s on 3 MB of pathological backticks. The harvest regexes are not a ReDoS vector. Recorded so it is not re-raised. The real doc-DoS lives in unbounded I/O and the office/PDF converters above, not the regex layer.

## Product surface

- **No docs at all (greenfield repo): catalog still builds, `INDEX.md` shows a self-recovery hint (minor gap).** With zero discovered docs, `_render_catalog_md` emits `_No documents discovered. Pass --docs PATH..._` in its header (`writers.py:33-51`). That is good UX. But `INDEX.json` is still written with `docs: []` and `default_discovery_used: true`. `output/docs.py:_render_doc_section` short-circuits to a "no docs" line (`output/docs.py:260-298` region). Gap: a user who expects docs gets a silent empty catalog. Example: a `docs/` dir of `.adoc` or `.org` files. Nothing hints that the extension set is closed. `.adoc`, `.org`, `.tex`, and `.ipynb` are not in `_DOC_EXTENSIONS` (`discovery.py:43-48`), and they are never reported as skipped.
- **Many docs — `INDEX.md` table is uncapped, but `PROJECT.md` section caps at 5 with no "+N more" — inconsistent capping.** `_render_catalog_md` renders every doc as a table row (`writers.py:56-62`). A 500-doc monorepo gets a 500-row table. That is fine as a catalog. But the curated `PROJECT.md` "notable" list silently truncates to `[:5]` (`output/docs.py:276-280`). It has no "+N more" affordance. The low-confidence broken-ref list does show `_… +{more} more_` (`writers.py:92`). Gap: a `PROJECT.md` reader cannot tell 5 high-confidence docs from 50. The cap is invisible.
- **Confidence-grading surprise: `unknown` age + low broken-ratio → `high`, displayed like a genuinely fresh `high` — trust ambiguity.** On a first build (`newest_code_mtime is None`), every clean doc grades `high` (`catalog.py:86-87,155-156`). It renders `**high**` with age column `unknown` (`writers.py:61`). A user scanning the confidence column sees `high` and trusts it. But `unknown` age means freshness was never evaluated. The `high` rests only on broken ratio. Gap: `high` conflates "verified fresh and clean" with "clean, freshness unknown." The age column carries the caveat. The bold confidence verb dominates the eye. No visual tier separates "high (fresh)" from "high (unknown age)".
- **Confidence-grading surprise: a doc with zero refs always grades on age alone. A prose-only README can be `high` while saying nothing checkable.** `broken_ratio = 0.0` when `refs` is empty (`catalog.py:153`). A doc with no backticked tokens sails to `high` if recent or unknown (`_classify_confidence`, `catalog.py:85-89`). The `INDEX.md` broken-refs column shows `—`. That is correct. But the `high` badge implies "safe to quote," when nothing was cross-checked. Gap: "0 refs, high confidence" reads as endorsement. It is unfalsifiable. A `referenced_count == 0` doc should arguably be tiered separately, not lumped with genuinely verified `high`.
- **Broken-ref false-positive surface: one global name-set flags correct cross-project refs.** `find_broken_refs` matches each token against `symbol_names ∪ file_paths ∪ extra_names ∪ whitelist` (`catalog.py:148-153`). There is no per-doc scoping. Gap (UX): in a monorepo, a `--docs ../other-service/README.md` citing `OtherService.handle` is reported `broken`. The symbol exists, but not in *this* repo's AST. That can drag the external doc to `low`. `writers.py:73-93` lists it under "Low-confidence docs". There, the legit symbol shows as "no longer in the AST." This is a confusing false signal. The remediation (`extra_names` or `--docs` co-indexing) is not surfaced to the user.
- **Staleness signal clarity: `aging` docs get no day count.** The `INDEX.md` "X day(s) before the newest code change" line renders only for `stale` and `old`. `writers.py:95-99` gates the day delta on `age_bucket in ("stale","old")`. An `aging` doc, 31 to 90 days old (`catalog.py:26`), shows only the bucket word `aging`. No day count appears anywhere. Gap: the most actionable staleness number is hidden for the middle bucket. A user must open `INDEX.json` for `age_delta_seconds`. Also, "before the newest code change" is computed against the single global `newest_code_mtime` (prior Data-integrity §6). The day count can read large because of one unrelated edit, not because *this* doc's subsystem changed.
- **Staleness signal clarity: the catalog has no "I am stale" banner.** `generated_at` is present but never compared to current source. `DocCatalog.generated_at` is an ISO timestamp (`catalog.py:196-198`). `INDEX.md` and `_render_doc_section` never state how old the catalog is. The drift hook (`plan-update`, `help.py:51`) reports *feature-doc* drift via the cache manifest. That manifest "does not cover the source-docs `INDEX` files specifically" (prior Data-integrity §5). Gap: a user reading `source-docs/INDEX.md` cannot tell whether the confidence verdicts used today's code or last month's. The `_ADVISORY_BANNER` (`writers.py:31`) is generic, not freshness-aware.
- **`--docs` external-root UX: missing paths warn-and-skip silently to stderr. A typo'd root yields a confidently wrong, smaller catalog with no nonzero exit.** `resolve_doc_paths` prints `warning: --docs path not found, skipping` to stderr and drops the path (`common.py:173-178`). The build continues. Gap: in CI or non-interactive runs the warning scrolls past. The run exits 0. The catalog silently omits the intended docs. The user believes their `--docs ./design-docs` was ingested. No summary line exists, such as "ingested 2 of 3 --docs roots." No opt-in strict mode exists either. Compounding: a `--docs` pointing at a *file* versus a dir is not distinguished in the warning.
- **`--docs` external-root UX: external docs are de-confined by design. The only at-a-glance signal is the absolute `path`. The confidence column does NOT tier them below in-repo docs.** `is_external=True` docs render with an absolute path and a non-clickable abs link (`writers.py:104-106`). They appear in the same confidence-sorted table as in-repo docs (`catalog.py:191`, `writers.py:56`). Gap: an external `high` doc sorts above an in-repo `medium` doc. That implies the external doc is the stronger evidence, though its provenance is less trusted. Prior Security §19 flagged the trust dimension. The product gap: the sort elevates external docs, and the table has no "external" column to warn the reader.
- **`--docs` is repeatable and dedup'd by resolved path. Overlapping roots silently double-attribute by first-match order — confusing `source_root` in `INDEX.json`.** `_attribute_source_root` returns the first `extra_doc_roots` entry the doc lives under (`catalog.py:206-215`). Iteration order is the user CLI order. Gap: pass `--docs /a --docs /a/sub`. A doc under `/a/sub` attributes to `/a`, the first listed, not the more specific root. This is a minor provenance surprise. No user-facing explanation of the precedence rule exists.

## Cross-review notes

- **Security §16/§17 (unbounded read / decompression bomb) has a direct product-surface consequence. There is no size column or skip report, so a user cannot SEE which docs were huge.** `INDEX.md` shows no `size_bytes` column, though it is a model field (`models.py:27`). When the indexer OOMs or stalls on a `--docs` tree, no catalog row points at the offending file. The run dies. A `_MAX_DOC_BYTES` cap (Security remediation) should also emit a visible "skipped (too large): path (N MB)" row. The product surface then explains the omission, instead of silently dropping the file.
- **Security §18 (symlinked doc files read through to target) is invisible at the product surface.** The resolved target path lands in `path`/`abs_path`, with no "via symlink" marker. When `notes.md -> /etc/passwd` is ingested, `INDEX.md` shows the *resolved* `/etc/passwd` as the doc path (`catalog.py:165-185`, `_relpath_or_abs` resolves first). It appears with its confidence and headings. A reader auditing the catalog has no signal that the entry arrived via a symlink. Beyond the security fix (skip symlinks), the product surface should mark or omit symlinked entries, so the catalog explains itself.
- **Security §19 partially mitigated in code. Flag for the security critic.** Prior Security §19 warns that an external README's first paragraph can seed `PROJECT.md`. The downstream `_description_from_catalog` already excludes externals. Its README candidate filter is `not d.is_external and d.confidence != DocConfidence.LOW` (`output/docs.py:205-217`). The HIGH-only title fallback has the equivalent check. So the description path is already confined to in-repo docs. Code wins over the §19 "can become the project's self-description" claim, for the description specifically. The residual §19 risk stands. External bytes still feed `extra_names` and title tokens. Those widen the trusted name-set, so they can suppress their own broken refs. Recommend §19 be narrowed accordingly.
