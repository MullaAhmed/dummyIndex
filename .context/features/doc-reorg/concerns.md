## Data integrity

- **Backup-then-gitignore ordering window: the snapshot lands in the worktree BEFORE it is ignored.** `backup_docs` copies every doc into `root/.context/_doc_backups/<utc>/` and writes the manifest (`safety.py:93-116`). Only afterwards does it call `_ensure_backup_ignored` (`safety.py:120`). If `.context/.gitignore` does not yet carry `_doc_backups/`, the certified-clean tree is dirty with the backup itself. That defeats the precondition the reversibility gate established. plan.md:46 asserts the ignore means the snapshot can't dirty the tree. The code writes the snapshot first and ignores second. Reverse the order so the ignore runs before the copy loop. The gitignore must be in place before any backup byte hits the tree.

- **Backup copies and the manifest bypass `write_text_atomic` — the one mandatory persistence rule.** `data-access.md:5-7` ("Atomic writes (the one mandatory rule)") requires every persisted artifact be tmp+`replace`. The manifest is written with a plain `write_text(... )` (`safety.py:114-116`), and each doc via `shutil.copy2` (`safety.py:105`), neither atomic. A crash mid-`copy2` or mid-manifest-write leaves a truncated backup file or half-written `manifest.json`. Restore then reads it (`safety.py:138`) or copies it back as authoritative original content (`safety.py:164`). This is silent corruption of the safety net. Restore *reads* atomically (tmp+`replace`, `safety.py:162-165`). The backup that feeds it does not, so the chain is only as strong as its non-atomic write half. The `.gitignore` append at `safety.py:189-195` is likewise a non-atomic read-modify-write.

- **No verification that the backup captured every in-scope doc — partial backup passes silently at backup time.** `backup_docs` skips any `src` that is not a file (`safety.py:97-98`). It also skips any path resolving outside root (`safety.py:100-102`) with a bare `continue`. It records only what it `captured` (`safety.py:106,111`). A doc that vanishes or errors between discovery and copy is dropped from the manifest. No count check compares the result with the input `files`. The CLI then reports `len(backup.files)` as success (`cli/doc_reorg.py:88`). A short backup reads as complete. The `skipped` honesty surfaces only at *restore* time (`safety.py:158-159`). That is after the destructive session has already run. No backup-time assertion checks that captured count equals in-scope count. The user is told it is safe to proceed before any such check.

- **Atomicity of the multi-file restore is per-file, not all-or-nothing — a mid-restore failure leaves a half-restored tree.** Each entry is tmp+`replace`, and a failed entry unlinks its `.tmp` then raises `BackupError` (`safety.py:161-168`), aborting the loop. Files already `replace`d before the failure stay restored. Files after it do not. The tree is left in a mixed old/new state with no rollback of the partial restore. The gate in plan.md:41 frames it as: even a mid-restore failure leaves the tree clean. That holds only for stray `.tmp` debris, NOT for restore completeness. Because the starting tree was clean, `git restore` is still a full undo. But the *restore command itself* is not atomic across files. It reports nothing about how far it got before raising. Consider catching per-file errors into `skipped` and continuing. Then surface the partial set, rather than aborting on the first `OSError`.

- **`created_since` is recomputed by re-running discovery, so an upstream scope change silently mis-classifies rollback files.** `restore_backup` derives `created_since = current_docs − backed_up` by re-calling `discover_doc_files` (`safety.py:171-175`). That call transitively depends on `source_docs.discovery.discover_default_doc_paths` (`discovery.py:12-14,29`). The plan flags at plan.md:20 that a change to default-doc discovery silently widens or narrows reorg scope. Concretely: if discovery's scope narrowed between backup and restore, a doc that existed at backup time is no longer discoverable. It is then absent from `current`, so it is neither restored-as-missing nor reported. If scope widened, an unrelated pre-existing doc now in scope is mis-reported as `created_since`. The report marks it a reorg artifact that the user may `git clean -fd` (`cli/doc_reorg.py:113-119`). That risks deleting a file the reorg never created. The manifest is the only trustworthy record of backup-time scope. `created_since` should be computed against a re-walk that does not re-consult mutable upstream discovery. Alternatively, the manifest should record enough to make this set difference scope-stable.

- **No-data-loss guarantee leans entirely on a clean-tree precondition the CLI guard does not enforce on the destructive paths.** The library `backup`/`restore` domain calls never invoke `require_clean_tree` themselves. The gate is a separate CLI `GUARD` action (`cli/doc_reorg.py:51-66`) that the user must run first. It re-implements the clean/dirty/unknown branching inline instead of routing through `require_clean_tree` (`safety.py:57-75`), per plan.md:54. Nothing forces `backup` (let alone the session's subsequent in-place edits) to have passed the guard. If a caller runs `backup` on a dirty tree, the backup snapshots already-modified docs as if they were pristine originals. A later `restore` faithfully recreates the *dirty* state, not the committed baseline. The "given a clean starting tree" invariant (plan.md:7) is assumed, never asserted, on the path that writes. The reversibility promise is only as good as the user remembering to run `guard` separately.

- **`git status --porcelain` includes untracked files, so an untracked backup dir or unrelated file blocks the guard. Tampering with `.git` is undetectable.** `git_is_clean` treats any non-empty porcelain output as dirty (`safety.py:54`). That correctly catches a stray pre-existing `_doc_backups/` if it were ever un-ignored. The guarantee that "git is an authoritative undo" (plan.md:7, safety.py:5-7) assumes the user has not discarded git history out-of-band. That is an accepted boundary, not a defect. Noted for completeness; no action required.

## Security

- **Restore path-escape gate is symlink-blind: `.resolve()` passes, then the write follows a symlink out of the repo (`safety.py:149-168`).** The gate computes `dest = (root / rel).resolve()` then asserts `dest.relative_to(root)`. `Path.resolve()` collapses symlinks, so the *check* sees the real target. But if any **parent directory** of `root/rel` is a symlink that resolves under `root` at check time, it passes. Yet `dest.parent.mkdir(...)` (`safety.py:161`) and `tmp.replace(dest)` (`safety.py:165`) still operate on that path. They write *through* the symlink to wherever it points. Concrete path: a planted `docs/` symlink to `/etc` resolves outside root, so it is rejected. But an attacker, or a prior reorg step, plants `<root>/sub` as an in-repo symlink to `<root>/real`. The manifest then holds an entry `sub/x.md`. `resolve()` yields `<root>/real/x.md`, and `relative_to(root)` passes. So the restore clobbers `<root>/real/x.md`. That file is one the manifest's author chose, not the doc that was backed up. The gate proves the *resolved* path is in-repo. It never proves that no symlink was *traversed*. So an in-repo symlink redirects the write to an attacker-chosen in-repo target. `lstat`/`O_NOFOLLOW`-style refusal (reject if any component of `root/rel` is a symlink) is the missing control. Code wins over plan.md:40, which frames this gate as a complete "path-escape" defence. It stops `../` and absolute paths, not symlink redirection.

- **Backup follows symlinks on the source side and silently drops out-of-repo docs.** A reorg edit can then mutate a file no backup protects (`safety.py:95-106`). `src.resolve().relative_to(root)` rejects, via bare `continue`, any in-scope doc whose real path is outside the repo. For example, `docs/shared.md` is symlinked to `~/secrets/shared.md`. That doc is dropped from the manifest with no record. Yet it is still a "doc in scope" that the running session edits in place through the symlink. Result: the session destructively rewrites an out-of-repo file `~/secrets/shared.md` that the backup deliberately never captured. `git restore` cannot undo it, since it is not in the worktree. This is a permanent, un-reversible edit to an arbitrary file outside the repo. It breaks exactly the reversibility promise the package claims to guarantee (plan.md:7). The drop is silent: there is no `skipped` entry or warning at backup time. So the operator is told "N docs backed up" and proceeds believing the edit is reversible.

- **[RESOLVED] Destructive backup ran with NO clean-tree assertion — the reversibility gate was opt-in and the CLI never opted in.** Original finding: `require_clean_tree` was defined but called nowhere in the CLI. `BACKUP` invoked the domain directly, so `backup` on a dirty tree captured already-modified docs as "originals". A later `restore` faithfully reproduced that dirty state instead of the committed baseline. There was no warning that the undo was poisoned. The "given a clean starting tree" invariant (plan.md:7) was assumed by writing paths and asserted by none. **Fixed** when the reorg phase stopped being opt-in. `GUARD` routes through `require_clean_tree` (`cli/doc_reorg.py:55-65`), and `BACKUP` now calls it itself. It exits `1` on a dirty or unknown-git tree before snapshotting anything (`cli/doc_reorg.py:77-89`; tests `test_cli_backup_refuses_dirty_tree`, `test_cli_backup_refuses_non_git_tree`). `RESTORE` remains deliberately ungated. Restoring is the recovery path, so requiring a clean tree there would block the only rollback.

- **`created_since` is fed to the user as a `git clean -fd` target while derived from mutable upstream discovery.** A scope-widen turns rollback advice into a data-loss instruction (`safety.py:171-175`, `cli/doc_reorg.py:113-119`). `restore_backup` computes `created_since = current_docs − backed_up` by re-walking `discover_doc_files` → `discover_default_doc_paths` (`discovery.py:29`, verified in symbols.json). The CLI then literally tells the operator these files "the reorg created" should be dropped with `git clean -fd` (`cli/doc_reorg.py:113-119`). The feature flags this dependency as able to silently widen or narrow scope (plan.md:20). If discovery's default scope widened between backup and restore, a pre-existing, un-backed-up, possibly-untracked file now appears in `current`. It is mis-classified as `created_since`, so the user is told to `git clean -fd` it. That destroys a file the reorg never touched. The set difference trusts live discovery, not the manifest's frozen scope. The irreversible action (`git clean -fd`) is gated on the least trustworthy input.

- **Non-atomic backup writes corrupt the safety net itself.** A crash mid-snapshot yields a truncated manifest/copy that `restore_backup` later treats as authoritative (`safety.py:105,114-116,138`). `data-access.md`'s "atomic writes (the one mandatory rule)" is bypassed on the backup side. Docs use `shutil.copy2` (non-atomic, `safety.py:105`). The manifest uses plain `write_text` (`safety.py:114-116`). A crash or kill mid-`copy2` leaves a truncated backup file that restore copies back as "original" content. A half-written `manifest.json` either fails JSON parse (`safety.py:138-140`, recoverable) or, worse, truncates at a record boundary. It then silently shrinks backup scope, so restore reads as complete while docs are missing. The undo chain is only as atomic as its weakest write. The *producing* half is not atomic. Not remotely exploitable, but it converts a power loss or OOM-kill during backup into silent doc loss. The operator cannot tell this apart from a successful snapshot.

## Product surface

- **No preview/dry-run before the destructive session — the user cannot see what will be edited.** The four verbs are guard/list/backup/restore (`cli/doc_reorg.py:3-7`). `list` prints in-scope docs (`cli/doc_reorg.py:68-76`). No command shows the *proposed* reorg (diff of moves/renames) before editing starts. The user backs up blind, then the session rewrites under per-file Edit confirms. The session offers no upfront "here is the plan" surface. Gap: the only preview is the post-hoc `list` of scope, not the intended changes.

- **Undo is discoverable only at backup time, never at restore-failure or session start; the restore string scrolls away.** The exact restore command is printed once, on the backup line (`cli/doc_reorg.py:89`). If the operator loses that scrollback, there is no `doc-reorg latest`/`doc-reorg list-backups` to rediscover the `<utc>` dir. They must hand-navigate `.context/_doc_backups/`. Gap: undo discoverability hinges on retained terminal output of a single line. No command re-surfaces the most-recent snapshot path.

- **The clean-tree gate is advisory and decoupled — nothing chains guard→backup→edit, so the gate is trivially skippable.** `GUARD` is a standalone read-only exit-code command (`cli/doc_reorg.py:51-66`). `BACKUP`/`RESTORE` never call it. A user who runs `backup` then starts editing without ever running `guard` gets no warning. The plan itself flags, at plan.md:54, that guard bypasses `require_clean_tree`. It also flags that the CLI exposes no such flag. Gap: the messaging frames guard as the pre-check (`cli/doc_reorg.py:4`). But no path enforces or even nudges running it first.

- **`--allow-dirty` exists in the library but is invisible at the CLI.** The documented escape hatch is unreachable from the product surface. `require_clean_tree(..., allow_dirty=True)` is the "single deliberate escape hatch" (plan.md:45, `safety.py:57,63`). Yet the CLI never calls `require_clean_tree` at all and parses no `--allow-dirty` flag (`cli/doc_reorg.py:51-66`). Gap: a user on an intentionally-dirty tree (e.g. mid-feature) has no sanctioned override. Their only option is to ignore the advisory guard entirely, which trains them to disregard it.

- **`restore` hands the user a raw `git clean -fd` instruction for `created_since` files.** It is a destructive command the tool tells the user to run, with no `--dry-run` nudge. On restore the CLI prints "drop them with `git clean -fd` for a full rollback" and lists the files (`cli/doc_reorg.py:113-119`). `git clean -fd` deletes untracked files repo-wide, not only the listed paths. The `created_since` set is derived from mutable upstream discovery (see Data integrity / Security above). Gap: the product surface recommends a blunt destructive command. It never suggests `git clean -nd` (dry-run) first. Nor does it scope the clean to the listed paths. Fatigue/trust here can wipe unrelated untracked work.

- **Per-file Edit confirmation fatigue is unbounded and unbatched.** A large doc tree means one confirm per file, with no scope summary. The destructive edits happen in-session via Edit "so the user confirms each" (`cli/doc_reorg.py:9-11`). `list` shows the count (`cli/doc_reorg.py:75`). But the reorg flow offers no "apply all / apply N" batching surface. Gap: on a repo with dozens of docs, the user faces dozens of individual confirms. There is no running progress or "you are M of N" feedback. This invites rubber-stamping, which defeats the per-file safety the design leans on.

- **What the user loses: no rename/move tracking — restore recreates backed-up paths but cannot tell a rename from a delete+create.** `restore_backup` recreates manifest paths and reports anything new as `created_since` (`safety.py:171-182`, plan.md:31). If the session renamed `a.md`→`b.md`, restore recreates `a.md` (original content). It lists `b.md` as `created_since` to `git clean`. The user loses the *new* content of `b.md` unless they notice and keep it. Gap: the surface presents a rename as created file, drop it. It gives no signal that dropping it discards the reorg output for that doc.

## Cross-review notes

- **Operator impact of the symlink-clobber finding (Security): a restore can silently write to a doc the operator never inspected.** The in-repo-symlink-traversal write (`safety.py:149-168`) means `doc-reorg restore` may clobber `<root>/real/x.md`. The success line reports "restored N doc(s)" (`cli/doc_reorg.py:105`), naming the *manifest* path, not the real target. From the product surface, no signal shows that the restored path differs from the written path. The operator's only feedback is a reassuring count. So the redirection stays invisible exactly when the operator expects verification.

- **Operator impact of the advisory-only clean-tree gate (Security).** The reversibility promise is presented as a guarantee but enforced as a suggestion. Help text bills the safety net as "refuse-on-dirty, backup, and honest restore" (`cli/doc_reorg.py:10-11`) and guard as "the reorg's pre-check" (`cli/doc_reorg.py:4`). But no destructive path calls the guard (`cli/doc_reorg.py:78-101`). The operator reads a refuse-on-dirty guarantee and gets advisory behavior. The gap surfaces only after the destructive session has run. That is exactly when undo is most needed and least sound.
