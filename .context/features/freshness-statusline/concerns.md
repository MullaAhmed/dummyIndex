## Data integrity

- **Concurrent writers race on a fixed `.tmp` name.** `write_text_atomic` derives the tmp as `path.with_suffix(path.suffix + ".tmp")` (`context/domains/atomic_io.py:22`). That is one deterministic `freshness-badge.tmp`, with no PID/uuid uniqueness. Two overlapping `plan-update` runs trigger this. Examples: two SessionStart hooks firing near-simultaneously, or a manual `dummyindex context plan-update` overlapping a hook. Both write the same tmp, then `replace`. On POSIX the final `replace` is atomic per-call, so the *published* badge is never torn. But the two `tmp.write_text` calls can interleave. One `replace` can act on bytes the other writer is mid-truncating. The surviving badge is one writer's value (last-replace-wins). Acceptable for a best-effort projection. It is an unbounded last-writer-wins, not a documented guarantee. Plan claims only "concurrent reader never sees a half-written badge" (`plan.md:31`, `cli/plan_update.py:44-46`). That claim is true. It says nothing about writer/writer. Low severity: the value is idempotent-ish (same `DriftReport`, same badge). Worth one line.
- **No reader/writer atomicity gap, confirmed.** Both readers target the exact final name (`badge_cache_path` → `.context/cache/freshness-badge`, `cli/plan_update.py:34-36`; wrapper `cat .context/cache/freshness-badge`, `dummyindex/skills/statusline/statusline.sh:16`). The transient `freshness-badge.tmp` is a different filename. A concurrent statusline read opens the old badge or the new one, never the tmp. POSIX `rename` over an open read fd is safe. Clean.
- **Read-verbatim vs. byte-faithful write: no corruption, but a latent encoding asymmetry.** The writer is byte-faithful (`atomic_io.py:11-19`, no normalization). The Python reader does `read_text(encoding="utf-8")`, then `print(badge, end="")` (`cli/statusline.py:60-62`). The shell wrapper does a raw `cat` (`dummyindex/skills/statusline/statusline.sh:16`). The badge contains a non-ASCII glyph (`✓`, `drift.py:103`). The two readers can disagree if the host shell's locale isn't UTF-8. `cat` emits raw bytes, and the host renders them per its own encoding. The CLI forces utf-8 decode, then re-encodes via `print` to `sys.stdout`'s encoding. On a non-UTF-8 stdout the CLI path can `UnicodeEncodeError`. That error is swallowed (`cli/statusline.py:64-66`), giving an empty badge. `cat` would still show garbled-but-present bytes. Not corruption, since degrade-to-silent holds. But the two "identical" readers are not byte-identical under a non-UTF-8 host. Unmentioned in `plan.md:31` ("readers echo the file's exact bytes").
- **Best-effort write cannot corrupt or fail the hook: verified.** `_write_badge` is severed from the drift report. It receives an already-computed `DriftReport` and only adds a side effect. The caller wraps it in a bare `try/except: pass` (`cli/plan_update.py:71-74`). That also covers the `mkdir` (`:49`) and any `compute_badge` raise. An unwritable/read-only `.context/cache/` degrades to no badge. It never causes a non-zero exit or perturbed stdout (stdout only touched after, `:76-78`). Matches the load-bearing decision (`plan.md:47`). No Windows `PermissionError` copy-then-delete fallback as in `pipeline/io/cache.py:98-105`. But the outer swallow makes that unnecessary here. Consistent, not a gap.
- **Cache staleness is by-design drift, not data corruption. The badge has no freshness stamp.** The badge refreshes only at SessionStart `plan-update` (`plan.md:51`, `cli/plan_update.py:66-74`). A mid-session source edit leaves `[ctx ✓]` cached while the real state has drifted. The cached file carries *no* mtime/anchor/version of its own. A reader (CLI or wrapper) cannot tell a fresh badge from a stale one. There is no TTL or "stale" sentinel. The intended trade-off (hot path = zero recompute). But it means the badge can confidently assert "no drift" when drift exists, with no in-band way to detect it. The cache layer convention fingerprints staleness via `manifest.json` mtime/size compare (`conventions/data-access.md:19-21`). The badge deliberately opts out of that. So consumers must treat the badge as advisory-only. Worth a one-line note (open question `plan.md:56`).
- **Single-source path holds on the Python side. The shell wrapper is the lone divergence, and it is cwd-fragile.** Writer and CLI reader both resolve through `badge_cache_path` (`cli/plan_update.py:34-36`, imported at `cli/statusline.py:28`), so they cannot diverge. The wrapper hard-codes the relative literal `.context/cache/freshness-badge` (`dummyindex/skills/statusline/statusline.sh:16`). It assumes cwd == project root. A non-root cwd silently reads nothing, giving an empty badge (degrade-to-silent, `plan.md:50,55`). Not a corruption risk (read-only, swallowed). But the relative literal is a second source of truth. It silently rots if `BADGE_CACHE_NAME` (`cli/plan_update.py:31`) ever changes, because the wrapper won't be caught by the import coupling. A test asserting the wrapper's literal equals `badge_cache_path(...)`'s tail would close the divergence.

## Security

- **No command-injection sink: badge bytes are echoed, never evaluated.** `compute_badge` emits only `[ctx ✓]` or `[ctx: N drift]`, with `N` an int (`context/drift.py:91-109`). Wrappers `cat` it (`dummyindex/skills/statusline/statusline.sh:16`) or `Write-Host -NoNewline $badge` (`statusline.ps1:17-18`). The CLI does `print(badge, end="")` (`cli/statusline.py:62`). None use `eval` or `Invoke-Expression`. Tampered content can't run code. Keep it that way. A future `eval "$(cat …badge)"` would turn a writable gitignored cache into per-prompt RCE.
- **Terminal-escape / statusline spoofing via verbatim echo.** The badge is printed unsanitized. Anything that can write `.context/cache/freshness-badge` (hostile dep, cloned repo, co-tenant) can plant ANSI/OSC escapes. Those render every prompt (`dummyindex/skills/statusline/statusline.sh:16`, `cli/statusline.py:62`). Display tampering, not RCE. Strip C0/C1 control bytes in the Python reader before `print`.
- **Attacker-plantable trust input, no integrity check.** Gitignore (`.gitignore:19`, `.context/.gitignore:3`) excludes only *your* commits. A cloned hostile repo can ship its own badge. There is no signature, owner, or freshness check. The reader trusts the bytes (`cli/statusline.py:60`). `git clone evil && cd evil` → first prompt renders the planted badge (can fake `[ctx ✓]`). Advisory only, never a security signal.
- **cwd-relative read widens surface.** Wrappers read the relative literal against process cwd (`dummyindex/skills/statusline/statusline.sh:16`, `statusline.ps1:17`). There is no root confinement or canonicalization. Entering an attacker tree via `cd` renders its planted badge. The Python cold path gates on resolved root (`cli/statusline.py:47-53`), but it isn't the per-prompt path.
- **Emit-only summary feeds the session prompt, not the shell: bounded.** `render_drift_summary` (`context/drift.py:178-201`) feeds `additionalContext`. Malicious feature/path names are generic SessionStart prompt-injection, never a shell. Badge writer severed and swallowed (`cli/plan_update.py:39-50,71-74`). A write failure can't fail the hook or touch stdout.
- **Swallow-all blinds tamper detection.** Every error becomes silent-empty (`dummyindex/skills/statusline/statusline.sh:16` `|| true`; `statusline.ps1:15`; `cli/statusline.py:64-66`). A planted or flipped badge gives no signal. Document the statusline as non-authoritative. Verify drift via `dummyindex context plan-update`.

## Product surface

- **Setup discoverability hinges on one transient `print` during `hooks install`.** The nudge is surfaced only in the `for nudge in result.nudges: print(f"  {nudge}")` loop of `cli/hooks.py:69-70`. That loop runs during `dummyindex context hooks install`. A user who installed hooks before this feature shipped never sees the wiring tip again. The same holds for a user who scrolled past that one line. `statusline_nudge` is *emit-only*. It is re-checked only on the next install (`context/hooks.py:225-241`, `:400-403`). Gap: no `status`/`doctor` surface re-emits the nudge. The badge is effectively undiscoverable post-install, except by reading `plan.md`. The cold-path command `dummyindex context statusline` itself prints nothing when unwired (silent by contract, `cli/statusline.py:50-56`). A curious user running it gets no "you haven't wired this" hint.
- **The nudge snippet hard-codes the Python cold path and never mentions the shipped wrappers.** `_STATUSLINE_NUDGE` advises `"command": "dummyindex context statusline"` (`context/hooks.py:201-205`). But `plan.md:11,21,49` says that command is only the *cold-path fallback*. The shell wrappers (`statusline.sh`/`.ps1` under `SCRIPT_DIR`, `cli/statusline.py:34`) are the deliverable and the real per-prompt hot path, per plan wording. Gap: the one discoverability surface points users at the slow path. It never tells them the fast `cat` wrappers exist or where `SCRIPT_DIR` is. A user can't find the wrapper they're supposedly meant to wire. The wrappers' own header comments give wiring JSON (`statusline.sh:14-15`, `statusline.ps1:13-14`). You'd only see those if you already located the file.
- **Badge meaning is undocumented for users: `[ctx ✓]` vs `[ctx: N drift]` is only explained in docstrings.** The semantics live in `compute_badge`'s docstring (`context/drift.py:92-101`: N = distinct drifted files + unassigned-new + awaiting-enrichment) and the cold-path module docstring (`cli/statusline.py:14`). Gap: nothing user-facing (no README/help text) tells a wirer what `[ctx ✓]` asserts or what the integer in `[ctx: 3 drift]` counts. The badge reads as opaque. Worse, `N` is a *composite* of three different signals (mtime drift + two commit-anchored signals, `drift.py:104-108`). A user seeing `[ctx: 3 drift]` cannot tell whether that's 3 edited files or 1 file + 2 unindexed. The badge offers no drill-down path. The real detail is in `render_drift_summary`, shown only at SessionStart (`drift.py:178-201`).
- **Stale-cache badge is actively misleading on the hot path, with no in-band tell.** Confirmed by-design (`plan.md:51`, Decisions). The badge refreshes only at SessionStart `plan-update`. So a mid-session edit leaves `[ctx ✓]` rendered every prompt while drift exists (`cli/plan_update.py:66-74`). From the *user's* seat this is the sharpest product gap. It shows a green check for an entire session after source edits. There is zero affordance (no dimming, no age, no `[ctx ✓?]`). Nothing signals that this is a cached snapshot from session start. Open question `plan.md:56` flags it. It needs a user-facing note. No such note exists in any shipped surface. The wrappers' header comments (`statusline.sh:1-15`) don't mention it. A user will reasonably trust the green check and be wrong.
- **"What if not wired" degrades to total invisibility, indistinguishable from "wired but no drift".** If the user never wires `statusLine`, there is no badge anywhere. If they wire it but no `plan-update` has run yet, the readers print nothing (`cli/statusline.py:54-56`, `dummyindex/skills/statusline/statusline.sh:16` empty `cat`). Gap: "not wired" and "wired but cache cold" look the same. A decode error with a cache present also renders empty, even when there is genuinely no drift (`cli/statusline.py:64-66`). All of these collapse to the same empty render. Users cannot self-diagnose their state from the statusline alone. The only signal that wiring *worked* is a non-empty badge. That itself requires a `plan-update` to have fired first. The first-run ordering (wire → start a session so `plan-update` writes the cache → see badge) is never spelled out. So a user who wires it and sees nothing will reasonably conclude it's broken.
- **Cross-platform parity is structurally good, but the nudge and docs are sh-only.** Both `statusline.sh` (POSIX) and `statusline.ps1` (pwsh) ship with matching contracts (`statusline.ps1:1-20` mirrors `statusline.sh:1-16`). The ps1 header even gives Windows wiring JSON with `pwsh -File` (`statusline.ps1:14`). Gap: the single discoverability nudge (`context/hooks.py:201-205`) is platform-agnostic only because it points at the Python command, not the wrappers. No guidance tells a Windows user whether to wire `statusline.ps1` or the Python command. `plan.md` never states the wrappers require `cwd == project root` on *either* platform. The cwd-relative `.context/cache/freshness-badge` literal (`dummyindex/skills/statusline/statusline.sh:16`, `statusline.ps1:17`) is the trap. A Windows user wiring the absolute ps1 path from a non-root cwd gets a silently empty badge with no error. Same trap as POSIX, undocumented on both.
- **No uninstall or un-wire story for the badge.** `statusline_nudge` deliberately never writes `statusLine` because a scalar has no sentinel to safely un-clobber (`plan.md:48`, `context/hooks.py:198-200`), which is correct. But the inverse is also unaddressed. Nothing tells a user how to *remove* the badge once wired. `hooks uninstall` (`cli/hooks.py:74-82`) only touches the hooks block. It leaves the user's `statusLine` (and the gitignored cache) in place. Minor, but "how do I turn this off" has no documented answer. That fits the emit-only design, but worth one line.
