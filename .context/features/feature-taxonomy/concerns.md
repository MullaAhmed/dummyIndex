## Data integrity

- **No cross-file atomicity. Only per-file atomicity.** Each op persists `feature.json`, `INDEX.json`, `INDEX.md`, and `graph.{json,html}` as *independent* tmp+`replace` writes (`helpers.py:131-140`). `assign_files` does `_write_json(feature_json)` → `_write_pending_marker` → `_update_index_counts` → `_refresh_index_artifacts` as four separate replaces (`placement.py:170-182`). Validate-before-write makes a *rejected* op a clean no-op. A crash or SIGKILL *mid-sequence* leaves the canonical machine map permanently out of sync with the feature folder. Example: a crash after `feature.json` updates but before `INDEX.json`. There is no journal and no rollback. The plan's "atomic persistence" claim (`plan.md:23,45`) holds per-artifact, **not** across the 3-5 artifacts one op mutates. Same risk for `merge_feature`, which spans section.md → feature.json → folder delete → INDEX → graph → council-log (`ops.py:226-342`). A crash after `_rmtree(src)` (`ops.py:263`) but before the INDEX drop (`ops.py:266-299`) strands an INDEX entry pointing at a deleted folder.

- **Member derivation is deterministic but silently empties on an absent or stale symbols map.** `_members_for_files` returns `()` when `map/symbols.json` is missing (`placement.py:463-465`, `_load_symbols_map` `indexes.py:177-182`). A `scaffold`, `assign`, or `unassign` run before or without a maps rebuild writes `members: []` and `member_count: 0`. It lands in both `feature.json` and `INDEX.json`. It looks authoritative. Determinism holds only against the symbols-map snapshot at op time. Nothing re-derives members when `symbols.json` later changes. `rebuild --changed` rebuilds the map, but no placement re-runs. So `members` can silently drift from the symbol set the files contain. The plan flags the absent-map tolerance as deliberate (`plan.md:40,61`). It does not flag the resulting count drift in INDEX.

- **`merge_feature` does NOT re-derive members. It set-unions raw lists.** Unlike placement, merge combines target and source `members`, `files`, and `entry_points` by dedup union (`ops.py:253-257`). It does not re-run `_members_for_files` over the combined file set. If source `members` were stale (derived against an older symbols map), they propagate into the target unchecked. That breaks the "members follow files" invariant (`plan.md:40`) for the one op that crosses two features' member sets.

- **Duplicate-id rejection covers scaffold, but the INDEX can hold duplicates from a partial merge or rename.** `scaffold_feature` rejects an existing folder id (`placement.py:78-82`). `_validate_placement_id` blocks reserved `community-*` ids (`placement.py:395-403`). Folder-level dedup is sound. But `_append_index_entry` blindly appends. It never scans for an existing `feature_id` entry (`placement.py:489-509`). It relies on the folder-existence guard upstream. A prior op may have crashed, leaving a stale INDEX entry (see the cross-file point). Or `rename` may have partly completed. A scaffold of a *new* folder whose id collides with a stranded INDEX row yields two entries for one id. `_update_index_counts` and `_drop_index_entry` then update or drop *all* matching rows ambiguously (`placement.py:521-524`, `placement.py:537`).

- **`rename_feature` referential update is best-effort per artifact, not all-or-nothing.** It updates `feature.json`, every `flows/*.json` `feature_id`, INDEX.json, INDEX.md, and graph.json. Each write is guarded and independent (`ops.py:65-149`). Each guard is `if <file>.exists()`. So a missing graph.json silently skips graph rewiring, while INDEX still updates. The folder is renamed. But `graph.json` nodes and edges still carry `from_id`. That happens if graph.json was absent at a prior step, then regenerated stale elsewhere. No post-condition verifies that all four references converged on `to_id`.

- **Idempotency of `assign`/`unassign` is real for the file set. The pending-enrichment marker is re-dropped every call.** Re-assigning an already-owned file is a clean no-op on `files` (set union, `placement.py:163`). Every call unconditionally re-writes `.pending-enrichment` (`placement.py:173`, `placement.py:248`). So a no-op-effect assign still re-flags the feature for enrichment. That blocks `reconcile-stamp` (`plan.md:41,68`). Idempotent on payload, **not** on enrichment state.

- **`graph.json` regenerates from disk while `INDEX.json` is hand-edited. That gives two divergent sync paths.** After a mutation, `INDEX.json` is patched in place (`_append`, `_update`, `_drop` in `placement.py:489-548`). `graph.json` is fully rebuilt by walking `features/*/feature.json` (`indexes.py:51-104`). The two can disagree. A `feature.json` on disk may be stale against its INDEX row, for example after the partial-write window above. INDEX then shows old counts, while the graph shows current file contents. `_refresh_index_artifacts` swallows `FileNotFoundError` (`placement.py:562-563,567-568`). So a missing INDEX.md or graph leaves the op "successful". Navigation artifacts are absent, with no warning.

- **The ranked seed degrades silently. A lost `seed-rank.json` reorders the whole scan with no warning.** `load_seed_rank` returns `None` on a missing, unreadable, or wrong-shaped artifact. It skips malformed rows (`scan/rank.py:57-87`). The seed then falls back to file-count ordering (`seed.py:160-175`). That is deliberate for repos without a symbol graph. But a *corrupted* artifact on a repo that had one demotes the seed's selection and ordering. Different features may survive the node cap. Nothing reports it. Not the seed, and not `scan-check`, because the rank is not part of the scan contract. The only on-wire tell: fallback seed nodes carry no `evidence` or `symbolRef` fields at all. The same silent-degradation shape applies to viewer extras. `load_viewer_extras` leaves the placeholder island on any read failure (`viewer/extras.py:188-200`). So a `graph.html` rendered before or without the artifacts has no tier 2 or 3. It gives no message saying why.

- **`_drop_index_entry` flow_count decrement trusts the INDEX row's own `flow_count`.** It subtracts the dropped entry's recorded `flow_count` from the top-level total (`placement.py:540-546`). If that per-entry count drifted from the actual `flows/*.json` on disk, the top-level `flow_count` is wrong. Nothing reconciles it from disk. The plan notes "no disk-rebuild helper" for INDEX (`plan.md:36`). The same trust-the-stored-count pattern appears in `merge_feature` (`ops.py:275`) and `remove_flow` (`ops.py:413,418`).

## Security

- **RESOLVED (viewer rewrite): stored XSS via the raw `confidence` chip.** The v1 viewer built grid-card chips by string concatenation. It assigned them with `sub.innerHTML = chips`, interpolating `f.confidence` unescaped. A `feature.json` carrying `"<img src=x onerror=…>"` in `confidence` would run on the next `graph.html` open. The sink is gone. It no longer renders feature cards or a confidence chip. `graph.json` no longer carries per-feature confidence into the DOM. In the schema-v2 viewer, every scan string reaches the DOM through `esc()` or `textContent` (`context/output/viewer/script.py`). **Keep the underlying lesson:** the payload is model- and PR-authored. Treat every scan field as untrusted at render time.

- **RESOLVED (viewer rewrite): `file://` origin plus CDN script, no CSP.** The v1 viewer `fetch()`ed `graph.json`, so it needed `python3 -m http.server`. It loaded `d3` from `cdn.jsdelivr.net` with no CSP or SRI. So any injected payload could read sibling `.context/` files. The viewer now makes **no network requests of any kind**. There is no CDN, no SRI to get wrong, no `fetch`, and no `XMLHttpRequest`. The scan is inlined as a `<script type="application/json">` data island. So it opens over `file://` with nothing to fetch. Guarded by `tests/context/domains/features/test_scan_artifact.py::test_viewer_makes_no_external_requests`.

- **REVIEWED CLEAN (graph consumption upgrade, commit 1921bbf): the tier-2/3 viewer adds a second Python-written island and new DOM sinks. All hold the established discipline.** Both v1 XSS concerns above **stay retired**. The upgrade reintroduced neither a `fetch`/CDN path nor an unescaped interpolation. The `graph-extras` island passes through the same `_embed` neutralization as the scan island. `</` and `<!--` are rewritten (`viewer/__init__.py:117`). Every extras string that reaches HTML in `tiers.py` goes through `esc()`: community cards, panel, and ghost labels and paths. Two values land *outside* an HTML-text context. They are folded onto closed alphabets first. `evidence` goes through `safeEvidence` before it becomes a class name. `relation` goes through `safeRelation` before the ghost verb slot (`tiers.py:34-37`). This mirrors `safeKind`. Community link `weight` is coerced through `Number()` before any `strokeWidth` math. The expansion lookup is `Object.prototype.hasOwnProperty`-guarded. So a `symbolRef` of `__proto__` finds nothing (`expansionFor`, `tiers.py:191`). Guarded by `tests/context/output/test_viewer_extras.py::{test_extras_island_neutralizes_hostile_strings, test_extras_keep_the_viewer_offline, test_viewer_js_folds_evidence_onto_a_closed_alphabet, test_viewer_js_folds_expansion_relations_onto_a_closed_alphabet}`. Extras payloads are extraction- or model-derived, and untrusted at render time. Any future sink must either `esc()` or fold onto a closed alphabet. It must never interpolate raw.

- **id-slug path traversal is correctly closed. Keep it that way.** `_validate_feature_id` is a strict whitelist: `[a-z0-9-_]`, no `.` or `/`, and no leading/trailing `-` (`helpers.py:18-29`). `_validate_placement_id` adds the reserved `community-*` block on top (`placement.py:395-403`). `remove_feature` validates the slug BEFORE deriving `feat_dir`. So a `../sibling` id cannot reach `_rmtree` of an out-of-tree dir (`placement.py:292-296`). No traversal via id on scaffold, assign, or remove. It is flagged so a future "allow richer ids" change does not silently regress it. For example, permitting `.` would reopen `_rmtree`/folder-creation traversal.

- **`assign_files` path containment is enforced, but `.resolve()` follows symlinks.** `_normalize_files` does `(repo_root / f).resolve()`, then `relative_to(repo_root)`. It errors on out-of-repo paths (`placement.py:419-427`). This correctly blocks `--file ../../etc/passwd`. But `.resolve()` canonicalizes through symlinks. A repo-internal symlink to an outside target is rejected. A symlink whose target is *inside* the repo stores the canonical inner path. The residual risk is TOCTOU and semantic. The stored repo-relative string later feeds `graph.html`, docs, and `(repo_root / f).is_file()` re-checks in `_live_files` (`placement.py:348`). A path that was a file at assign time, but is later replaced by a symlink, changes what `remove_feature`'s live-guard sees. Low severity (local, single-user CLI), but worth a note. Containment is path-string-based, not inode-pinned.

- **`unassign_files` and `_normalize_for_removal` skip the `is_file()` stat. Containment relies solely on `relative_to(repo_root)`.** By design, removed files no longer exist, so the function does not stat them. It rejects out-of-repo paths only via `relative_to` after `.resolve()` (`placement.py:447-453`). `Path.resolve()` on a non-existent path still normalizes `..` without touching disk. So `--file ../../x` is rejected, and containment holds. No write touches the named path. It only edits the feature's `files` list. So even a containment miss cannot write outside the repo. The blast radius is a bad entry in `feature.json`, not an arbitrary filesystem write. Correct but load-bearing: removal security depends entirely on `relative_to`, since the existence gate is intentionally absent.

- **Superseded: feature `name`/`summary` reaching Markdown and HTML.** The v1 analysis found these escaped in the viewer and raw in `INDEX.md`. The risk was content spoofing only, with no script execution. `INDEX.md` is unchanged, and that assessment still holds. The HTML half now concerns scan fields, not feature fields. Two of them are **bounded rather than escaped**, because they do not land in an HTML context. `kind` is folded onto the closed `ScanNodeKind` alphabet by `safeKind()` before it reaches a class name or a `--kind:var(--k-…)` custom property. Otherwise `x);color:red;--y:(` would inject into `style.cssText`. `stats` values are `esc()`d on their way into the header. Server side, `_embed()` rewrites `</` and `<!--`, so scan text cannot close the data island early.

## Product surface

- **Merge silently discards source flows and never merges flow accounting.** An operator runs `features-merge from=A into=B`, and B is left with fewer flows than the union. Gap: `merge_feature` set-unions only `members`, `files`, and `entry_points` (`ops.py:253-257`). `flow_ids` is NOT in that key tuple. The source flow `.json/.md` files are deleted with the folder, via `_rmtree(src)` (`ops.py:263`). The graph step then drops the source flow nodes entirely (`ops.py:309-314`). So flows that documented behavior in the absorbed feature vanish. They are neither re-parented to `into_id` nor folded into the section prose. Contrast `rename`, which DOES re-point every `flows/*.json` `feature_id` (`ops.py:86-93`). An operator who consolidates a "trivial" feature that owns a real flow loses that flow, with no warning. The success line reports only a file-touch count (`cli/features.py:163-166`).

- **Merge is `supporting`-only, and the error names no path to widen it from the CLI.** Gap: an operator who wants `as-section=noise-absorbed` gets exit 2. The allowlist cannot be extended without editing source. `as_section` is gated against `_VALID_MERGE_SECTIONS` = `{"supporting"}` (`ops.py:230-233`, `constants.py:91`). The CLI defaults to `supporting` (`cli/features.py:132`). There is no `--allow-new-section` escape hatch on `features-merge`. `section-write` has one (`cli/features.py:19-29`). The docstring says broadening "requires updating the procedure in `18-filter-trivial.md`" (`ops.py:217-221`). That is a code or skill edit, not an operator flag. The same repo offers `--allow-new-section` elsewhere, so an operator reasonably expects it here. The rejection message does not say it is source-only.

- **No `split` op exists, despite the taxonomy domain claiming the council can "reshape that taxonomy in place".** Gap: an operator who must break one over-broad feature into two has no command. `plan.md:23` advertises a "family of atomic CRUD ops" to reshape the taxonomy. The delivered verbs are rename, merge, scaffold, assign, unassign, remove, remove_flow, and write_section (`plan.md:10-11`). Splitting takes a multi-step workaround. Scaffold a new id with the carved-out files via `scaffold-feature`, then `unassign-files` them from the original. That is two ops, two `.pending-enrichment` drops, and two INDEX edits. The curated prose does NOT follow the moved files. Scaffold writes a fresh stub (`placement.py:107`). Merge is the documented inverse. Its dual, split, is hinted at by the symmetric "reshape" framing. It is never delivered.

- **`assign-files` silently swallows already-owned and missing-from-symbols files.** An operator cannot tell which `--file` args actually landed. Gap: already-assigned paths are dropped by the set union (`placement.py:163`). No count separates new files from skipped ones. `PlacementResult` reports the full merged set, not the delta. If `symbols.json` is absent, or a file contributes no symbols, `members` silently stays `()` or unchanged (`placement.py:466-468`). The feature then gains a file but zero members. The operator sees `member_count` not move, which is easily mistaken for "assign didn't work". No CLI line distinguishes "0 new files" from "files added but no symbols matched."

- **`rename from=A to=B` onto a stale `B` INDEX row writes TWO rows both keyed `B`.** Gap: an operator gets a duplicated, ambiguous INDEX after a rename onto a previously stranded id. The INDEX refresh loop matches `entry.feature_id == from_id OR == to_id` (`ops.py:101`). It rewrites every match to `to_id` (`ops.py:102`). If a prior crashed or partial op left a row for `to_id` (the cross-file atomicity window in `## Data integrity`), rename stamps `to_id` onto both the A row and the pre-existing B row. That yields two `feature_id=B` entries. `_update_index_counts` and `_drop_index_entry` then touch *all* matching rows (`placement.py:521-524`, `:537`). So counts double-apply. Pure-metadata rename (`from==B, to==B`) is the documented idempotent path (`ops.py:43`). The OR match makes a *real* rename onto an occupied id non-idempotent and corrupting.

- **`unassign` refuses to empty a feature, and the asymmetry is a trap.** The error names a two-command detour: an operator removing the last file of a feature is told to use `features-remove`. Yet `assign` happily creates single-file features. Gap: `unassign_files` raises if removal leaves zero files (`placement.py:234-238`). But the reconcile flow "file deleted from repo" must branch. It unassigns if other files remain, else runs `features-remove`. The operator or skill must pre-check the feature's file count before choosing the verb. No single "remove file, and delete the feature if it was the last one" op exists. This is easy to script wrong, and it hits exit 2 mid-reconcile.

- **Graph and INDEX regeneration after every mutation reads possibly stale extraction artifacts.** A placement op can publish a scan or INDEX that disagrees with the just-edited `feature.json`. An operator opens `graph.html` and sees old structure. Gap: placement ops re-derive members at op time from `symbols.json` (`placement.py:164`). When the scan is still the seed, `rebuild_features_graph` regenerates it from the on-disk `feature.json` files. It also uses the symbol graph's edge list and ranked shortlist (`_load_call_links` and `load_seed_rank`, `indexes.py:111-119`). If `symbols.json`, `symbol-graph.json`, or `seed-rank.json` predate the file moves, the derived members and the seed's edges and ordering reflect the old symbol set. INDEX counts reflect the op's snapshot. A curated `INFERRED` scan is preserved verbatim. For it, staleness surfaces through `scan-check` instead. It shows as `symbol_ref_unresolved` errors against the refreshed artifacts, or as the `symbol_ref_unchecked` warning when they are absent. The success messages never warn that a maps rebuild is owed. Plan flags the absent-map tolerance (`plan.md:40,61`). It does not flag that an operator must run `rebuild --changed` BEFORE placement for counts and graph to be trustworthy.
